## Release sequence: expand, establish floor, switch, then remove

1. **Finish code prerequisites with activation off.** Close remaining operation
   ownership/consumer gaps above, validate the intended supported-client matrix,
   and repeat schema/source/bundle/boundary proofs on the exact release heads.
   A green candidate-path suite does not justify turning on every family.
2. **Cut a separate expansion release.** Start from the supported main image;
   include additive schema, compatible capture, exact readiness and durable
   outcome interpretation. Keep behavior outside that scope and old wire intact.
   Do not label the full combined draft "schema-only". Preserve base marker46
   plus the additive router marker; include Group A's owner/profile additions.
   Run old read/write operations interleaved with actual DDL, both exact images,
   boot/restart, migration rerun and image-only auto-revert in isolation.
3. **Deploy expansion with the router off and establish the recovery floor.**
   Use the existing two-machine canary sequence. Record immutable image IDs,
   deployment record, schema/capability evidence and original images. Both serving
   machines and the rollback image must interpret retained command identity,
   pending/UNKNOWN/expired outcomes and generation ownership. Old boot success
   or retained tables alone are insufficient. This deployed floor is not yet
   established by local evidence.
4. **Switch only through the authorized rollout after its pre-rollout gates.**
   Use the existing single `BEELINE_NETWORK_ROUTER_V1` setting; add no family
   switches or hidden fallback. The switch migration must leave the expansion
   image usable and perform no destructive DDL. Canary auto-revert must restore
   the ledger-aware expansion image, preserving writes and outcomes. Measure the
   selected serving cohorts below; full cohort closure follows evidence, not
   the act of enabling a flag. A pre-router historical image is not a safe
   post-command rollback floor.
5. **Remove only after the supported-version and stability evidence.** Rebase
   the held removal build onto the final integrated source, rerun its consumer
   proofs, and finish the remaining generic/legacy sweep before calling removal
   complete. Delete the temporary unified switch after its job is done. Old
   installed phones do not disappear with time: retain their bounded compatible
   ingress until an actual supported-version floor is authorized and enforced.
   Preserve the expansion rollback floor throughout the rollback window; any
   later schema contraction is separate.

The existing promotion and rollback tools swap images, not database history.
