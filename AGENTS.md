## Branch conventions

- **Bringing a corner feature branch up to date with its fixed target is standing merge-preparation authority, for every agent and every merge.** Agents must fetch and merge/rebase the target into the feature worktree without asking for a second permission, resolve conflicts, rerun relevant checks, and commit before review; they still never modify or land the target branch themselves. `Body.publishMergeReady` verifies the feature tip contains the current tip read from the remote's **push URL** (not a potentially different fetch URL) before publishing a review target. If the target moves after approval, `blockMovedTarget` keeps the corner approval standing, starts one automatic `target-sync` continuation, and lands the updated current tip without another human tap. Coverage: `apps/body/src/github-delivery.test.ts` and the standing-instruction assertion in `apps/body/src/body.test.ts`.
- `fm/*` feature branches often stack on each other (PR base is another `fm/*` branch, not always `main`) — check `gh pr list --json baseRefName,headRefName` before assuming a task's target file exists on `main`.
- The local-only `fm-integration-verify` branch (many `fm/*` branches merged together for cross-branch verification) has a pushed origin counterpart: `fm/buzzy-integrated`. If a task references a file that doesn't exist on `main`, check `fm-integration-verify`/`origin/fm/buzzy-integrated` before concluding the task's premise is wrong; find the originating single `fm/*` branch with `git branch -a --contains <commit>` to pick the correct PR base rather than opening against `main`.
- Cherry-picking a single commit off a `feature/*` branch that has other, superseded commits ahead of it in the same lineage: the target commit's diff can still reference state (a JSX identifier, a style key) introduced by one of those earlier, unwanted commits, because that state is unchanged context between the cherry-picked commit and its parent and so is never part of the applied patch. `git cherry-pick` resolves the surrounding hunks fine but silently omits the declaration, leaving a dangling reference — `npm run typecheck` catches it (`Cannot find name`), but a plain merge-conflict resolution pass will not. Diff the target commit against its own parent (`git show <parent>:<file>` vs `git show <commit>:<file>`) to see exactly what it adds versus what it merely touches as context, and drop the JSX/state that belongs to the unwanted ancestor commit rather than reintroducing it.
- Reconciling two independent corner branches that each add a new trailing optional parameter to the same shared function (e.g. two different `feature/*` branches both extending `activity.ts`'s `buildAgentMessage`/`postAgentMessage` signature) produces a real conflict on the parameter list, not an auto-mergeable one — git cannot infer the combined order. Resolve by grepping every call site of the function on the pre-merge `origin/main` (`git show origin/main:<file> | grep -n '<fn>('`) to see which positional slot each already-auto-merged caller (git 3-way merges call sites cleanly even when the signature itself conflicts) assumes for its own new argument, then place each conflicting branch's parameter to match what call sites already assume rather than inventing an order and having to re-edit every call site afterward.
- Merging `origin/main` into a stale `fm/*` PR branch: the only conflicts are usually the committed generated release-bundle artifacts under `relay-stack/web/dl/` (`beeline-linux-x64.tar.gz`, its `.sha256`, `manifest.json`) — `git merge` reports "Cannot merge binary files" plus a text conflict inside `manifest.json`'s hash/byte-count fields, even when every real source file (`apps/body`, `apps/mobile`, `packages/buzz-client`) auto-merges cleanly with no conflict markers. Don't hand-resolve the binary/hash content — pick either side to unblock the commit (content is stale regardless of pick), then regenerate for real with `npm ci && npm run bundle:beeline` and commit the freshly built artifacts in a follow-up commit; the sha256/bytes will differ from both merge parents since they now reflect the merged source tree.
- Rebasing a `fm/*` branch whose commit adds a new top-level `describe(...)` block to a test file (e.g. `apps/body/src/body.test.ts`) onto a `main` that already merged a sibling branch which appended its own new top-level `describe(...)` block at the same end-of-file location: git's 3-way merge produces a conflict whose two hunks interleave rather than cleanly concatenate (each side's block shares a boilerplate helper/fixture — e.g. a `stubGlobal('fetch', ...)` snippet — that appears identical on both sides and so lands _outside_ the conflict markers, splitting each side's actual block across two separate `<<<<<<</=======/>>>>>>>` regions). Naively picking "ours then theirs" per hunk nests one new `describe` inside the other's braces instead of placing them as siblings, and the file still passes an `Edit` tool's diff review but fails a proper syntax check (esbuild "Unexpected end of file" / mismatched depth) — a plain brace-counting sanity check on the merged region can also false-positive on unrelated file-wide ambiguity, so verify with `npx esbuild <file> --outfile=/dev/null` or run the actual test file rather than trusting a hand count. Fetch each commit's own full, uncut version of its new block with `git show <sha>:<path> | sed -n '<range>'` and reconstruct the two blocks as clean siblings (old block, unchanged; new block, inserted whole) rather than trying to resolve the conflict markers in place.

## Push credential boundary (ref-policy broker + sandbox masks)

- **The invariant — an agent can NEVER land on main without an owner-signed protected-ref authorization — is structural, not a branch-protection setting, and holds on ANY GitHub plan.** Three layers: (1) **no handed credentials** — `buildAgentEnv`'s `REPO_PUSH_CREDENTIAL_ENV_DENYLIST` (`apps/body/src/config.ts`) strips `GH_TOKEN`/`GH_ENTERPRISE_TOKEN`/`GITHUB_TOKEN`/`SSH_AUTH_SOCK` from every ACP child's env LAST, after prefixes (`GH_`, `GITHUB_`) and even an explicit `BUZZY_BODY_AGENT_ENV_PASSTHROUGH` extension, so no configuration can hand a session a push-capable token; (2) **sandbox credential masks** — `bwrap-sandbox.ts` replaces the known stores (`~/.config/gh`, `~/.config/trusty-squire`, `~/.ssh`, `~/.netrc`, `~/.git-credentials`, `~/.secrets.env`) plus owner-configured extras (runtime record `sandboxMaskPaths` / `BUZZY_BODY_SANDBOX_MASK`) with empty tmpfs (dirs) or `/dev/null` (files) in BOTH modes — the whole-home `--ro-bind / /` makes them read-only, not private, and a readable token can push out-of-band; masks are emitted AFTER the ro-bind they override and BEFORE writable binds; (3) **one ref-policy funnel** — every daemon-performed push goes through `performBrokeredPush` (`apps/body/src/push-broker.ts`): the corner's feature branch → allowed; a protected ref → only with either the ordinary verified owner-signed corner approval (`findHumanMergeApproval`) or the distinct freshly verified `mission-standing-land` authorization bound to the Room, repository key, controller, corner, source SHA, and target ref; anything else → refused before git is invoked. Both push sites in `body.ts` route through it (`publishMergeReady`'s feature publish, `landOnDirectRemote`'s landing), each emitting one greppable `[body] push-broker:` audit line.
- **Residual, stated honestly** (docblock authority: `bwrap-sandbox.ts`): no mask list enumerates every secret on a shared operator machine — ambient env files remain the operator's own exposure on their own account; what Beeline guarantees is that it HANDS nothing, hides what it knows, and audits every credential-carrying push it performs. Sandbox-piercing capabilities (docker.sock, systemd user bus) override all of this by owner choice. Recommended strong posture for exposed hosts: run daemons under a dedicated credential-less user account — documented, deliberately not built here.

- **A release is a conversation, not release machinery — the daemon's whole contribution is three things** (`apps/body/src/release-flow.ts`, wired in `replyInRoom`): (1) ground truth — `summarizeUnreleasedWork` reads commits since the newest tag out of git and the briefing hands that list to the Room turn, so the answer is verifiable rather than recalled; (2) a held offer — `releaseRoomIntent` (a release ask, or "what's unreleased") registers a `PendingReleaseProposal` per Room, expiring after `RELEASE_PROPOSAL_TTL_MS` (30min), so a person's plain "yes" (`isReleaseConfirmation`, which must be the WHOLE message — "yes, but bump the minor" is new work, not agreement) later opens a corner briefed with `releaseCornerTaskPrompt`; (3) one affordance at the far end — `--follow-tags` on `landOnDirectRemote`'s existing push. ## Production host deploy on merge

- `.github/workflows/deploy-host.yml` deploys to the live host on every push to `main` via `scripts/deploy-relay-host.sh`, executed by a **self-hosted runner ON the production host** — the host has no inbound ports (Cloudflare tunnel only), so hosted runners cannot reach it and no server credential lives in GitHub. Stated trade: anyone who can merge can execute code on that host; today that is the captain alone.
- Runner: user `beeline-runner`, install `/home/beeline-runner/actions-runner`, systemd unit `actions.runner.lunchboxfortwo-beeline.beeline-production-squire.service`, label `beeline-prod-host` (workflow also pins `self-hosted` so a hosted runner can never pick the job up). It is in the `docker` group and the `relay-web` group; the web tree at `/home/lunchbox/buzz-router-relay-prod/relay-front/web` is setgid `relay-web`. Privileged steps go through fixed-argument sudoers rules in `/etc/sudoers.d/beeline-deploy-compose` (root reads the lunchbox-owned env files; the runner user never can). The rules are enumerated verbatim in the header of `scripts/deploy-relay-host.sh` — originally just `up -d --no-deps auth`; the stack rollout (below) added two `/usr/bin/install` placement lines and one full-stack `up -d` line, all exact-shape. If an invocation doesn’t match a rule, the deploy fails loudly there — never widen privileges in script to work around it.
- The deploy swaps the WHOLE `relay-stack/web/` tree in place under the nginx bind-mount root (the directory must keep its inode — an atomic rename would orphan the container's mount). rsync must use `-a -O --no-p --no-o --no-g`: the live dirs are owned by `lunchbox`, and preserving group/perms/dir-times across users fails with rsync exit 23. Verification compares the PUBLIC URL against the CHECKOUT (`REPO_WEB`), never against the staged copy — public==stage blesses staging corruption, which is exactly how the stale hand-deployed `install.sh` bug survived. Post-swap failure ⇒ automatic rollback from `web-backups/` + re-verify + red job. Drill: workflow_dispatch input `drill=fail-public`.
- **Two stacks, deliberately**: `relay-stack/{compose.yml,nginx.conf}` is the isolated GATE stack (`name: buzzy-gate`, local/manual only); production is tracked in `relay-stack/prod/` (`name: buzz-router-prod`) and deployed on merge. Coverage: `npm run test:deploy`.
- A merge triggers TWO serialized deploys: the merge itself, then beeline-bundle-bot’s fresh-bundle commit (deploy-host deliberately does NOT skip bot commits — those commits are how new bundles reach main). Both idempotent; concurrency group serializes them.

## GitHub identity and repository authority

- **A repo an admin does not OWN can only be linked via the owner's App install — the typed pending-grant flow, not an error.** Only a personal account's owner can install a GitHub App on it, so an admin binding a foreign repo can never self-serve. Auth answers `owner_grant_needed` (a 403 whose body carries `install_url` — the state-less `publicInstallUrl`, safe to share; distinct from `repository_not_granted`, which now means moved-repo only) and records a durable pending link in `beeline_github_room_link_requests` (PK `(community, room_id)` — one repo per Room; activation never resurrects an active row). Activation is idempotent (`activateGitHubRoomLinks` returns only rows it flipped) and hooked into ALL grant paths — install callback, `installation_repositories` webhook, and reconcile — each announcing exactly once via a deterministic-delivery-id `beeline_room_link` row in the existing repo-event feed the daemon long-polls. The daemon parks the join transiently on that refusal and posts one "access is live" card when the Room finally serves (`isOwnerGrantNeededFailure`/`pendingOwnerGrantNotice`, room-runtime.ts). Mobile renders the typed state as the `OwnerGrantNeededCard` share CTA (probe at bind attempt + paste-flow `owner-grant` plan), never an error wall.

- **GitHub repository identity is the immutable id; owner/name is only its current address, and the auth service heals transfers — never callers.** The live proof: moving `lunchboxfortwo/beeline` to the `Beeline-Work` org made every Room-token request fail with `repository_not_granted` because Room bindings keep the pre-transfer name while installation snapshots carry the new one. Resolution order lives in `resolveGitHubRepositoryAccess` (`apps/auth/src/github-repository-access.ts`, consumed by `/auth/github/room-token` and `/auth/github/room-events`): exact stored grant → id-heal in `AuthStore.githubRepositoryAccess` (a deactivated row still carries the old name's immutable repository id, so the active row with that same id under an active installation wins and returns `resolvedFullName`) → persisted alias (`beeline_github_repository_aliases`) → GitHub's own rename redirect via `GitHubAppClient.repositoryByFullName` (`GET /repos/{old}` 301s; body describes the new location), persisted as an alias on first success. A probe-found destination that is NOT granted produces `{movedTo}`, which room-token surfaces as `repository moved to <owner/name>; grant the App access there` instead of a generic not_granted. Do NOT re-derive this per caller or "fix" it by rewriting relay bindings — auth has no relay write authority by design. **The Room binding's `githubInstallationId` pin is a bind-time hint, never a veto**: the final production layer of that incident was `usable()` in `/auth/github/room-token` demanding `authority.githubInstallationId === candidate.installationId`, which permanently refused every token after a transfer moved the repo to an org installation reconcile had just claimed (the relay binding still pinned the old personal install id, and pino dropped the undefined `repositoryAccessReason`/`movedTo` from the refusal log — an authority-shaped log line with no repositoryAccessReason means the pin veto, not resolution, refused). The store only ever resolves installations recorded for the authorizing pubkey (`i.pubkey = authorizedBy`), so dropping the equality check does not widen authority; row ties break on fresher `updated_at`. Related: when the STORED user OAuth token 401/403s during reconcile's ownership listing, the token row is marked stale (`beeline_github_user_tokens.stale_at`, cleared on re-bind or a successful listing) and `/auth/github/repos/:pubkey` exposes `user_token_stale: true` so the app can silently re-auth. Related sharp edge: PostgreSQL rejects a bind with an unused intermediate parameter (42P18, "could not determine data type of parameter $3") — parameter numbers must be contiguous in every store query.
- **Org GitHub App installations cannot be verified through `GET /user/installations`.** That endpoint is keyed to the OAuth lookup token's visibility: user-owned installations always appear but organization installations generally do not (and can fail outright), which 500'd the real org install callback at `completeGitHubInstallation`. The check is therefore account-type-aware in `apps/auth/src/server.ts`: a User installation requires positive confirmation (unchanged posture); an Organization installation treats GitHub's state-bound redirect (only the installing admin's browser receives the one-time state) as authority, refuses on a definitive listing denial, and logs-and-proceeds when the listing is unavailable. Never make the user-token listing a hard gate for Organization installs again.
- **Install-callback persistence is NOT the only ingestion door — `reconcileGitHubInstallations` enumerates with the App JWT.** The production incident behind this: an org install whose callback 500'd pre-#355 was never recorded, and nothing re-discovered it, so room tokens kept refusing (`repository_not_granted`) while GitHub showed the App installed. The reconcile in `apps/auth/src/server.ts` lists ALL installations via `GitHubAppClient.listInstallations()` (App-JWT `GET /app/installations` — the only credential that sees org installs), then per installation: already-recorded rows refresh through the same guarded upsert (subject-match moves the row onto the current pubkey; other accounts' links stay untouched), NEW rows are claimed only after a one-shot user-token listing gate — positive confirmation for User accounts, callback-precedent log-and-proceed on an unavailable listing for Org accounts, definitive denial refuses. Triggered from three places: repos endpoint when the visible set is empty, repos `?refresh=1` UNCONDITIONALLY (refresh used to only re-list repositories of known installs, so a new install was invisible forever), and the room-token refusal path when the repository's owner account has no recorded active installation (`githubActiveInstallationCoversAccount`) — reconcile once, retry resolution, then refuse. Rate-limited per `(community, subject)` via `claimGitHubInstallationReconciliation` (5 min). Suspended installations are skipped so they are never re-recorded as active.
- **The auth error handler must never produce a silent 500**: non-ProtocolError exceptions are logged at error level with the Fastify request id and returned as `{error:'internal_error', message, reqId}` where message embeds the upstream client error text (plain-language, credential-free) plus the reqId for log correlation. This exists because a production org-install callback returned bare `internal_error` with no error-level log line, making diagnosis impossible.

- Authority and deployment shape: `apps/auth/README.md`. `/auth/capabilities` is the launch gate: GitHub OAuth is visible only when all five `BEELINE_GITHUB_*` values are configured; otherwise the existing Google OIDC path remains visible and unchanged.
- `apps/body/src/repository-truth.ts` is the sole Room repository resolver and supersedes older Stage-1 repository-path notes elsewhere in this file. A remote binding is truth and its canonical checkout is a fetched cache; a `localOnly` binding seeds a separate canonical checkout once and that checkout becomes declared truth. Pairing `root` is private history used only by the opt-in, clean fast-forward post-land sync and must never reach an agent-visible surface.
- One GitHub App installation supplies both picker visibility and repository access. Body mints short-lived installation tokens through `apps/body/src/github-app.ts`; GitHub clone/fetch/push/land paths must not consult ambient Git configuration, credential helpers, `gh`, or host tokens.
- The auth service owns Authorization Code + PKCE and a PostgreSQL-backed, hashed, one-use signed binding ceremony. It never accepts a free-standing provider token or grants relay, Room, role, or merge authority.
- Hermetic provider, adversarial protocol, JWKS rotation/stale-cache, and durable restart coverage: `npm test -w @beeline/auth`.
- **GitHub repository event ingestion is a hosted materializer consumer, never an agent-daemon responsibility.** `apps/body/src/events-service.ts` retains discovery, polling, signing, and no-replay behavior, while `apps/push-gateway/src/hosted-events.ts` supplies its lifecycle and the shared Postgres reservation persistence. `events-state.ts` reserves each signed typed card before relay publication, so an ambiguous retry has the same Nostr id across restart. `github-events.ts` admits only PR opened/closed/merged and issue opened/closed events (never pushes); `room-indexer.ts` accepts their complete typed tag envelope and hides legacy generic rows, and mobile renders that DTO without a service-key byline. Cards retain `#t=github-event` and are explicitly suppressed by `apps/push-gateway/src/mapping.ts`. The retired `beeline-events.service` and `beeline events daemon` entrypoint must not return.
- Merge review custody is explicit in `apps/gate/src/worker.ts`: agent identity remains the first fail-closed check, and managed/remote reviewer keys are refused before role lookup.
- Native onboarding uses the strict bind client in `packages/buzz-client/src/oidc-bind.ts` and `apps/mobile/sources/app/(app)/buzz/onboarding.tsx`; reproduce the auth service locally with `npm run dev:emulator -w @beeline/auth` (see `apps/auth/README.md`). Web remains on the legacy advanced-key path until browser key storage is hardened.
- Native GitHub returns have three delivery shapes (browser result, warm `Linking` event, cold `Linking.getInitialURL`) and one authority: `apps/mobile/sources/auth/github-auth-session.ts` durably correlates the strict bind state and GitHub App installation return path; the Expo Router fallbacks are `buzz/github-callback.tsx` and `buzz/github-installation.tsx`. Every new GitHub browser entry point must use that coordinator so a real-device Intent cannot bypass state validation, lose its originating repo picker, or hit an unmatched route. A warm Intent can replace the onboarding component while its original `Linking` listener is still finishing the bind, so callback failures must also go through `google-onboarding-state.ts`'s replayable notice channel; setting only component-local state loses the alert on the visible route. Coverage: `github-auth-session.test.ts` and `onboarding.github-callback.test.ts`.
- **GitHub App install/update returns share the OAuth callback, not a Setup URL.** The production App has "Request user authorization during installation" enabled, which makes Setup URL unavailable; "Redirect on update" sends `installation_id`/`setup_action` back to `/auth/github/callback`, whose first branch must remain the installation-completion dispatcher before ordinary sign-in code exchange. A return with NO `state` at all is a foreign install (share link/marketplace): it gets a friendly HTML landing (200, "GitHub connected") with NO session binding or token minting — server-side webhook/reconcile ingestion already covers the grant; a state that is present but wrong gets a readable HTML error page instead of raw JSON (both in `completeGitHubInstallation`). Repository-selection browser sessions also refresh `/auth/github/repos/:pubkey?refresh=1` on foreground return/dismiss, because a deep link and the installation webhook are delivery optimizations, not correctness prerequisites. Authority: `apps/auth/src/server.ts`, `packages/buzz-client/src/oidc-bind.ts`, and `apps/mobile/sources/auth/github-auth-session.ts`.
- **Onboarding has three ways onto a device, and the third one is gated: GitHub bind, import an existing `nsec1…`, and create a new key.** `apps/mobile/sources/auth/new-key-onboarding.ts` owns the create path's pure half; `onboarding.tsx` renders it as a dedicated backup step. The load-bearing rule is that a key created here is **never persisted until the person has actually seen it and said so** — `createNewKeyDraft` generates with `persist: false` (the same deferral the provider-bind path uses for its candidate key), and `canEnterWithNewKey` requires BOTH `seen` (the nsec was revealed or copied at least once — a checkbox over a masked string confirms nothing) and `confirmed` (the explicit "I saved my key" tap). A device-held Nostr key has no server-side recovery, so an unbacked key silently written to SecureStore is an identity the person loses with the phone. The gate is re-checked inside `handleEnterWithNewKey` and inside the checkbox's own `onPress`, not only via `disabled`, so it never depends on a touchable honouring a prop. Coverage: `sources/auth/new-key-onboarding.test.ts` (key validity, no-persist, gate truth table) and `sources/app/(app)/buzz/onboarding.newkey.test.ts` (the real screen, rendered).

## Daemon self-update

- **Authority**: `apps/body/src/self-update.ts` (download/verify/atomic-swap/rollback/busy-gate/restart) and `apps/body/src/self-update-manifest.ts` — the ONE seam for the published manifest contract (URL resolution + JSON shape mapping). When the `beeline-cli-publish` companion lands its real contract, reconcile by editing ONLY that seam file. On-demand path: `apps/body/src/self-update-cli.ts` (`beeline update [--check|--status|--rollback|--force]`). End-to-end proof: `apps/body/scripts/self-update-demo.ts`; coverage: `self-update.test.ts`, plus `self-update-layout.test.ts` (the layout contract, incl. a real-shell install→update→fresh-shell e2e).
- **Supervised update convergence is a 10-minute end-to-end contract, not merely a drain timeout.** `ManagedUpdateHandoff` (`apps/body/src/managed-update.ts`) checks the published channel every 30s by default while the install-scoped `update-state.json` and install lock collapse same-host daemon checks; once the active anchor moves it journals the exact desired release and an absolute wall-clock drain deadline. `cli.ts` passes that persisted deadline into `RoomRuntimeCoordinator`, publishes `update pending, converging` through systemd STATUS, quiesces, and exits so `Restart=always` owns resurrection. The drain deadline timers in `room-runtime.ts` must stay referenced: an unresolved Promise does not keep Node alive, so `unref()` lets a quiesced daemon exit before forced recovery runs. Coverage: `managed-update.test.ts`, including the opt-in transient-user-systemd continuous-work acceptance (`BEELINE_SYSTEMD_ACCEPTANCE=1`).
- **THE `<prefix>/lib/beeline` CONTRACT (one meaning, five consumers — see "THE CONTRACT" in self-update.ts): it is the ACTIVE BUNDLE ANCHOR** (symlink into `lib/beeline-releases/<id>`, or a legacy real dir pre-migration), never "the lib directory itself". The 1.x regression: wrappers resolved the anchor with `pwd -P`, node mis-resolves any `..` that follows a symlinked dir, AND `beelineInstallLayout` derived `binDir` one level off (`<prefix>/lib/bin`) so activation rewrote its stable forwarders where nothing executed them — net effect: after the first update executed from a post-swap shell, every fresh-shell `beeline` died MODULE_NOT_FOUND on `<release-root>/beeline-cli.mjs`. The fix: forwarders + bundle wrappers export/derive BEELINE_LIB_DIR as the clean anchor path (never handing node a `..`; forwarderScript() must stay textually identical to install.sh's heredocs — repairInstallForwarders content-matches against it), beelineInstallLayout normalizes symlink-resolved values back to the prefix anchor, entrypoint/identity reads tolerate both bundle shapes (release-shaped and legacy-flat; activateRelease normalizes flat migrations via normalizeLegacyBundleShape), cli.ts repairs stale forwarders at startup, and install.sh lays out release-shaped installs and converges legacy/mid-migration hosts. Do not reintroduce pwd -P resolution of $0 or a second writer of `<prefix>/bin/*`.
- **The `curl | sh` installer must swing the anchor with rename(2), never `mv`.** GNU/BSD `mv` follows a destination symlink that points at a directory — exactly the anchor's contract shape — so the pre-#333 install.sh moved each new anchor link INSIDE the old release (`beeline-releases/<old>/beeline.new.<pid>`) and left `<prefix>/lib/beeline` on the previous bundle forever: every reinstall kept running the stale release and piled up timestamp-suffixed duplicate dirs. install.sh now stages the download beside the releases root (same-fs), reuses a complete same-id release dir on reinstall (idempotent — no `<id>-<epoch>` duplicates), swaps via `node fs.renameSync` (the same primitive as `activateRelease`), sweeps stray `beeline.new.*` links and release-id-named symlinks under `beeline-releases/`, and prunes only guarded `<base>-<digits>` duplicates whose commit matches an existing `<base>` and that neither the previous nor current anchor referenced. Coverage: `self-update-layout.test.ts`'s over-install suite.
- **Install layout after first update**: bundles live in `<prefix>/lib/beeline-releases/<releaseId>/` and `<prefix>/lib/beeline` becomes a SYMLINK swapped by a single atomic rename; the previous release is kept for rollback, and `<prefix>/bin/*` become stable forwarders into the symlinked bundle. Legacy installs (real dir at `lib/beeline`) migrate on first activation — that one-time migration has a millisecond window between two renames; every later swap is one rename. Layout detection must use `lstat`, never `stat` (stat follows the symlink and misreads the layout as legacy).
- **Identity + state live in the install, not in any daemon**: `bundle.json` (stamped with commit + YYYY.MM.DD version by `scripts/build-beeline-bundle.mjs`, installed by `relay-stack/web/install.sh`) is what the daemon reports as running; `.state/update-state.json` and `.state/pending-update.json` under `beeline-releases/` are shared across daemons. The pending journal means "a daemon restarted onto this and must prove health within DEFAULT_UPDATE_CONFIRM_WINDOW_MS"; stale ⇒ auto-rollback at next start, fatal supervisor error inside the window ⇒ rollback + relaunch of the previous release. The CLI apply path deliberately sets `restartHandover: false` — no restart, no journal.
- **Anchor-drift restart is a systemd handoff, never daemon self-spawn.** `ManagedUpdateHandoff` captures the loaded release, runs manifest/download/verify/extract/smoke work in one locked disposable process group, and notices the atomically changed anchor only after a completed core tick. Drift writes both the global pending journal and a per-runtime exact desired-release handoff, quiesces intake, drains under an absolute nine-minute deadline, and exits. systemd starts the stable anchor; each successor must report the exact `loaded_release` before its handoff clears. A failure before READY rolls back the shared anchor once under the install lock. Coverage: `managed-update.test.ts`, `thin-core.test.ts`, and `systemd-acceptance.test.ts`.
- **Busy/drain state reuses existing turn state**: `Body.isBusy()` remains the local accepted-work signal, while `RoomRuntimeCoordinator.shutdown()` aborts intake, waits for durable turn completion, then `forceRecoverRoom()` group-kills remaining ACP/tool descendants only at the absolute deadline. The daemon never launches its own replacement; the supervision contract owns resurrection.
- Automatic updates are default-on (6h cadence, 2min startup grace); `BEELINE_UPDATE_DISABLE=1` turns off only the automatic path — an explicit `beeline update` request always wins. Manifest URL: `BEELINE_UPDATE_MANIFEST_URL` (default currently points at the not-yet-published `usebeeline.app/dl/manifest.json`).

## GitHub key succession (device-key replacement)

- **Role resolution is succession-aware at the roster funnel, not per-screen.** `communityMembers(ctx, id, {predecessors})` (`packages/buzz-client/src/community.ts`) runs every assembled role through `inheritRolesThroughSuccession`: a predecessor of the caller that still holds a role — or authored the Workspace create event (crowned owner last, unchanged) — transfers its role to the CURRENT key and is deleted from the roster, so both keys never render. Source precedence: kind:39002 p[2] role tags are the base (honored now; previously everyone flattened to member), kind:39001 admins override them, create-author crowning stays last. `listCommunities`' viewerRole uses the same chain via `projectedCommunityRoleForChain`. The mobile app wires nothing per-screen: `BuzzClient.communityMembers` lazily fetches the chain once per client from `/auth/oidc/predecessors` (best-effort, 5s bound, cached even when empty; unreachable auth degrades to published roles) and `setSuccessionPredecessors` seeds it explicitly to skip the probe. That lazy probe costs exactly one request on first roster read — pinned in the request-budget assertions of `relay-interaction-performance.test.ts`. Coverage: community.test.ts' `succession-aware Workspace role resolution`, client.test.ts' `succession-aware communityMembers`, agents.test.ts' `viewer with key succession`.

- **The ledger is `beeline_key_successions` (`apps/auth/src/store.ts`)**: one row per `(community, issuer, audience, subject, old_pubkey)` upserted inside the SAME transaction as the identity-link update in `recoverConsumedTicketLink`, so the ledger can never disagree with the link. Chains walk forward via `store.resolveCurrentPubkey(community, pubkey)` and compare via `store.sameIdentity(a, b)` — those two are THE helpers; never scatter succession logic. `successionPredecessors` walks backwards for the `/auth/oidc/predecessors/:pubkey` endpoint (NIP-98, signer must equal the requested key).
- **Room-token authority resolves the binding author to its CURRENT key** (`github-room-authority.ts` returns `currentAuthorizedBy`; server uses it for installation lookup/reconcile/link-request recording) and echoes it in the room-token response as `authorized_by`. The gate worker's pinned `trustedReviewer` authors-filter does NOT follow succession yet — known limitation.
- **Binding RESOLUTION follows the chain too, via one injected resolver** (production 2026-08-23: a restored Room's kind:30078 repo binding was authored by the owner's PREDECESSOR key, which no longer reads back as a Room admin, so `readRoomRepositoryConfig` reported `unverified`, the room-token request died with `room_repository_missing` before #391's authority check ever ran, and every daemon clone/land in that Room failed with "could not access this Room's repository"). `resolveRoomRepository*` / `getRoomRepository` / `readRoomRepositoryConfig` take an optional `RoomRepositoryAuthorResolution` (`packages/buzz-client/src/room-repository.ts`): `{ resolveCurrentPubkey }` makes the author-role check also accept the author's CURRENT successor key. - **Zero re-invite migration is CLIENT-side because the relay accepts kind:9000 membership writes from any authenticated key** (measured on the local stack 2026-08-23: outsider self-join and member-adds-both succeed; projections are replaceable). `migrateSuccessorMemberships` (`packages/buzz-client/src/community.ts`) self-joins the successor into every Workspace/top-level Room a predecessor held, at the HIGHEST role any predecessor held there; DMs and corners are skipped (immutable two-person / inherited membership), agents' memberships never written. `BuzzClient.listCommunities(pubkey, predecessors)` runs it before discovery; mobile loads the chain via `buzz/succession-chain.ts` (session-cached, best-effort → []) passed through `prepareWorkspaceContext`'s `options.loadPredecessors`. A fake-relay test MUST scope projection reads by `#d`/`#h` or scoped reads leak across channels. **Production relay reality (2026-08-23, DB-inspected): upstream block/buzz honors kind:9000 member-adds only when authored by a room ADMIN — a successor's self-join into a room whose only admin was the predecessor is stored but its 39002 projection never updates; the room is permanently orphaned.** The migration therefore degrades gracefully: `waitUntilMember` throws the typed `MembershipProjectionTimeoutError` (`channel.ts`), and both `migrateSuccessorMemberships` and `assertCommunityMemberInChannels` (the repair path runs right after in the same `listCommunities` call) classify that post-publish assert timeout as NOT MIGRATABLE — one console line naming the room id, verdict recorded in `packages/buzz-client/src/unmigratable-rooms.ts` (session cache keyed `(channelId, pubkey)`, seedable/persistable via `seedUnmigratableRooms`/`unmigratableRooms`), room skipped, remaining rooms still migrate. Genuine publish failures (relay reject/network) keep throwing. Mobile persists verdicts across launches in `buzz/unmigratable-rooms-cache.ts` (own tiny MMKV store, same discipline as room-read-state), seeded before and persisted after discovery by `prepareWorkspaceContext`'s `options.unmigratableVerdicts` seam — so app start never re-pays the 15s projection wait for a known-orphaned room.

Fix: put the marker and body inline segments as children of the _same_ `<Text>` (nested Text-in-Text lays out fine; Text-flex1-in-row-View does not) instead of splitting them across sibling Text nodes in a row View.
- **Ledger row components (`MonoMarkdown`, `IdentityMark`, `ActivityTimeline`, and `chat/[channelId].tsx`'s own `AgentPresenceLight`) must stay `React.memo`'d.** `[channelId].tsx`'s FlatList `renderItem` is a `useCallback` that depends on `agentPresences`/`presenceNow`/`presenceReconnectGrace`, which change at least twice during every room-load sequence (once right when a room's data finishes loading — i.e. at "enter room" — via `setAgentPresences`/`setPresenceNow` in the mount effect) and again on every live presence event afterward (`applyAgentPresence`). Each change forces FlatList to re-invoke `renderItem` for every visible row; without memoization on these leaf components, React fully re-executes markdown-to-JSX construction and SVG avatar/polygon-mark element trees for every row on every such update, even though that row's own content never changed — this was the confirmed root cause of an enter-room freeze plus a "smattering of freezes" during active corner sessions. All of these components take primitive/stable-reference props (strings, numbers, `StyleSheet.create` results), so a shallow `React.memo` compare is sufficient — no custom comparator needed. `LedgerActivity` (unexported, same file) additionally must keep its activity-array fallback (`message.activity?.length ? message.activity : [...]`) wrapped in `useMemo` keyed on `message.activity`/`message.text`, or a fresh array literal on every render defeats `ActivityTimeline`'s memoization regardless. **Testing this class of regression**: `React.Profiler`'s `onRender` fires on every commit that reaches that tree position _regardless of a memo bailout_ — it is not a valid way to detect whether a memoized child actually skipped re-rendering. Instead, spy on the memoized component's `.type` property directly (`React.memo(Component)` exposes the wrapped function there) — see the `does not re-render when its own props are unchanged` tests in `IdentityMark.test.ts`/`MonoMarkdown.test.ts`.
- **An agent's name is only as good as the roster the resolver is handed, and BOTH halves of an agent's registration are community-scoped.** `resolveAgentDisplayIdentity` (`buzz/agent-display.ts`) is correct — soul overlay, then registered `displayName`, then the seed placeholder — but it falls back for any pubkey the roster lacks, so an empty or wrong-Workspace roster does not degrade the name, it replaces it with a confident fake. `listAgentIdentities` queries the agent record by `#h = communityId` and the soul overlay is keyed `soulKey(communityId, agentPubkey)`, so reading one wrong community yields _zero_ agents. Reading strictly `channelCommunityId` is what made the transcript show a placeholder ("Alden") or a bare npub while the Members screen, scoped to the viewer's selected Workspace, showed the real soul name ("Beebee") for the identical key. The chat screen now reads **every** Workspace the viewer belongs to, channel's own first, then the viewer's selection, then the rest (`agentRosterCommunityIds` + `mergeAgentRosters`, precedence positional except that an entry which cannot name its agent never blocks a later one that can). Each `listAgents` is individually `.catch`ed so one unreachable Workspace does not cost the others, and the merged roster is committed to the channel cache _immediately_ through `hydrateRoomEntry`'s own `onAgents` handler (`sources/buzz/room-entry.ts`) — it used to land only after the person-profile read, so one failure there left the transcript with no names at all. **The union is a second pass that can never block the first**: the channel's own Workspace roster commits as soon as it resolves, and only then are the gap-filling Workspaces read, because those need `listCommunities` and a hanging Workspace listing must not cost the channel the names it already knows. Neither pass commits an _empty_ roster — an empty read must never wipe cached names, which is the same seed-placeholder flash this whole mechanism exists to remove. **Only the roster widens**: `communityMembers`, `listPersonProfiles`, `replaceProfiles`, and `saveActiveCommunityId` are authority-adjacent and stay on `channelCommunityId` (`transcriptSurfaces.test.ts` asserts both halves). A roster from another Workspace can only ever _add_ a match, since an entry is used only when its pubkey equals the message signer's. **The merge itself had a deeper bug than the "cannot name its agent" override alone could fix, twice**: `mergeAgentRosters` originally kept one WHOLE incoming `Agent` object per pubkey and discarded the other roster's object entirely — so whichever Workspace's roster was consulted first for a pubkey won outright, _including its absence of a soulProfile_, silently dropping a later Workspace's real `soulProfile` even when nothing else about the earlier roster's object was better. A first attempted fix only widened _which_ entries counted as "cannot name its agent" (`redeemAgentPairingCode`, `packages/buzz-client/src/agent.ts`, registers every freshly paired agent with `displayName: fallbackAgentName(pubkey)` — never empty — so a Workspace where the agent is registered-but-unsouled looked "already named" and still won outright) — that widened which cases got picked correctly, but the merge still swapped one whole object for another rather than combining fields, so it remained possible for an earlier roster's real (non-fallback) `displayName` with no soul to still block a later roster's soulProfile from ever being merged in. The fix has to be structural: `mergeAgentRosters` (`buzz/agent-display.ts`) now unions FIELDS across entries for the same pubkey rather than swapping whole objects — once any roster supplies a `soulProfile` for a pubkey, it is carried onto the merged entry and never dropped, regardless of which roster's other fields (like `displayName`) are kept; a later roster cannot _displace_ an already-found soul (positional precedence, `agentRosterCommunityIds`' own Workspace first), but it can always _fill in_ one the earlier entry lacked. Regression: `agent-display.test.ts`'s "never drops a soulProfile the merge finds just because an earlier entry already won the pubkey" (confirmed to fail against the whole-object-swap merge before this fix, with the earlier entry's real non-fallback `displayName` masking the gap).
- **A second, distinct cause of the same "Alden" flash: calling the resolver before the roster read has even finished, not just scoping it to the wrong community.** Even with the correct-community roster above, `[channelId].tsx`'s transcript/corner-header calls `resolveAgentDisplayIdentity(pubkey, knownAgent)` on every render, including the renders that happen _while_ `listAgents` is still in flight (`participantsHydrated` false, "LOADING MEMBERS") — `knownAgent` is `undefined` then, so the resolver correctly-but-unhelpfully returns its own seed placeholder, which then visibly snaps to the real name a beat later. `resolvePendingAgentDisplay` (`buzz/agent-display.ts`) closes this: it returns `null` until a `hydrated` flag is true, so callers fall back to a neutral placeholder (`shortMemberNpub`, or `'AGENT'` in the corner header) instead of a specific-but-wrong name. Both call sites in `[channelId].tsx` (the transcript row's `display` and the corner header's `cornerAgentDisplay`) are gated on `participantsHydrated`; the transcript row's is inside `renderItem`'s `useCallback`, so `participantsHydrated` must stay in that callback's dependency array or the gate freezes at whatever it was when the callback was last created.
- **Attribution is per run, not per entry** (`apps/mobile/sources/buzz/ledger-attribution.ts` + `ledgerSpeakerKey` in `chat/[channelId].tsx`): only the first entry of a voice's run carries its inline handle, so a Room's final response and its trailing tool line read as one continuous voice instead of a chat feed. Anything that is not that voice — a person's steer, a merge summary, a permission card — returns `null` from `ledgerSpeakerKey` and ends the run, so the next agent entry re-announces itself. The set is derived once per transcript change over the chronological `visibleMessages`, never inside `renderItem`. **A collapsed tool/thought row never confers continuation onto the prose below it** (`isMachine` on `LedgerSpeakerEntry`, 2026-08-23 owner report): a run ordered [tool-summary, prose] used to spend the byline on the tool block (which carries only a compact handle) and leave the agent's actual text turn bare — machine rows still fold after their own prose, but prose always re-announces across one.
- **Persistent chrome carries no `HullSurface`**: the Room-list header, the chat header, the Members header, and the Workspace rail are the same obsidian as their content, parted by a hairline only — a textured `HullSurface` there read as a plate laid on the slab. `HullSurface` is now reserved for regions that genuinely float over it and do not repeat (modal sheets, the merge-approval panel, the write-permission card). `channels.design.test.ts` and `transcriptSurfaces.test.ts` both assert this, so re-wrapping a header in `HullSurface` fails the suite.
- **One glyph per concept**: `MEMBERS_GLYPH`/`MEMBERS_LABEL` (`apps/mobile/sources/buzz/vocabulary.ts`) is the single members mark (`⌬`) and word used by every route into the members screen — the Room-list header, `CommunityInviteEntry`, `settings/workspace.tsx`, and `MembersScreen`'s own title and empty state. `buzz/members-glyph.test.ts` asserts both halves of the rule: every entry point imports the token (no hardcoded glyph, no surviving "PEOPLE" wording), and the glyph is never one of `cornerStatusPresentation`'s lifecycle glyphs, because a diamond on any Buzz surface means live corner work.
- **A durable failure fact carries one plain-language reason, never a generic status.** `failureReason` (`apps/mobile/sources/buzz/activity-timeline.ts`) folds the tool result envelope into one clamped clause such as `command not found: pnpm`; the settled transcript renders that clause inline on its single brass room-update line. Live tool rows remain one non-interactive mono line per call with a verdict. There is no group row, disclosure, raw-output sheet, historical tool receipt, or tap-to-replay affordance.
- **The pinned corner line and the per-turn "thinking" indicator are two independent facts, and the daemon has always published them as two unrelated streams.** `#t=agent-turn` (`postAgentTurnStatus`, `apps/body/src/body.ts`) is published on _the channel the turn runs in_ — a Room turn's `working` event lands in the Room, a corner turn's lands in the corner — and means only "this agent is composing a reply here". A corner's existence and lifecycle reach the parent Room through a completely different event: `postParentCornerStatus`'s `subchannel`+`display-status` card, plus the `status=archived` close notice. Nothing on the wire is ambiguous; the client conflated them. `[channelId].tsx`'s pinned-line derivation used to set its gold `live` flag from the Room's agent-turn signal and take its destination from `tappableCornerId ?? permittedCornerId` — and `permittedCornerId` (the last write-permission ALLOW's `subchannelId`) is a durable transcript event with **no lifecycle filter at all**, so a plain question in a Room lit the gold `beebee active: <corner> · view →` line pointing at a long-archived corner and let the reader tap into a read-only channel. `selectPinnedCorner` (`apps/mobile/sources/buzz/room-indicators.ts`) now owns that choice from corner state alone: it merges the transcript's live status cards with the relay-read `cornerLifecycle` snapshot taking the **most terminal** status either source reports (a snapshot fetched before a corner closed must never re-open it), and honours `permittedCornerId` only when _neither_ source knows the corner yet _and_ the lifecycle read has actually answered (`cornerLifecycleLoaded` — "unknown" and "not loaded yet" are different answers). **The line's presence means "this corner is open and worth returning to," not "actively working"**: any non-terminal status (`live`/`needs-attention`/`open`) is a candidate — only `isCornerTerminal` (`merged`/`failed`/`archived`) excludes one, so a corner that finishes its work and goes quiet keeps its pinned line instead of vanishing back to the corners-list expander. An earlier cut of this line restricted candidates to `live` alone, which over-corrected: a finished, review-ready corner had no entry point back except the expander. Gold and the breathing pulse (`isPinnedCornerLive`) are reserved for `live` only, so an idle/waiting corner still reads as calmer than a working one even though both are pinned. When several corners qualify, `PIN_RELEVANCE` (`room-indicators.ts`) — deliberately distinct from `cornerStatusPrecedence`, which resolves conflicting reports of _one_ corner's status and must stay terminal-highest — picks a review-ready one (`open`, `isPinnedCornerReadyForReview`) first, then a working one (`live`), then the most recently active, because review-ready is the most actionable thing a captain can do. `open`'s ONLY path onto the wire (`cornerSummaryFromEvents` in `buzz-rig-transport.ts`) is a `ready` display-status or a `merge-ready` tagged event — it never means a plain idle-but-open corner, which is why `cornerStatusPresentation`'s label for it is `READY`, not `OPEN` (`[channelId].tsx`'s `!isCorner` branch of `cornerLiveBar` also hides the line outright when `agentsOffline`, for the same reason — an offline daemon cannot be doing that work). The turn indicator is its own `TurnProgressLine` (`apps/mobile/sources/components/buzz/TurnProgressLine.tsx`), unpressable, driven by `activeAgentTurn` alone. Independence is enforced as source assertions over the two `useMemo` dependency lists in `roomIndicators.test.ts`, not by care. **Known gap, deliberately not closed here**: the daemon posts no parent corner status for a corner _follow-up_ turn (`pollMembers`' `promptNewTurn`), so a corner running a follow-up shows no pinned line at all until its next `working`/`ready` card — honest-but-conservative, and preferable to the false gold that shipped. (A corner's _own_ self-referential line, rendered when `isCorner` — "is this session I'm in still moving" — is a separate code path keyed on `sessionState`/`displayedCornerStatus` and still uses the quiet `idle` tier; only the Room-level pick-among-corners line above the composer is active-only.) **The Room indicator's lifecycle input is `latestAgentTurns` (`buzz-event-projection.ts`), derived per agent from the normalized journal — one marker each, latest by createdAt then eventId.** The typed-snapshot rewrite (#460) dropped the raw-event producer that stamped `ChatDisplayMessage.agentTurn`, leaving the field and the screen's consumer as dead code, and `selectTranscript` synthesizes its live activity lane only once streamed content exists — so between the daemon's WORKING receipt (published before harness activation) and the first draft/thought/tool fact the Room showed no thinking indicator at all. Turn markers are presentation state: they must never become conversational transcript rows. Coverage: `chat-event-projection.test.ts`'s bare-working-receipt regression.
- **A corner's status is NEVER in the transcript — active or terminal.** `CornerLiveBar.tsx` is one line directly above the composer on both surfaces, naming who is working and what on (`beebee active: feat/ux-fix-now`) with `view →` in the right gutter; it is the Room's _only_ active-corner affordance. `renderItem` returns `null` for **every** `item.corner` message (not just active ones) and for an `allowed` write-permission with a subchannel, and `WritePermissionOutcome` does not navigate at all. Rationale: a note inscribed when a corner opened scrolls away and then lies ("open" long after it merged), and a terminal stamp (`Alden ✕ FAILED`, `◇ OPEN`) interrupts a live conversation with a dead record while duplicating the pinned line. Finished corners are recorded in `buzz/corners/[roomId]` instead. **Motion**: the live line breathes via `HullLivePulse` — a calm heartbeat on the shared `motionTokens.liveCycle`, mounted only when live. It is deliberately NOT a travelling sweep, progress bar, or row of dashes (a 28-segment gold flow band shipped once and read as broken chrome at rest); a moving indicator also implies "filling toward a finish", which is a claim the product cannot make about an agent's turn. An open-but-idle corner keeps the same line on `ledgerQuiet` with no motion, so gold stays the live/online meaning only, redundant with the copy (`active` vs `idle`) and never lit for an offline agent (that fact belongs to the separate offline hint).
- **Diff added/removed coloring is a deliberate, in-code-documented exception to Grok Mono Hull's zero-chroma rule ("captain override"), not a violation to grayscale-ify.** `ChangeReviewPanel.tsx`'s `diffAddedLine`/`diffRemovedLine` and `ActivityTimeline.tsx`'s `diffAdded`/`diffRemoved` (its own inline per-file diff drill-down) both source the same conventional green/red from `darkTheme.colors.diff` (`theme.ts`, Happy's legacy palette) — one shared source, not two independently hand-picked palettes, after a fix that found `ActivityTimeline.tsx` had drifted onto a second, slightly different pair of hex values. Hunk headers and context lines stay on the neutral grayscale palette in both (`groknight.bgHover`/`bgTerminal`, `groknight.textMuted`/`textSecondary`) — only added/removed lines get color; `groknight.ts`'s `danger`/`success` tokens still deliberately share one gray, since that rule has no carve-out for chrome/state elsewhere in the app. **Corner change-review diff (`ChangeReviewPanel.tsx`) does not use the legacy Happy diff renderers** (`components/diff/PierreDiffView.tsx`, `DiffView.tsx`) despite sourcing the same color values — those components render a different diff UI shape entirely, not because of the color exception. The per-file diff sits inside the parent Room's _inverted_ transcript `FlatList` (as `ListHeaderComponent`). **Android nested-scroll direction matters**: a vertical `FlatList` nested inside a horizontal `ScrollView` never receives vertical drags on Android regardless of `nestedScrollEnabled` — that shape (shipped in #173) left the diff unscrollable vertically. The working shape is vertical-outer, horizontal-inner: a bounded (~300px) vertical `ScrollView` (`testID="change-review-diff-scroll"`, `nestedScrollEnabled`) wrapping a horizontal `ScrollView` (`nestedScrollEnabled`) wrapping a plain column of `Text` rows — same-axis nesting (vertical diff inside the vertical transcript) hands the gesture off correctly via `nestedScrollEnabled`, cross-axis does not. Rows are plain `Text`, not a virtualized `FlatList` (the previous vertical `FlatList` is exactly the piece that broke), capped at `DIFF_MAX_RENDERED_LINES` (1500) with a truncation footer to bound memory; long lines use `numberOfLines={1}` plus an explicit width estimated from the longest line (`DIFF_CHAR_WIDTH_PX`) rather than wrapping, so the horizontal `ScrollView` has real content to scroll.

## NIP-05 handles (display + verify + Buzz-issued `name@usebeeline.app`)

- `packages/buzz-client/src/nip05.ts` owns parsing (`parseNip05Identifier`/`normalizeNip05Identifier`) and client-side verification (`verifyNip05`, fetches `https://<domain>/.well-known/nostr.json?name=<local>` and checks it maps back to the expected pubkey) of a `name@domain` identifier. It never throws — every failure mode (bad format, unreachable domain, malformed response, name/pubkey mismatch) resolves to a distinct honest status (`verified`/`mismatch`/`unreachable`/`invalid`), consumed by `apps/mobile/sources/buzz/nip05-verification.ts`'s cache/hook so a label only ever renders the nip05 string once _that viewer's own client_ has independently confirmed it — the profile's `nip05` field itself is never trusted at face value.
- `PersonProfile.nip05`/`PersonProfileInput.nip05` (`packages/buzz-client/src/types.ts`, wired in `person-profile.ts`) round-trips through the standard NIP-01 kind:0 `nip05` content key, same optional-field pattern as `avatar`/`handle`.
- `apps/mobile/sources/buzz/member-display.ts`'s `personIdentityLabel` is the one shared display waterfall (verified nip05 → `@handle` → name → truncated npub); it is wired into `MembersScreen.tsx` (central per-render verification map keyed by pubkey) and `settings/identity.tsx` (own-profile editor + verification badge, `useVerifiedNip05Status`). The chat transcript (`chat/[channelId].tsx`) only got the DM peer room-title spot wired (the one self-contained async call site); its many other `shortMemberNpub` call sites (message author, participant list, mention dropdown) were deliberately left on the pre-nip05 fallback chain — wiring those in means either extracting per-row list components to host `useVerifiedNip05Status` or growing this already 2800+ line file's central `personProfileByPubkey`/effect graph, and was scoped out of the initial landing as a fast-follow rather than risked blind.
- **Managed `@usebeeline.app` identity is owned by `apps/auth`** (`protocol.ts`, `store.ts`, `server.ts`; client contract in `packages/buzz-client/src/nip05.ts` and `oidc-bind.ts`). A verified GitHub bind transactionally reserves/provisions the GitHub login, preferred display name, and NIP-05 for the bound key; GitHub ownership wins over an earlier unlinked key claim so a key-only user cannot squat a linked or subsequently linked GitHub handle. Key-only onboarding claims exactly one canonical lowercase `[a-z0-9-]` handle of 3–30 characters. Linking GitHub later updates the existing key's registry link and history in place, with one optional adoption of the GitHub handle that releases the old NIP-05 mapping. `GET /.well-known/nostr.json`, `POST /nip05/claim`, `GET /auth/identity/:pubkey`, and `POST /auth/identity/:pubkey/github-handle` are the service boundary; both relay-front nginx configs must proxy the top-level NIP-05 routes. Native entry points are `onboarding.tsx` (first-run ceremony and zero-step GitHub landing) and `settings/identity.tsx` (same-key GitHub upgrade).

## Direct messages

- SDK authority: `packages/buzz-client/src/direct-message.ts`. A DM is a deterministic, private NIP-29 Room marked `t=buzz-dm`, bound immutably to one Workspace and two sorted participant pubkeys; SDK discovery requires the current projection to contain exactly those two members.
- Workspace membership propagation and Room/agent invite APIs skip or reject DMs, and mobile hides the Room member picker in DM chat. Agent DMs are discovered by `apps/body/src/thin-core.ts` but remain strictly conversational/read-only: they never borrow another Room's repository, request write permission, or open an edit corner.

## Explicit external MCP capabilities

- `apps/body/src/external-mcp-capabilities.ts` is the authority for account-backed tools deliberately granted to one agent. Runtime records store profile names only (`externalMcpCapabilities`), never copied operator MCP config, commands, environment values, or credentials. Trusty Squire has two disjoint profiles, `squire-credential-use` and `squire-app-access`, selected independently at pairing; there is no umbrella profile that grants both. Account capabilities require `--access creator`, are re-expanded on every Room/corner session and restart, and are omitted again defensively for any non-creator config. Pairing runs the idempotent, human-present `npx @trusty-squire/mcp connect` ceremony through `trusty-squire-onboarding.ts`, then loads the skill into both the shared and harness-native skill roots. Only codex/claude may select Squire: their ACP permission callbacks are measured and interceptable; every other harness fails closed. Daemon mounts use the explicit `server` subcommand and must never trigger browser setup.
- Trusty Squire is the one explicit governed hole in the read-only MCP boundary. Metadata inventory (`list_credentials`, `list_app_access`, `audit_log`) is read-only; the selected profile mounts only its governed verbs. `use_credential`, `grant_app_access`, and `revoke_app_access` each require P1's exact Tier-2 `operation.execute` envelope with an argument digest, secret-free target, current human-owner signature, one use, and durable started/terminal execution receipts. `grant_app_access` additionally requires an explicit hourly cap; its host-scoped grant remains independently revocable in Squire. Both Room and corner handlers route these calls through P1 before any generic allow path, and the host broker reverifies current authority immediately before forwarding. Unknown Squire verbs, shell-title spoofs, missing ACP provenance/session/tool ids, and unsupported harnesses are refused. Pairing and the host broker force Squire onto one stable Body-owned file-only XDG store; the sandbox masks that resolved store and legacy Squire stores while stripping keychain/session-bus IPC access. No Squire bearer, store, or reusable broker credential is mounted into an agent namespace. Coverage: `external-mcp-capabilities.test.ts`, `trusty-squire-onboarding.test.ts`, `squire-host-broker.test.ts`, `permission-runtime.test.ts`, and the Squire cases in `body.test.ts`.
- Mobile draft/final reconciliation happens in `upsertChatMessages` (`apps/mobile/sources/sync/transport/buzz-event-projection.ts`). When a final `agent-message` settles an already-visible `isAgentDraft` bubble, strip `isNew`: otherwise `LedgerEntry`'s typewriter blanks the fully streamed draft and retypes the final text from scratch, which looks like two competing renderers.
- **`isNew` is a transient "arrived this session" signal — never persist it, and the entrance animation is consume-once.** It drove the new-message entrance (`NewMessageMaterialize`, `MonoHull.tsx`) but was written verbatim into the MMKV snapshot by `persisted()` and re-stamped on already-seen messages by warm revalidation's inclusive cursor edge (`local-cache-sync.ts`), so old rows replayed their entrance on every Room re-entry / FlatList remount. Three load-bearing halves: `persisted()` strips it at serialization; `restoreChannels()` strips stale flags caches written by pre-strip builds (same floor as retired-agent notices); and `buzz/message-reveal.ts` holds the module-scoped, never-persisted revealed-id set that makes `NewMessageMaterialize enabled messageId=<id>` animate at most once per id per app session (decision frozen per instance via ref so a mid-animation re-render can't flip the wrapper; marked in an effect, not during render). The typewriter is on the same contract (it was the second half of the same replay bug, fixed separately): `Ledger.tsx`'s `TypewriterMarkdown` gates its one type-out per message id through the SAME `message-reveal.ts` registry (same freeze-per-instance + mark-after-commit care), so warm revalidation / WS replay re-stamping `isNew` cannot re-type already-seen prose either — do not reintroduce a raw `Boolean(item.isNew)` animation gate outside the component. Coverage: `local-cache.test.ts`'s persist/restore isNew tests, `components/buzz/NewMessageMaterialize.test.ts`, `components/buzz/Ledger.test.ts`'s typewriter reveal-lifecycle block.

## Local relay stack vs canonical clones (demo/live-testing sharp edge)

- `repository-truth.ts`'s `cloneUrl` maps the `git://host[:port]/path` origin marker to `https://…` — correct for production but UNUSABLE against the local docker stack (`relay-stack/compose.yml`, plain HTTP on 127.0.0.1:3010): a paired repository Room's daemon cannot materialize its canonical checkout and parks the Room with `could not clone canonical cache … gnutls_handshake failed`. When live-testing daemons against the local stack, pair repo-less (`beeline pair <code>` with no `--repo`) and invite top-level Rooms instead — Room lifecycle, serving, quarantine, presence and restart behaviour are all exercisable without git hosting. Gate helpers (`createCommunity`, `createChannel`, `queryEvents`, …`) resolve their relay from env AT IMPORT TIME: set `BUZZY_RELAY_HOST=127.0.0.1:3010`, `BUZZY_RELAY_SCHEME=http`, `BUZZY_RELAY_URL=http://127.0.0.1:3010`, `BUZZ_RELAY_URL=ws://127.0.0.1:3010` BEFORE importing `@beeline/gate`, or reads/writes silently go to PRODUCTION (usebeeline.app) — this bit once and littered a handful of empty test Workspaces onto the production relay.
