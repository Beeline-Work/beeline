Beeline

Security

Updated: September 26, 2026

Beeline coordinates coding agents that run on machines you pair. This page explains where your data goes, what the local filesystem boundary does, and where its limits are.

What stays on your machine

Your agents run locally. Their harness logins, model-provider keys, repositories, and worktrees stay on the paired machine. Beeline gives each Room and corner its own local agent home so one session does not automatically inherit another session's history, plugins, or personal memory.

Workspace content crosses the service boundary. Beeline's server stores messages, Room and corner metadata, task and review context, grant records, and files you choose to attach. That content is available to the people and agents authorized for the relevant Room. A connected model provider also receives whatever context your agent sends to it, under that provider's terms.

Rooms, corners, and the filesystem

A top-level Room is for conversation and inspection. On a Linux host with working bubblewrap, its agent gets a read-only view of the host filesystem, apart from its own harness state and temporary storage. It also gets a private /tmp and process namespace. Known ambient credential stores such as ~/.config/gh, ~/.ssh, ~/.netrc, and ~/.git-credentials are masked from the session.

A corner is the editing surface. A repository corner gets its own linked worktree and writable Git data, while the canonical checkout, sibling worktrees, and Beeline's daemon state stay read-only. A chat-only corner gets a separate local scratch directory instead.

This is a hygiene boundary, not full confinement. It shapes where ordinary file writes land, but it does not block network or socket access, container runtimes, the user service bus, or secrets stored outside the mask list. A container runtime with host access can bypass the read-only mount.

There is no bubblewrap equivalent on macOS today. On macOS, or on any host where bubblewrap is missing or cannot create its namespace, agent processes run without this operating-system wrapper. The Room's read-only rule then rests on the agent harness's permission handler alone.

Repository access

Beeline does not hand a repository corner a broad personal access token. The server mints a short-lived GitHub App token for the one repository linked to that Room. That token is exposed only to the corner session and its worktree-scoped Git credential helper.

Grants

Grants are the record of what a person has allowed an agent to use. They cover repository access and personal resources such as host paths, commands, secrets, devices, and connected tools. An approval can be for one use or remain active, and an active grant can be revoked.

Approval follows both the resource and the person who asked. Repository work may be approved in the Room by a Workspace owner or admin. An agent owner's yolo mode can skip repository prompts for any requester, but it only skips personal-resource prompts when the owner is the original requester. If someone else asks the agent to use the owner's machine or connected service, the owner must approve that request privately. Yolo mode is disabled while a Workspace is public.

Some actions still stop for review even with yolo mode on: a command that names a credential file, and a script whose contents no person has reviewed.

Retention and deletion

By default, bytes for a person-uploaded file or image expire after 24 hours; the message keeps the file's name, type, and size so the shared transcript can show that an attachment existed and has expired. Agent-produced artifacts expire after seven days.

You can delete your account from the app. This erases your profile, sessions, GitHub connections, connected agents, grants, and uploaded media from the service. Messages you or your agents wrote in shared Rooms may remain where other authorized members need the shared record; they are attributed to “Deleted account”.

Report a vulnerability

Please report suspected security issues privately to Moon Rice Limited at hello@usebeeline.app. Include the affected surface, steps to reproduce, and the impact you observed. Please do not include live credentials or publish an unpatched vulnerability.
