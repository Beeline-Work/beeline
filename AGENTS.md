## Branch conventions

- `fm/*` feature branches often stack on each other (PR base is another `fm/*` branch, not always `main`) — check `gh pr list --json baseRefName,headRefName` before assuming a task's target file exists on `main`.
- The local-only `fm-integration-verify` branch (many `fm/*` branches merged together for cross-branch verification) has a pushed origin counterpart: `fm/buzzy-integrated`. If a task references a file that doesn't exist on `main`, check `fm-integration-verify`/`origin/fm/buzzy-integrated` before concluding the task's premise is wrong; find the originating single `fm/*` branch with `git branch -a --contains <commit>` to pick the correct PR base rather than opening against `main`.
- Cherry-picking a single commit off a `feature/*` branch that has other, superseded commits ahead of it in the same lineage: the target commit's diff can still reference state (a JSX identifier, a style key) introduced by one of those earlier, unwanted commits, because that state is unchanged context between the cherry-picked commit and its parent and so is never part of the applied patch. `git cherry-pick` resolves the surrounding hunks fine but silently omits the declaration, leaving a dangling reference — `npm run typecheck` catches it (`Cannot find name`), but a plain merge-conflict resolution pass will not. Diff the target commit against its own parent (`git show <parent>:<file>` vs `git show <commit>:<file>`) to see exactly what it adds versus what it merely touches as context, and drop the JSX/state that belongs to the unwanted ancestor commit rather than reintroducing it.
- Reconciling two independent corner branches that each add a new trailing optional parameter to the same shared function (e.g. two different `feature/*` branches both extending `activity.ts`'s `buildAgentMessage`/`postAgentMessage` signature) produces a real conflict on the parameter list, not an auto-mergeable one — git cannot infer the combined order. Resolve by grepping every call site of the function on the pre-merge `origin/main` (`git show origin/main:<file> | grep -n '<fn>('`) to see which positional slot each already-auto-merged caller (git 3-way merges call sites cleanly even when the signature itself conflicts) assumes for its own new argument, then place each conflicting branch's parameter to match what call sites already assume rather than inventing an order and having to re-edit every call site afterward.
- Merging `origin/main` into a stale `fm/*` PR branch: the only conflicts are usually the committed generated release-bundle artifacts under `relay-stack/web/dl/` (`beeline-linux-x64.tar.gz`, its `.sha256`, `manifest.json`) — `git merge` reports "Cannot merge binary files" plus a text conflict inside `manifest.json`'s hash/byte-count fields, even when every real source file (`apps/body`, `apps/mobile`, `packages/buzz-client`) auto-merges cleanly with no conflict markers. Don't hand-resolve the binary/hash content — pick either side to unblock the commit (content is stale regardless of pick), then regenerate for real with `npm ci && npm run bundle:beeline` and commit the freshly built artifacts in a follow-up commit; the sha256/bytes will differ from both merge parents since they now reflect the merged source tree.
- Rebasing a `fm/*` branch whose commit adds a new top-level `describe(...)` block to a test file (e.g. `apps/body/src/body.test.ts`) onto a `main` that already merged a sibling branch which appended its own new top-level `describe(...)` block at the same end-of-file location: git's 3-way merge produces a conflict whose two hunks interleave rather than cleanly concatenate (each side's block shares a boilerplate helper/fixture — e.g. a `stubGlobal('fetch', ...)` snippet — that appears identical on both sides and so lands *outside* the conflict markers, splitting each side's actual block across two separate `<<<<<<</=======/>>>>>>>` regions). Naively picking "ours then theirs" per hunk nests one new `describe` inside the other's braces instead of placing them as siblings, and the file still passes an `Edit` tool's diff review but fails a proper syntax check (esbuild "Unexpected end of file" / mismatched depth) — a plain brace-counting sanity check on the merged region can also false-positive on unrelated file-wide ambiguity, so verify with `npx esbuild <file> --outfile=/dev/null` or run the actual test file rather than trusting a hand count. Fetch each commit's own full, uncut version of its new block with `git show <sha>:<path> | sed -n '<range>'` and reconstruct the two blocks as clean siblings (old block, unchanged; new block, inserted whole) rather than trying to resolve the conflict markers in place.

## Body (@beeline/body) — agent session manager

- `apps/body/` — agent body service (see `apps/body/README.md`).
- **An archived Room is terminal, and quarantine must stop the retry.** The relay's `channel is archived` refusal (verbatim: `publishEvent kind=9 failed: HTTP 400 {"error":"invalid: channel is archived"}`) is a fact about the Room, not a transient failure — re-serving can only reproduce it. The captain's daemon once spent 161 serve/quarantine cycles on one archived Room against 2 for its live Room. Two halves in `supervisor.ts`: discovery reads `getChannelMetadata` BEFORE serving any not-yet-running Room and drops archived ones (`archivedRooms` cache means one read, ever, per process), and the quarantine catch classifies via `isArchivedChannelError` — an archived refusal parks the Room for the process lifetime; any other error stays an ordinary retryable quarantine. Rooms are held INERT rather than deleted from `runtime.rooms` deliberately: after a restart the join path re-reads relay truth before serving, so a Room comes back only through a fresh authoritative NOT-archived answer — never by our own retry loop. The drop notice is logged once per process. Coverage: `supervisor.test.ts` → `WorkspaceSupervisor archived Room`; proven against a real daemon + relay stack (pre-fix loop vs post-fix drop).
- **`beeline start` RESTARTS a running daemon — there is no silent "already running" early return left.** The CLI help always claimed "Restart this repo's durable agent" but the code returned `already running (pid N)` and changed nothing, so the documented restart path was a no-op. `startStoredRuntime` (`start-command.ts`, DI-testable) stops the old daemon via `stopRuntimeDaemon` then launches through the SAME `launchRuntimeDaemon` handover self-update uses. A stop waits out the graceful drain (SIGTERM → supervisor stopAll → `Body.dispose` awaits every running turn) for up to 30min — never force-killing mid-turn, mirroring self-update's busy gate — and reports the wait; a failed stop fails loudly WITHOUT launching a second daemon. `stopRuntimeDaemon` verifies process identity via `/proc/<pid>/cmdline`, falling back to `ps -o command=` on non-Linux, and fails closed when it cannot identify the process. Coverage: `start-command.test.ts` (including the stub-daemon graceful-drain test).
- **Corner metadata and its opening plan come from one hidden, tool-free model turn before channel creation.** `Body.modelCornerMetadata` sends the triggering request plus a bounded recent Room transcript through a short-lived ACP session with an empty MCP inventory and a reject-all permission handler. Only strictly parsed, length-capped `{title, objective, items}` JSON survives: the title names the corner and supplies the feature-branch slug, the objective becomes the immutable `task` tag, and concrete task-authored items seed the pinned plan until the working harness publishes its own status updates. The response is never projected into chat, the call is attributed as `corner-metadata` spend, and every spawn/timeout/schema/tool-use failure preserves the deterministic objective path while the panel shows one honest `Working…` state instead of fabricated generic steps. Keep this before `createAgentSubchannel`; coverage is in `corner-metadata.test.ts`, `activity.test.ts`, and `corner-clarity.test.ts`.
- **Room delivery is WS-push, not polling**: `Body.runRoomPushLoop` (`apps/body/src/body.ts`) holds one authenticated WS subscription per Room (`since`-cursor reconnect, HTTP `pollChannelRequests` only as a one-shot backstop after each (re)subscribe, plus a low-rate maintenance timer for child steering/merge closure). `WorkspaceSupervisor`'s watchdog (`apps/body/src/supervisor.ts`, `DEFAULT_ROOM_WATCHDOG_STALE_MS`) force-recycles a Room whose `lastPollAt` goes stale — so the push loop must keep calling `onRoomPollSuccess` for the *life* of a healthy socket, not just once at subscribe time: it fires on every delivered event and on the maintenance tick whenever `client.socket?.connected`. Getting this wrong (as the original WS-push landing on `main` did) makes a perfectly healthy, silent WS Room get killed and reconnected every `watchdogStaleMs`, which is a self-inflicted request-volume storm, not an ingress problem — see `room-ws-push.live.test.ts` and the liveness-signal test in `body.test.ts`.
- **One mention → at most one corner**: `Body.processChannelRequestEvents` (`apps/body/src/body.ts`) is entered concurrently for the same relay event — the WS-push delivery callback and the one-shot HTTP backstop query above both call it, and `pollRoomMaintenance`'s per-tick invocation can overlap a still-running prior tick. The relay-backed `requestAlreadyOpened` idempotency check has a network round-trip race window, so two concurrent calls can both pass it and both call `openSubchannel`, producing duplicate corners from a single mention. `inFlightRequestIds` (a same-process `Set`, checked-and-set synchronously with no `await` in between, released in a `finally`) closes this: the loop body is claimed per event id before any async work, so a second concurrent call for the identical event id no-ops instead of racing. It is deliberately separate from `processedRequestIds` (only set on success, so a failed attempt still retries on a later poll) — see the "creates exactly one corner" test in `body.test.ts`.
- **Query retry policy**: `packages/buzz-client/src/http.ts`'s `requestQueryEvents` retries 5xx/transport errors (3 attempts, 10s/attempt, linear backoff), mirroring `apps/gate/src/relay.ts`'s `createRelayClient().queryEvents` so every `createBuzzClient()` read (mobile + Body's non-`agentRelay` call sites) tolerates a transient ingress 502/429 instead of failing the turn. `WorkspaceSupervisor.reconcile`'s membership/role reads (`isMember`/`listMembers`/`latestRoleProjection` in `packages/buzz-client/src/channel.ts`) go through this same `queryEvents`, so they inherit the retry for free.
- **Query volume attribution (off by default)**: `http.ts`'s `queryEvents()` carries built-in call-site instrumentation — `getQueryInstrumentation()` / `setQueryInstrumentationEnabled()` / `resetQueryInstrumentation()`, or `BUZZ_QUERY_INSTRUMENT=1` in a Node process like Body. `networkRequests` counts actual `/query` POSTs 1:1 with relay access-log lines; `callSites` groups logical `queryEvents()` calls (cache hits included) by `{kinds, tagKeys, callerLabel}` via a best-effort stack-trace label, so it's always >= `networkRequests` — that gap is the batching/caching win, not a bug. Zero-cost when disabled (single boolean check). Immutable-read caching in the same file (`queryCacheTtl`) also covers a single scoped kind:39000 metadata read once non-empty (same 5-minute TTL as a scoped kind:9007 create), and a genuinely-unscoped scan (no `#h`/`#d` — e.g. `listSubchannels`'s child-discovery scan) gets 10s instead of 500ms.
- **`waitUntilMember`/`waitUntilMemberRole`/`waitUntilNotMember`/`waitUntilRoomArchived` (`packages/buzz-client/src/channel.ts`) are WS-primary, not fixed-cadence pollers**: the shared `waitForRelayProjection` helper subscribes to the relevant 39000/39001/39002 kind(s) scoped to the channel (`#d` and `#h`, matching this file's existing dual-tag read fallback) over `ChannelOpsContext.ws` — an optional live-socket accessor `BuzzClient` wires to its own `this.ws` in `client.ts` — and re-runs the same `isMember`/`getChannelRole`/`getChannelMetadata` check whenever a live event arrives, instead of polling every 300ms. WS is opportunistic only (gated on `ws.connected`, never forces a connect): a `RELAY_PROJECTION_BACKSTOP_POLL_MS` (5s) poll of the same check runs concurrently for the whole wait as the correctness backstop, so an absent/never-authenticated/dropped socket just resolves on the next backstop tick instead of stalling — same technique as `apps/body`'s `waitForWritePermissionDecision` below. A raw hand-built `ChannelOpsContext` with no `ws` field (e.g. `Body.agentClientContext()`) transparently falls back to the original fixed-interval loop, which is why that one Body call site and `apps/gate`'s separate HTTP-only client were deliberately left unwired rather than migrated — see `channel.test.ts`'s `waitUntilMember (WS-driven)` suite for both paths.
- **`query(ctx, filters)` (`packages/buzz-client/src/query.ts`) is the WS-primary read funnel every `queryEvents(ctx.http, ...)` call site in `channel.ts`/`community.ts`/`agent.ts`/`direct-message.ts`/`person-profile.ts`/`repo-room.ts`/`client.ts` now goes through**: opportunistic on `ctx.ws?.().connected` (same gate as `waitForRelayProjection` above — never forces a connect, so cold-start reads stay on HTTP), one-shot NIP-01 REQ→EOSE via `wsQueryEvents` (`ws.ts`) on any hit, HTTP `queryEvents` fallback on literally any WS failure (no WS, not connected, throw, timeout, or a close before EOSE). `enqueueWsQueryEvents` in `query.ts` ports `http.ts`'s same-tick microtask batching (`canPartitionFilter`/`selectQueryEvents`, both exported from `http.ts` for reuse) so concurrent same-tick `query()` calls on the same socket collapse into one multi-filter REQ, split back apart per caller exactly like the HTTP batcher. **Sharp edge proven by a live regression test (`ws.test.ts`)**: `wsQueryEvents` must call its `subscribe()` unsubscribe on every exit path (resolve/timeout/close) or the one-shot REQ's subId is left in `RelayWs.subscriptions` and gets wrongly replayed as a live REQ by a later reconnect's `resubscribeLiveRequests()`. `community.ts`'s `findCommunityInvite` is deliberately NOT wired to this funnel — it takes a bare `http`/`readerPubkey` pair (invite redemption can run before a full `ChannelOpsContext`/socket exists), not a `ctx`, so it stays HTTP-only. `apps/gate`'s independent HTTP-only client is likewise untouched (still no WS support there — see `waitForRelayProjection`'s note above).
- **`Body.isRoomAgentOnline()`'s presence cache cannot reuse `roomSockets`**: `apps/body/src/body.ts`'s `presenceCaches` (keyed by channelId; each entry owns its own `createBuzzClient()` + `agentPresenceSubscribe` subscription, seeded once via a single `agentRelay.queryEvents` read since a fresh subscribe's backfill replay isn't guaranteed to have landed yet) exists because its sole caller, `processChannelRequestEvents`'s agent-exchange online/offline gate, is reachable both from `runRoomPushLoop`'s live socket (where `roomSockets.get(channelId)` is populated) *and* from `pollChannelRequests` called directly with no push loop running at all — every live test exercising this path (`agent-exchange.live.test.ts`) does exactly that, so `roomSockets` is not a reliable source there despite looking like a "straight swap" target. Torn down in `dispose()` alongside `roomSockets`.
- **Reconcile never crash-loops the fleet**: `WorkspaceSupervisor.run` (`apps/body/src/supervisor.ts`) wraps each `reconcile()` call in try/catch — a reconcile rejection (e.g. the relay retry budget above is exhausted) backs off via `reconcileRetryMs` and loops again instead of throwing out of `run()`. Because the failure happens before `reconcile()` ever touches `this.running`, already-active Rooms/corners are untouched by a failed tick. Coverage: `apps/body/src/supervisor.test.ts` → `WorkspaceSupervisor transient relay resilience`. **A per-Room join failure is per-Room, and must never reach that outer catch.** `reconcile()`'s join loop wraps each Room in its own try/catch (`noteRoomDiscoveryFailure`): a Room that cannot be served for a legitimate durable reason — the observed one is `materializeRoom` throwing `invited Room <id> is local-only on another checkout` — used to throw straight out of `reconcile()`, which both starved every Room *behind it in the loop* of its join and pinned the whole discovery pass to the 5s error backoff, logging once per pass forever. Such a Room is now parked for `DEFAULT_ROOM_DISCOVERY_RETRY_MS` (10min) and its console line is emitted only when the reason *changes*. The **classification** loop above it (`getChannelCommunityId`/`resolveRoomRepository`/`getDirectMessage`) is deliberately NOT fault-isolated: a Room missing from `desired` is stopped by the loop directly below, so swallowing a transient read there would tear down a healthy running Room — that class of failure belongs to the outer "keep the last known set" backoff. Coverage: `supervisor.test.ts` → `WorkspaceSupervisor per-Room discovery isolation`.
- **Workspace/Room removal is a corroborated tri-state read, and agent keys are never deleted.** `WorkspaceSupervisor.reconcile()` returns `member | not-member | unknown`; every membership query exception (including a non-retryable HTML edge response) is `unknown`, resets removal corroboration, keeps all Rooms/runtime state, logs the degraded state, and retries on the short watchdog cadence. A Workspace or running Room is considered removed only after `REMOVAL_CONFIRMATION_READS` consecutive successful reads agree it is absent. `removeAgentRuntime` (`apps/body/src/runtime.ts`) is intentionally recoverable despite its legacy name: it renames the complete key-bearing directory into `<state-root>/deleted-runtimes/<pubkey>-<timestamp>/` and deletes only repo-local pointer records. Restore by moving that directory back to `<state-root>/beeline/agents/<pubkey>/` and running `beeline start --agent <pubkey>`; see `apps/body/README.md`. Coverage: `apps/body/src/supervisor.test.ts` → `WorkspaceSupervisor removal lease` and the production-shaped HTML failure fixture.
- **`reconcile()` is wake-driven, not a 5s forever poll**: `WorkspaceSupervisor.run` (`apps/body/src/supervisor.ts`) opens one persistent control-plane WS per daemon subscribed to `{kinds:[KIND_PUT_USER, KIND_REMOVE_USER], '#p':[agent.publicKey]}` (9000/9001, the durable NIP-29 mutation log) and calls `reconcile()` only on startup, on a pushed event, or every `reconcileHeartbeatMs` (default `DEFAULT_RECONCILE_HEARTBEAT_MS` = 60s) as a correctness backstop — not every `pollMs` tick. **This is deliberately 9000/9001, not the 39001/39002 role projections**: a removal republishes the projection *without* the agent's `p` tag, so a `#p`-filtered subscription on the replaceable projection would never notice its own removal; the raw put/remove-user event always carries the affected pubkey. The Room watchdog stays on the tight `pollMs` tick (default 5s) since it only reads already-local `RunningRoom` timestamps — no relay cost either way, so decoupling its cadence from `reconcile()`'s costs nothing. If the control-plane WS never connects (or drops), `run()` logs and falls back to the heartbeat alone; it must not call `.disconnect()` on a client whose `.connect()` never resolved (`supervisor.test.ts`'s existing `mocks.createBuzzClient.mockReturnValue({...})` fixtures reuse one shared mock object across every `createBuzzClient()` call in a test, including this new control socket, so an unconditional `finally`-block disconnect there would silently double the disconnect count and break unrelated assertions). Coverage: `apps/body/src/supervisor.test.ts` → `WorkspaceSupervisor control-plane wake signal`.
- **Write-permission decisions resolve off the Room's own WS first, HTTP poll is the backstop**: `Body.waitForWritePermissionDecision` (`apps/body/src/body.ts`) subscribes on `this.roomSockets.get(tlcChannelId)` (the same live socket `runRoomPushLoop` already holds open) for the `WRITE_PERMISSION_RESPONSE_TAG` kind:9 event, instead of polling `agentRelay.queryEvents` every 500ms. The WS path is opportunistic only — a `WRITE_PERMISSION_BACKSTOP_POLL_MS` (5s) HTTP poll runs concurrently for the whole wait regardless of socket state, so a Room driven without a live socket (e.g. `pollChannelRequests` alone, as `room-conversation.live.test.ts` does) still resolves correctly, just off the backstop instead of instantly.
- **The Room/Corner write boundary is ONLY as strong as the harness's permission callback — and one shipped harness has none.** `apps/body/src/session-sandbox.ts` is the fail-closed policy both handlers use: a Room denies every write/edit/delete/move/execute request outright *regardless of the path it names* (cwd isolation constrains the default directory, not absolute-path reach — the observed breach was a Room session editing `/home/lunchbox/proj-buzzy/...` by absolute path while its cwd was correctly the canonical checkout), and a corner denies a mutating request whose target resolves outside its own worktree (absolute, `..`, or symlink — `physicalPath` realpaths the deepest existing ancestor before comparing, so a symlink inside the worktree cannot launder a write out). Reads are untouched on both surfaces. Per-harness flow, read out of the installed adapters and pinned in `apps/body/src/harness-capabilities.ts`: **codex-acp** routes every command/file change through `session/request_permission` AND advertises a real `read-only` mode backed by Codex's own OS sandbox (strongest); **claude-agent-acp** routes every tool through `canUseTool`→`session/request_permission` but advertises no read-only mode (its modes are `default`/`acceptEdits`/`plan`/`dontAsk`/`auto`), so the daemon callback is the whole boundary; **pi-acp NEVER calls `requestPermission` for a tool** — its only permission requests are pi's own extension-UI `select`/`confirm` events, and read/write/edit/bash are emitted as `tool_call` telemetry *after* pi ran them. pi ships no sandbox (its own `docs/security.md` says so), exposes no permission flag/env/setting, and `pi-acp` hard-codes `pi --mode rpc --no-themes`, so there is nothing to pass at spawn: **a pi-backed Room's read-only rule is advisory, not enforced** (`roomSandboxWarning` logs this at Room provision). ACP's permission response carries only an option id — no reason field, and every adapter hard-codes its own denial text — so the "open a corner instead" steer rides `ROOM_READ_ONLY_STEER` into the Room system prompt and the durable conversation, never the rejection itself. Coverage: `session-sandbox.test.ts`, `harness-capabilities.test.ts`, and `body.test.ts`'s `Room sessions cannot write or execute at all`.
- **Agent-initiated corners use the harness protocol, with one narrow exception.** In repository Rooms, codex-acp and claude-agent-acp are prompted to attempt the required mutating tool themselves; their real `session/request_permission` reaches `Body.handleRoomPermissionRequest`, which posts the existing human-signed allow/deny card and opens the corner only after ALLOW. Do not restore the host-side mutation-verb shortcut or expose the `CORNER_REQUEST:` response sentinel to capable harnesses. `pi-acp` cannot request permission before executing, so `corner-request.ts`'s stripped text marker remains a pi-only fallback selected by `usesTextCornerRequestFallback`; unknown/custom harnesses do not inherit it. Coverage: `body.test.ts`'s native/plain-mutation and pi fallback tests, plus `room-native-corner-request.live.test.ts` against real codex-acp.
- **The permission handler is the policy; bubblewrap is a HYGIENE layer under it, not a security floor (captain's decision, 2026-08-22)** (`apps/body/src/bwrap-sandbox.ts`). The bullet below is only as strong as a harness that asks — pi never does. When `bwrap` is on PATH, `Body.sessionSpawnCommand` (`body.ts`) wraps every ACP child: `--ro-bind / /` (which is what makes every checkout, the operator's tree, and `$HOME` read-only without enumerating them), `--dev /dev`, `--proc /proc`, `--tmpfs /tmp`, then per-session mounts. **Both** modes get read-write binds for the harness's own state — the `agent-home.ts` env overlay plus `harnessHomeStateDirs(agentCommand)` for roots no env var relocates; a **corner** adds its worktree and, load-bearing, the repository's **git common directory**, because a corner worktree is a *linked* worktree whose refs/index/objects live under the canonical checkout's `.git`, so without it a corner can edit but never commit (`resolveGitCommonDir`; an unresolvable git dir makes `sessionSpawnCommand` fail OPEN and spawn unwrapped rather than ship a corner that cannot commit), plus the **merge gate's state root** (`~/.no-mistakes` via `mergeGateStateDirs()`, edit sessions only — a Room gains no bind for it): an edit session drives the no-mistakes gate from inside its namespace, and while the shared daemon socket is reachable through the read-only mount (so health checks passed), gate init writes run state under that root and died with "state repository directory is mounted read-only" (live repro 2026-08-23). It is deliberately a SHARED writable bind, not per-corner `NM_HOME` relocation: one gate daemon serves every repo/lane, and a per-corner home would strand corners from that daemon and have them spawn their own inside their namespaces. Network is deliberately untouched (no `--unshare-net`). **A Room having writable harness state is a deliberate departure from "a Room writes nothing but /tmp", and it is not optional** — measured, not assumed: with those dirs read-only `codex-acp` cannot open a Room session at all (`failed to initialize sqlite state runtime under …/codex`) and `pi-acp` cannot open one in either mode (`EROFS … '~/.pi/pi-acp/session-map.json'`, a path pi-acp hard-codes so `agent-home.ts` cannot relocate it). Both surface as a `session/new` error, never as a denied tool call, so nothing on the permission path would report them — `harness-sandbox.live.test.ts` is the guard, and adding a harness preset means checking whether it needs a `HARNESS_HOME_STATE_DIRS` entry. **Three more sharp edges.** (1) `--tmpfs /tmp` replaces the whole of `/tmp`, so any session path living under it — a fixture checkout, a state dir, a corner worktree — is not denied, it is *absent*: `SandboxMountPlan.readOnly` re-binds those after the tmpfs, and argv order is asserted as an exact array in `bwrap-sandbox.test.ts` since bwrap applies mount ops in order. (2) Writable mounts use `--bind-try`, not `--bind`, so a never-created state root cannot fail the whole spawn; `sessionSpawnCommand` `mkdir`s the ones it knows about first, because the harness itself cannot create one on a read-only `$HOME`. (3) The spawned command becomes `bwrap`, so `AcpClient` grew an `agentLabel` (`acp.ts`) used in its exit-rejection text — without it every harness crash is reported and logged as a bubblewrap crash. Detection is one-shot at daemon start (`detectBwrapSandbox`, called from `cli.ts`'s `runStoredDaemon`) and the probe is the real mount table, never `--version`: a `bwrap` that exists but cannot unshare only fails when it tries. It **fails open** — missing/unusable bwrap logs one advisory line and spawns unwrapped, i.e. pre-sandbox behaviour. This is upstream of `createNarrativeCommitter`'s own `\n{2,}` paragraph-break segment cuts (`apps/body/src/activity.ts`) — that logic was always correct, it just never received a real break to cut on. **The break is a heuristic, and it must never fire between two tokens of one word.** Whether a resumption is a fresh thought or the same sentence continuing is not on the wire, so this is decided from the resuming delta's first character (`CHUNK_CONTINUES_PREVIOUS_WORD`, `acp.ts`): a delta opening with an apostrophe, a hyphen, closing/sentence punctuation, or its own leading whitespace binds to the word before it and gets no synthetic break. Without that carve-out any non-text `session/update` landing between the model's *first* token and its second (`"I"` then `"'ll"`) split the opening sentence, `nextNarrativeSegment` read the synthetic `\n\n` as a real paragraph boundary, and `createNarrativeCommitter` durably published the one-character head as its own kind:9 message — so the corner's first visible message read `'ll take a look at the README first.` and looked like the stream head had been eaten by a boilerplate filter. A resumption starting with an uppercase letter still breaks (that is the original glue defect). Regressions: `acp.test.ts`'s "inserts a paragraph break when narration resumes after a tool call…" and "keeps the first characters of a turn when a non-text update splits the opening word", plus `activity.test.ts`'s "commits an opening sentence as one segment, first character included".

Every kind:9 on a channel (narration, `postControlMessage` status cards, the periodic `activity_summary` flush) competes for that window, so once a corner's total kind:9 traffic passes the limit, the earliest events — including its opening narrative segment(s) — are the first pushed out, and the corner opens mid-thought with no error and no sign anything was dropped (durably published, just never fetched). `COLD_BACKFILL_LIMIT` (200, up from 50) trades a slightly larger initial read for making that eviction rare for a corner's realistically bounded single-task event volume; it does not fix the unbounded case (Rooms) or guarantee correctness for an extremely long-running corner — the underlying limit-based fetch is still "most recent N," just a bigger N. Automated tests are unaffected (`pair-cli.test.ts` et al. always `mkdtemp` a fresh git-inited repo *and* pass an isolated `XDG_STATE_HOME`) — the hazard is specific to ad-hoc manual CLI invocations. Always pass an isolated `XDG_STATE_HOME` (and, for `pair`, `--repo` pointing at a throwaway git repo) when hand-testing these commands in any worktree of this repo.
- **Corner ACP continuity has four coordinated authorities.** `session-reprime.ts` builds a #265-budgeted resume brief from the immutable kind:9007 `task`, latest activity plan, read-only git facts, and six recent turns; `SessionScheduler` protects its per-channel FIFO from idle eviction; `serializeRepoLanding` serializes target-ref mutation per repository; and `#t=corner-session` publishes `live`/`suspended`/`waiting-for-slot` with monotonic replay ordering.
- **Two slash vocabularies share one message box, and an unrecognized verb must be visibly marked, never silently executed.** `packages/buzz-client/src/slash-command.ts` is the single source for `BEELINE_SLASH_COMMANDS` (the six composer verbs, ordered to match mobile's picker — `slash-verbs.test.ts` in apps/mobile pins the sync) and `matchSlashCommand`, whose shape rules are load-bearing: a single-slash first token (`/loop`), but a second `/` in the token or args starting with one (`/etc/hosts`, `/usr/bin/env run`) is prose and stays unmarked. Mobile's composer no longer dead-ends on an unmatched token: send/Enter now sends as ordinary prose (daemon marks it), and `SlashVerbPicker`'s empty state names the token (`/<query> IS NOT A BEELINE COMMAND`). Live proof: `apps/body/src/slash-command-notice.live.test.ts`. **The captain's "it opened a corner and then stopped" was a consequence, not a separate defect**: `/loop` reached codex verbatim, which answered with harness-command semantics; if the model attempts a mutation the write-permission card waits up to 10 min of silence (then times out), and an ALLOW opens a corner whose objective is literally the meaningless text (`cornerNameForIntent('/loop')` → `loop`).

## GitHub identity and repository authority

- **GitHub repository identity is the immutable id; owner/name is only its current address, and the auth service heals transfers — never callers.** The live proof: moving `lunchboxfortwo/beeline` to the `Beeline-Work` org made every Room-token request fail with `repository_not_granted` because Room bindings keep the pre-transfer name while installation snapshots carry the new one. Resolution order lives in `resolveGitHubRepositoryAccess` (`apps/auth/src/github-repository-access.ts`, consumed by `/auth/github/room-token` and `/auth/github/room-events`): exact stored grant → id-heal in `AuthStore.githubRepositoryAccess` (a deactivated row still carries the old name's immutable repository id, so the active row with that same id under an active installation wins and returns `resolvedFullName`) → persisted alias (`beeline_github_repository_aliases`) → GitHub's own rename redirect via `GitHubAppClient.repositoryByFullName` (`GET /repos/{old}` 301s; body describes the new location), persisted as an alias on first success. A probe-found destination that is NOT granted produces `{movedTo}`, which room-token surfaces as `repository moved to <owner/name>; grant the App access there` instead of a generic not_granted. Do NOT re-derive this per caller or "fix" it by rewriting relay bindings — auth has no relay write authority by design. Related sharp edge: PostgreSQL rejects a bind with an unused intermediate parameter (42P18, "could not determine data type of parameter $3") — parameter numbers must be contiguous in every store query.
- **Org GitHub App installations cannot be verified through `GET /user/installations`.** That endpoint is keyed to the OAuth lookup token's visibility: user-owned installations always appear but organization installations generally do not (and can fail outright), which 500'd the real org install callback at `completeGitHubInstallation`. The check is therefore account-type-aware in `apps/auth/src/server.ts`: a User installation requires positive confirmation (unchanged posture); an Organization installation treats GitHub's state-bound redirect (only the installing admin's browser receives the one-time state) as authority, refuses on a definitive listing denial, and logs-and-proceeds when the listing is unavailable. Never make the user-token listing a hard gate for Organization installs again.
- **The auth error handler must never produce a silent 500**: non-ProtocolError exceptions are logged at error level with the Fastify request id and returned as `{error:'internal_error', message, reqId}` where message embeds the upstream client error text (plain-language, credential-free) plus the reqId for log correlation. This exists because a production org-install callback returned bare `internal_error` with no error-level log line, making diagnosis impossible.

- Authority and deployment shape: `apps/auth/README.md`. `/auth/capabilities` is the launch gate: GitHub OAuth is visible only when all five `BEELINE_GITHUB_*` values are configured; otherwise the existing Google OIDC path remains visible and unchanged.
- `apps/body/src/repository-truth.ts` is the sole Room repository resolver and supersedes older Stage-1 repository-path notes elsewhere in this file. A remote binding is truth and its canonical checkout is a fetched cache; a `localOnly` binding seeds a separate canonical checkout once and that checkout becomes declared truth. Pairing `root` is private history used only by the opt-in, clean fast-forward post-land sync and must never reach an agent-visible surface.
- One GitHub App installation supplies both picker visibility and repository access. Body mints short-lived installation tokens through `apps/body/src/github-app.ts`; GitHub clone/fetch/push/land paths must not consult ambient Git configuration, credential helpers, `gh`, or host tokens.
- The auth service owns Authorization Code + PKCE and a PostgreSQL-backed, hashed, one-use signed binding ceremony. It never accepts a free-standing provider token or grants relay, Room, role, or merge authority.
- Hermetic provider, adversarial protocol, JWKS rotation/stale-cache, and durable restart coverage: `npm test -w @beeline/auth`.
- **GitHub repository events in Rooms (stars/issues/PRs)**: the signed webhook (`apps/auth/src/server.ts`) extends past installation events to store compact records per repo in `beeline_github_repo_events` (7-day retention, one row per `x-github-delivery`); extraction/filtering is `apps/auth/src/github-repo-events.ts`. The hop to daemons is a long-poll PULL, not relay publish — daemons are outbound-only and public relay records would leak private repo activity — via `POST /auth/github/room-events`, which reuses the room-token authority (agent must be a current member of the Room bound to that exact repo; caller never names the repo) with a 5-min authority cache. Daemon side: `apps/body/src/github-events.ts` watcher per repository Room (started from `runChannelLoop`), cursor persisted in `DurableBodyState.githubEventCursors`; bootstrap = "start from now", later polls catch up late; posts coalesced ≤10-line agent-voice cards tagged `#t=github-event` (CI-watch precedent). Per-Room toggle `githubEventsEnabled` rides the room-config record (`setRoomGitHubEvents`), absent = ON. GitHub App must subscribe to **star, issues, pull_request** (console change) for anything to flow.
- Merge review custody is explicit in `apps/gate/src/worker.ts`: agent identity remains the first fail-closed check, and managed/remote reviewer keys are refused before role lookup.
- Native onboarding uses the strict bind client in `packages/buzz-client/src/oidc-bind.ts` and `apps/mobile/sources/app/(app)/buzz/onboarding.tsx`; reproduce the auth service locally with `npm run dev:emulator -w @beeline/auth` (see `apps/auth/README.md`). Web remains on the legacy advanced-key path until browser key storage is hardened.
- Native GitHub returns have three delivery shapes (browser result, warm `Linking` event, cold `Linking.getInitialURL`) and one authority: `apps/mobile/sources/auth/github-auth-session.ts` durably correlates the strict bind state and GitHub App installation return path; the Expo Router fallbacks are `buzz/github-callback.tsx` and `buzz/github-installation.tsx`. A warm Intent can replace the onboarding component while its original `Linking` listener is still finishing the bind, so callback failures must also go through `google-onboarding-state.ts`'s replayable notice channel; setting only component-local state loses the alert on the visible route. - **GitHub App install/update returns share the OAuth callback, not a Setup URL.** The production App has "Request user authorization during installation" enabled, which makes Setup URL unavailable; "Redirect on update" sends `installation_id`/`setup_action` back to `/auth/github/callback`, whose first branch must remain the installation-completion dispatcher before ordinary sign-in code exchange. Repository-selection browser sessions also refresh `/auth/github/repos/:pubkey?refresh=1` on foreground return/dismiss, because a deep link and the installation webhook are delivery optimizations, not correctness prerequisites. Authority: `apps/auth/src/server.ts`, `packages/buzz-client/src/oidc-bind.ts`, and `apps/mobile/sources/auth/github-auth-session.ts`.

The load-bearing rule is that a key created here is **never persisted until the person has actually seen it and said so** — `createNewKeyDraft` generates with `persist: false` (the same deferral the provider-bind path uses for its candidate key), and `canEnterWithNewKey` requires BOTH `seen` (the nsec was revealed or copied at least once — a checkbox over a masked string confirms nothing) and `confirmed` (the explicit "I saved my key" tap). A device-held Nostr key has no server-side recovery, so an unbacked key silently written to SecureStore is an identity the person loses with the phone. The gate is re-checked inside `handleEnterWithNewKey` and inside the checkbox's own `onPress`, not only via `disabled`, so it never depends on a touchable honouring a prop. Coverage: `sources/auth/new-key-onboarding.test.ts` (key validity, no-persist, gate truth table) and `sources/app/(app)/buzz/onboarding.newkey.test.ts` (the real screen, rendered).

## Daemon self-update

- **Authority**: `apps/body/src/self-update.ts` (download/verify/atomic-swap/rollback/busy-gate/restart) and `apps/body/src/self-update-manifest.ts` — the ONE seam for the published manifest contract (URL resolution + JSON shape mapping). When the `beeline-cli-publish` companion lands its real contract, reconcile by editing ONLY that seam file. On-demand path: `apps/body/src/self-update-cli.ts` (`beeline update [--check|--status|--rollback|--force]`). End-to-end proof: `apps/body/scripts/self-update-demo.ts`; coverage: `self-update.test.ts`, plus `self-update-layout.test.ts` (the layout contract, incl. a real-shell install→update→fresh-shell e2e).
- **THE `<prefix>/lib/beeline` CONTRACT (one meaning, five consumers — see "THE CONTRACT" in self-update.ts): it is the ACTIVE BUNDLE ANCHOR** (symlink into `lib/beeline-releases/<id>`, or a legacy real dir pre-migration), never "the lib directory itself". The 1.x regression: wrappers resolved the anchor with `pwd -P`, node mis-resolves any `..` that follows a symlinked dir, AND `beelineInstallLayout` derived `binDir` one level off (`<prefix>/lib/bin`) so activation rewrote its stable forwarders where nothing executed them — net effect: after the first update executed from a post-swap shell, every fresh-shell `beeline` died MODULE_NOT_FOUND on `<release-root>/beeline-cli.mjs`. The fix: forwarders + bundle wrappers export/derive BEELINE_LIB_DIR as the clean anchor path (never handing node a `..`; forwarderScript() must stay textually identical to install.sh's heredocs — repairInstallForwarders content-matches against it), beelineInstallLayout normalizes symlink-resolved values back to the prefix anchor, entrypoint/identity reads tolerate both bundle shapes (release-shaped and legacy-flat; activateRelease normalizes flat migrations via normalizeLegacyBundleShape), cli.ts repairs stale forwarders at startup, and install.sh lays out release-shaped installs and converges legacy/mid-migration hosts. Do not reintroduce pwd -P resolution of $0 or a second writer of `<prefix>/bin/*`.
- **The `curl | sh` installer must swing the anchor with rename(2), never `mv`.** GNU/BSD `mv` follows a destination symlink that points at a directory — exactly the anchor's contract shape — so the pre-#333 install.sh moved each new anchor link INSIDE the old release (`beeline-releases/<old>/beeline.new.<pid>`) and left `<prefix>/lib/beeline` on the previous bundle forever: every reinstall kept running the stale release and piled up timestamp-suffixed duplicate dirs. install.sh now stages the download beside the releases root (same-fs), reuses a complete same-id release dir on reinstall (idempotent — no `<id>-<epoch>` duplicates), swaps via `node fs.renameSync` (the same primitive as `activateRelease`), sweeps stray `beeline.new.*` links and release-id-named symlinks under `beeline-releases/`, and prunes only guarded `<base>-<digits>` duplicates whose commit matches an existing `<base>` and that neither the previous nor current anchor referenced. Coverage: `self-update-layout.test.ts`'s over-install suite.
- **Install layout after first update**: bundles live in `<prefix>/lib/beeline-releases/<releaseId>/` and `<prefix>/lib/beeline` becomes a SYMLINK swapped by a single atomic rename; the previous release is kept for rollback, and `<prefix>/bin/*` become stable forwarders into the symlinked bundle. Legacy installs (real dir at `lib/beeline`) migrate on first activation — that one-time migration has a millisecond window between two renames; every later swap is one rename. Layout detection must use `lstat`, never `stat` (stat follows the symlink and misreads the layout as legacy).
- **Identity + state live in the install, not in any daemon**: `bundle.json` (stamped with commit + YYYY.MM.DD version by `scripts/build-beeline-bundle.mjs`, installed by `relay-stack/web/install.sh`) is what the daemon reports as running; `.state/update-state.json` and `.state/pending-update.json` under `beeline-releases/` are shared across daemons. The pending journal means "a daemon restarted onto this and must prove health within DEFAULT_UPDATE_CONFIRM_WINDOW_MS"; stale ⇒ auto-rollback at next start, fatal supervisor error inside the window ⇒ rollback + relaunch of the previous release. The CLI apply path deliberately sets `restartHandover: false` — no restart, no journal.
- **Busy gate reuses existing turn state**: `Body.isBusy()` (`runningAgentTasks`/`inFlightRequestIds` — the same state the queued-steer ack trusts) polled through `WorkspaceSupervisor.isWorkspaceIdle()`; never invent parallel busy notions. Update notices go out via `broadcastDaemonNotice` (ordinary agent messages to served Rooms). Restart handover spawns the replacement from the ACTIVE release's `beeline-cli.mjs` via `launchRuntimeDaemon`'s `foreground` option (spawned children carry `BEELINE_DAEMON_BACKGROUND=1`); `runStoredDaemon`'s pid-file cleanup only unlinks while it names THIS pid.
- Automatic updates are default-on (6h cadence, 2min startup grace); `BEELINE_UPDATE_DISABLE=1` turns off only the automatic path — an explicit `beeline update` request always wins. Manifest URL: `BEELINE_UPDATE_MANIFEST_URL` (default currently points at the not-yet-published `usebeeline.app/dl/manifest.json`).

- **One glyph per concept**: `MEMBERS_GLYPH`/`MEMBERS_LABEL` (`apps/mobile/sources/buzz/vocabulary.ts`) is the single members mark (`⌬`) and word used by every route into the members screen — the Room-list header, `CommunityInviteEntry`, `settings/workspace.tsx`, and `MembersScreen`'s own title and empty state. `buzz/members-glyph.test.ts` asserts both halves of the rule: every entry point imports the token (no hardcoded glyph, no surviving "PEOPLE" wording), and the glyph is never one of `cornerStatusPresentation`'s lifecycle glyphs, because a diamond on any Buzz surface means live corner work.
- **The corner reads narration-first; tools are footnotes.** `buildTurnActivity` (`apps/mobile/sources/buzz/activity-timeline.ts`) splits one turn three ways and the split is the whole design: `narration` (`kind:'output'` items — the agent's own prose) renders on the slab at `ledgerBright`, full width, no glyph, no indent, **never** behind a disclosure; `actions` (anything that executed, mutated, or failed) keep one line each; `observations` (read/search/list) fold into a single verb-counted note (`12 TOOL CALLS · read 8, searched 3`) that opens a bottom-up review sheet, newest call first, with failures pinned to the top. The dividing line is "did this change or observe state," not "was it expensive" — `actionWeight()` owns it. Three distinctions worth not re-merging: `kind:'summary'` (body's synthetic `activity_summary` receipt) is mechanism and feeds only the count, never `narration`; a tool call with `files` emits *only* its file rows, never a parent row printing the same edit twice; and the tone ladder is quiet → `ledgerBody` (a mutated path) → `ledgerBright` (a failure), because gold is already spent and luminance is the only escalation left. Note that a corner's *main* narration wire is not activity at all — it is `createNarrativeCommitter`'s `#t=agent-message` segments, which have always rendered as ordinary luminous ledger prose.
- **The pinned corner line and the per-turn "thinking" indicator are two independent facts, and the daemon has always published them as two unrelated streams.** `#t=agent-turn` (`postAgentTurnStatus`, `apps/body/src/body.ts`) is published on *the channel the turn runs in* — a Room turn's `working` event lands in the Room, a corner turn's lands in the corner — and means only "this agent is composing a reply here". A corner's existence and lifecycle reach the parent Room through a completely different event: `postParentCornerStatus`'s `subchannel`+`display-status` card, plus the `status=archived` close notice. Nothing on the wire is ambiguous; the client conflated them. `[channelId].tsx`'s pinned-line derivation used to set its gold `live` flag from the Room's agent-turn signal and take its destination from `tappableCornerId ?? permittedCornerId` — and `permittedCornerId` (the last write-permission ALLOW's `subchannelId`) is a durable transcript event with **no lifecycle filter at all**, so a plain question in a Room lit the gold `beebee active: <corner> · view →` line pointing at a long-archived corner and let the reader tap into a read-only channel. `selectPinnedCorner` (`apps/mobile/sources/buzz/room-indicators.ts`) now owns that choice from corner state alone: it merges the transcript's live status cards with the relay-read `cornerLifecycle` snapshot taking the **most terminal** status either source reports (a snapshot fetched before a corner closed must never re-open it), and honours `permittedCornerId` only when *neither* source knows the corner yet *and* the lifecycle read has actually answered (`cornerLifecycleLoaded` — "unknown" and "not loaded yet" are different answers). **The line's presence means "this corner is open and worth returning to," not "actively working"**: any non-terminal status (`live`/`needs-attention`/`open`) is a candidate — only `isCornerTerminal` (`merged`/`failed`/`archived`) excludes one, so a corner that finishes its work and goes quiet keeps its pinned line instead of vanishing back to the corners-list expander. An earlier cut of this line restricted candidates to `live` alone, which over-corrected: a finished, review-ready corner had no entry point back except the expander. Gold and the breathing pulse (`isPinnedCornerLive`) are reserved for `live` only, so an idle/waiting corner still reads as calmer than a working one even though both are pinned. When several corners qualify, `PIN_RELEVANCE` (`room-indicators.ts`) — deliberately distinct from `cornerStatusPrecedence`, which resolves conflicting reports of *one* corner's status and must stay terminal-highest — picks a review-ready one (`open`, `isPinnedCornerReadyForReview`) first, then a working one (`live`), then the most recently active, because review-ready is the most actionable thing a captain can do. `open`'s ONLY path onto the wire (`cornerSummaryFromEvents` in `buzz-rig-transport.ts`) is a `ready` display-status or a `merge-ready` tagged event — it never means a plain idle-but-open corner, which is why `cornerStatusPresentation`'s label for it is `READY`, not `OPEN` (`[channelId].tsx`'s `!isCorner` branch of `cornerLiveBar` also hides the line outright when `agentsOffline`, for the same reason — an offline daemon cannot be doing that work). The turn indicator is its own `TurnProgressLine` (`apps/mobile/sources/components/buzz/TurnProgressLine.tsx`), unpressable, driven by `activeAgentTurn` alone. Independence is enforced as source assertions over the two `useMemo` dependency lists in `roomIndicators.test.ts`, not by care. **Known gap, deliberately not closed here**: the daemon posts no parent corner status for a corner *follow-up* turn (`pollMembers`' `promptNewTurn`), so a corner running a follow-up shows no pinned line at all until its next `working`/`ready` card — honest-but-conservative, and preferable to the false gold that shipped. (A corner's *own* self-referential line, rendered when `isCorner` — "is this session I'm in still moving" — is a separate code path keyed on `sessionState`/`displayedCornerStatus` and still uses the quiet `idle` tier; only the Room-level pick-among-corners line above the composer is active-only.)
- **A corner's status is NEVER in the transcript — active or terminal.** `CornerLiveBar.tsx` is one line directly above the composer on both surfaces, naming who is working and what on (`beebee active: feat/ux-fix-now`) with `view →` in the right gutter; it is the Room's *only* active-corner affordance. `renderItem` returns `null` for **every** `item.corner` message (not just active ones) and for an `allowed` write-permission with a subchannel, and `WritePermissionOutcome` does not navigate at all. Rationale: a note inscribed when a corner opened scrolls away and then lies ("open" long after it merged), and a terminal stamp (`Alden ✕ FAILED`, `◇ OPEN`) interrupts a live conversation with a dead record while duplicating the pinned line. Finished corners are recorded in `buzz/corners/[roomId]` instead. **Motion**: the live line breathes via `HullLivePulse` — a calm heartbeat on the shared `motionTokens.liveCycle`, mounted only when live. It is deliberately NOT a travelling sweep, progress bar, or row of dashes (a 28-segment gold flow band shipped once and read as broken chrome at rest); a moving indicator also implies "filling toward a finish", which is a claim the product cannot make about an agent's turn. An open-but-idle corner keeps the same line on `ledgerQuiet` with no motion, so gold stays the live/online meaning only, redundant with the copy (`active` vs `idle`) and never lit for an offline agent (that fact belongs to the separate offline hint).
- **Diff added/removed coloring is a deliberate, in-code-documented exception to Grok Mono Hull's zero-chroma rule ("captain override"), not a violation to grayscale-ify.** `ChangeReviewPanel.tsx`'s `diffAddedLine`/`diffRemovedLine` and `ActivityTimeline.tsx`'s `diffAdded`/`diffRemoved` (its own inline per-file diff drill-down) both source the same conventional green/red from `darkTheme.colors.diff` (`theme.ts`, Happy's legacy palette) — one shared source, not two independently hand-picked palettes, after a fix that found `ActivityTimeline.tsx` had drifted onto a second, slightly different pair of hex values. Hunk headers and context lines stay on the neutral grayscale palette in both (`groknight.bgHover`/`bgTerminal`, `groknight.textMuted`/`textSecondary`) — only added/removed lines get color; `groknight.ts`'s `danger`/`success` tokens still deliberately share one gray, since that rule has no carve-out for chrome/state elsewhere in the app. **Corner change-review diff (`ChangeReviewPanel.tsx`) does not use the legacy Happy diff renderers** (`components/diff/PierreDiffView.tsx`, `DiffView.tsx`) despite sourcing the same color values — those components render a different diff UI shape entirely, not because of the color exception. The per-file diff sits inside the parent Room's *inverted* transcript `FlatList` (as `ListHeaderComponent`). **Android nested-scroll direction matters**: a vertical `FlatList` nested inside a horizontal `ScrollView` never receives vertical drags on Android regardless of `nestedScrollEnabled` — that shape (shipped in #173) left the diff unscrollable vertically. The working shape is vertical-outer, horizontal-inner: a bounded (~300px) vertical `ScrollView` (`testID="change-review-diff-scroll"`, `nestedScrollEnabled`) wrapping a horizontal `ScrollView` (`nestedScrollEnabled`) wrapping a plain column of `Text` rows — same-axis nesting (vertical diff inside the vertical transcript) hands the gesture off correctly via `nestedScrollEnabled`, cross-axis does not. Rows are plain `Text`, not a virtualized `FlatList` (the previous vertical `FlatList` is exactly the piece that broke), capped at `DIFF_MAX_RENDERED_LINES` (1500) with a truncation footer to bound memory; long lines use `numberOfLines={1}` plus an explicit width estimated from the longest line (`DIFF_CHAR_WIDTH_PX`) rather than wrapping, so the horizontal `ScrollView` has real content to scroll.

- **The foreground never blocks on the network — enforced, not just intended.** The JS thread must not wait on a relay round-trip before showing UI, and must not project/sort/store-write a network response *on* the interaction that triggered it. Authority: `apps/mobile/sources/buzz/room-entry.ts` (the enter-room fan-out and its contract docblock) and `apps/mobile/sources/buzz/defer-interaction.ts` (`afterInteractions`, the only sanctioned way to schedule response processing). Add a new relay read as another independent `step()` in the fan-out; never as a link in a chain. **Two related whole-app re-render traps in `local-cache.ts`**: `updateListSummaries`/`updateListCornerStatus` must stay identity-preserving when nothing actually changed (the room list stays subscribed to this store while a Room covers it, so a rebuilt `channelLists` map re-renders and re-sorts it once per delivered live batch), and any live subscription must coalesce into `cacheLiveSessionEvents` per animation frame — measured 72.6x more array work feeding it one event at a time, before counting the store notification per event.

- **Chat header identity must never guess between "Room" and a corner slug**: `channelHeaderTitle`/`cachedChannelKind` (`sources/buzz/corner-session.ts`) own that decision. `resolvedChannelName` is `null` until the channel's own `getChannelMetadata` lands and `''` once it lands empty — two different answers — and `channelKind` is tracked separately from `parentChannelId` because an absent parent means "Room" only *after* the read (before that it means "unknown"). `null` from `channelHeaderTitle` means render the skeleton (`testID="chat-title-skeleton"`), never a word. Both reads are independent `step()`s of the `hydrateRoomEntry` fan-out (`sources/buzz/room-entry.ts`), each committing the moment it lands, because sharing one load `Promise.all` put the header name behind the transcript backfill, a possible 750ms empty-room retry, the presence subscribe, and the presence backfill. `onParentChannelId` therefore fires on **both** branches — `null` is the real answer "this is a Room", not the absence of one, and `channelKind` has no other source. The screen's own DM title (`displayRoomName`/`displayHeaderTitle`) layers on top of `channelHeaderTitle` from cached peer identity rather than from a read inside hydration, so a warm cache titles a DM on its first painted frame. `patchChannel` caches the channel's raw name (possibly `''`), never `ROOM_LABEL` — a cached label re-seeds the wrong header on the next cold open.
- **Leaving a corner is a lookup, not a stack pop** (`sources/buzz/corner-navigation.ts`, `chatBackAction`). A Room and a Corner are the *same* Expo Router route (`buzz/chat/[channelId]`), so "the screen underneath" is not reliably the parent Room, and `router.back()` from a corner could walk into another corner: the notification handler uses `router.navigate(..., { dangerouslySingular: true })`, which expo-router's forked StackRouter implements as *filter the matching route out of the middle of the stack and re-append it on top* (`node_modules/expo-router/build/layouts/StackClient.js`) — it reorders rather than pops, so a Room can end up above its own corner. Two more failure modes: the Room-list corner dropdown pushes a corner with the Room never on the stack, and a notification cold start can leave the corner as the only route, where `router.back()` is a silent no-op. `chatBackAction` finds the parent Room *by channel id* and pops exactly to it, opens it in place when it is absent, and falls back to the Room list rather than a no-op. `router.dismissTo` is **not** usable here: with no `getId` on the screen, React Navigation's `POP_TO` matches by route *name*, which the corner itself also has, so it would just rewrite the corner's own params. Every corner push goes through `cornerHref(cornerId, parentId, name?)` so the destination always knows its parent (and its title) on frame one.
- `/buzz/corners/[roomId]` (the standalone "All corners" list) is reached from the `ALL CORNERS` link that ends the Room-list dropdown, and it is now the **only** place a finished (`merged`/`failed`) corner is recorded — the transcript no longer carries corner cards. Active corners are also reachable from the Room-list dropdown and from the pinned corner line inside the Room.
- **Body control message shape**: subchannel-open and intro messages now carry `["repo", ownerHex/repo]`, `["tip", 40-hex]` tags alongside existing `branch`, `subchannel`, `session`, `mode` tags. See `apps/body/src/body.ts` `openSubchannel()`.
- **`getSubchannelMergeTarget()`**: reads merge target from subchannel body-control messages in `BuzzRigTransport`. Used by the Approve button UI.
- **Change review wire**: Body computes the exact base→feature-tip manifest and chunked per-file patches before `merge-ready` (`apps/body/src/change-review.ts`). Protocol tags/types live in `packages/buzz-client/src/change-review.ts`; payloads use kind:30078 so they never consume kind:9 transcript backfill. Mobile fetches the manifest eagerly and each signed patch lazily through `BuzzRigTransport`. `scripts/ui-demo-provision.ts` creates a relay-backed review fixture without running an agent.
- **Merge approval wire**: `buildMergeApproval`/`submitMergeApproval` from `@beeline/buzz-client` produce kind:9 events with `t=buzz-merge-approval`, `repo`, `branch`, `tip` tags. Gate worker (`apps/gate/src/worker.ts`) verifies the exact binding. No workflow kinds (46010/46011/46012).
- **Corner authority boundary**: edit-mode ACP permissions are auto-approved inside the isolated corner worktree. The only human approval is the exact-tip collapse into the protected line, and the gate rejects every registered agent identity regardless of Room role.
- **Demo script**: `scripts/merge-demo.ts` exercises the full merge flow end-to-end against live relay.
- **Tradeoff**: the parallel screen path avoids deep refactoring of Happy's sync layer. If extending screens further, consider unifying with Happy's screen hierarchy.

## Android push notifications

- App registration lives in `apps/mobile/sources/push/buzz-push-registration.ts`; runtime defaults/overrides are in `app.config.js` and `sources/buzz/runtime-config.ts`. Fresh clients use `https://usebeeline.app/push`; `https://push.buzzrouter.com` remains a permanent accepted alias for already-shipped or stored configurations. `relay-stack/compose.yml` runs the gateway on the shared network with no published port; `relay-stack/nginx.conf` strips `/push/` and forwards to `push-gateway:8788`, while its hostname-specific server preserves the alias. The FCM credential is read-only and the existing registry/delivery directory is bind-mounted for atomic durable writes; deployment and migration prerequisites are exact in `apps/push-gateway/deploy/README.md`.
- **The push toggle reflects REGISTRATION truth, not the requested preference** (fixed 2026-08 after the push-diagnosis scout proved a device could show "on" with no bound token). Each attempt classifies into a `BuzzPushRegistrationPhase`, persists to `@beeline/buzz-push/registration/<pubkey>`, and logs `[buzzy-push]` lines (permission tuple, token fingerprint+length — never the full FCM token, POST URL + HTTP status). Retryable failures retry automatically on foreground via `retryBuzzPushRegistration` (backoff in `_layout.tsx`'s AppState listener; permission gaps don't count against backoff, and automatic retries never re-prompt). Presentation rules are pure in `sources/push/buzz-push-status.ts`; screen wiring pinned by `identity.push.test.ts`. Never reintroduce an unlogged permission-denied return or a switch that mirrors the requested value.
- Notification presentation authority is `apps/push-gateway/src/mapping.ts`; cached recipient-authorized Room/sender resolution is in `metadata.ts`. Message previews are intentionally lock-screen-visible, while Android `tag`/FCM collapse keys replace rapid updates per Room.
- At-most-once delivery authority is `apps/push-gateway/src/delivery-state.ts`: event/recipient attempts are durably reserved before FCM, delivered results and per-recipient cursors survive restarts, and bounded history cannot reopen old backlog. `mapping.ts` + `metadata.ts` fail closed to persistent Workspace-linked Rooms and suppress fixture/test Room, repository, Workspace, and marker signals. `npm run verify:live -w @beeline/push-gateway` proves fixture=0, real=1, restart/replay=0 additional payloads with an isolated identity and no FCM client.
- Gateway authority and operations: `apps/push-gateway/README.md`; durable production deployment is `apps/push-gateway/deploy/README.md`. The Compose gateway reaches `relay:3000` for both ACL-scoped reads and event wakeups, carrying `BUZZY_RELAY_HOST=usebeeline.app`; its HTTP server starts only after the relay WebSocket connects. Credentials and device tokens must never be logged or committed.
- Gateway checks: `npm run build -w @beeline/push-gateway && npm test -w @beeline/push-gateway`.

## Community model

- SDK authority: `packages/buzz-client/src/community.ts`; gate convention + live proof: `apps/gate/src/community.live.test.ts`.
- Workspace pictures use the existing admin-gated kind:9002 metadata command and relay-signed kind:39000 projection; kind:9007 stays immutable and supplies the owner plus fallback picture. The relay's current projection preserves the namespaced picture URL through `purpose`; `community.ts` owns this compatibility convention.
- A community reuses NIP-29 group state: kind:9007 stream create with a self-referencing `community=<h UUID>` tag, kind:9000 roles, and 39001/39002 admin/member projections. Contained channels carry `community=<community UUID>`; absent remains a valid standalone channel.
- Workspace membership is asserted as direct membership in every live top-level Room for people: invite redemption skips corners, DMs, and archived Rooms while repairing existing Room membership, new community-linked Rooms mirror current human members, and self-listing Workspaces repairs historical/partial projections before mobile Room discovery. Registered agents are linked once at Workspace scope, never participate in that repair, and require an explicit per-Room attachment. Live proof: `packages/buzz-client/src/community-invite-visibility.live.test.ts`.
- Invites are signed kind:30078 lookup records (`t=buzz-community-invite`, `d=SHA-256(token)`, NIP-40 `expiration`). Token-only reads must use `findCommunityInvite`, which also scans the marker tag for legacy group-scoped kind:9 records because Buzz requires an unknown `h` to query those directly. Redemption validates the marker and self-adds through kind:9000; plaintext tokens are never published.
- Invite web authority is `relay-stack/nginx.conf`: the `relay-front` service owns the published relay port, serves `/join/bzi_*` plus both `/.well-known` app-association documents from `relay-stack/web/`, and proxies every other HTTP/WebSocket request to Buzz.

## NIP-05 handles (display + verify + Buzz-issued `name@usebeeline.app`)

- `packages/buzz-client/src/nip05.ts` owns parsing (`parseNip05Identifier`/`normalizeNip05Identifier`) and client-side verification (`verifyNip05`, fetches `https://<domain>/.well-known/nostr.json?name=<local>` and checks it maps back to the expected pubkey) of a `name@domain` identifier. It never throws — every failure mode (bad format, unreachable domain, malformed response, name/pubkey mismatch) resolves to a distinct honest status (`verified`/`mismatch`/`unreachable`/`invalid`), consumed by `apps/mobile/sources/buzz/nip05-verification.ts`'s cache/hook so a label only ever renders the nip05 string once *that viewer's own client* has independently confirmed it — the profile's `nip05` field itself is never trusted at face value.
- `PersonProfile.nip05`/`PersonProfileInput.nip05` (`packages/buzz-client/src/types.ts`, wired in `person-profile.ts`) round-trips through the standard NIP-01 kind:0 `nip05` content key, same optional-field pattern as `avatar`/`handle`.
- `apps/mobile/sources/buzz/member-display.ts`'s `personIdentityLabel` is the one shared display waterfall (verified nip05 → `@handle` → name → truncated npub); it is wired into `MembersScreen.tsx` (central per-render verification map keyed by pubkey) and `settings/identity.tsx` (own-profile editor + verification badge, `useVerifiedNip05Status`). The chat transcript (`chat/[channelId].tsx`) only got the DM peer room-title spot wired (the one self-contained async call site); its many other `shortMemberNpub` call sites (message author, participant list, mention dropdown) were deliberately left on the pre-nip05 fallback chain — wiring those in means either extracting per-row list components to host `useVerifiedNip05Status` or growing this already 2800+ line file's central `personProfileByPubkey`/effect graph, and was scoped out of the initial landing as a fast-follow rather than risked blind.
- **Issuance** (a first-come-first-served, Buzz-minted `name@usebeeline.app` handle) is owned by `apps/auth` (`@beeline/auth`), the same deployed TS service that already owns the DB and sits behind `usebeeline.app` via `relay-stack/nginx.conf`'s `/auth/` proxy — not `apps/gate`, which has no persistence layer. `apps/auth/src/protocol.ts`'s `isValidNip05Name` (lowercase alnum + `-`/`_`, 1-30 chars, reserved-name blocklist) gates a flat `beeline_nip05_names` table (`apps/auth/src/store.ts`'s `claimNip05Name`/`resolveNip05Name`; name is the primary key, so FCFS is enforced by the unique constraint itself — no explicit transaction needed). `POST /nip05/claim` (`apps/auth/src/server.ts`) is NIP-98-authenticated (reuses the same `verifyNip98Header` + `claimNip98Event` replay guard as `/auth/oidc/links/:pubkey`) and reachable through the existing `usebeeline.app` tenant — it needs no new `BUZZY_AUTH_TENANTS_JSON` entry. `GET /.well-known/nostr.json?name=<name>` deliberately bypasses the tenant/Host map entirely (it's a single flat namespace for the whole product, not per-community) and sets `access-control-allow-origin: *` for cross-origin NIP-05 fetches. **Both routes are new top-level paths, not nested under the existing `/auth/` prefix, so they are not yet reachable in production** — `relay-stack/nginx.conf` needs two new proxy locations to `auth:8789` (`/nip05/` and the exact-match `/.well-known/nostr.json`, mirroring the existing `/auth/` block's headers), and the bare apex hostname `usebeeline.app` (not just `usebeeline.app`) must reach the same `relay-front` container for the well-known route to resolve at all, since that's the literal domain NIP-05-verifying clients fetch. `packages/buzz-client/src/nip05.ts`'s `claimNip05Handle` is the SDK call site (same `endpoint`/`nip98AuthHeader`/typed-error shape as `oidc-bind.ts`'s `lookupRecovery`), wired into `apps/mobile/.../settings/identity.tsx`'s "BEELINE HANDLE" section, which writes the claimed `<name>@usebeeline.app` onto the profile via the existing `setGlobalPersonProfile` immediately (same immediate-write pattern as `changeAvatar`, not the deferred "Save identity" button) so the already-shipped verify/display path lights up as soon as the well-known route is wired.

## Explicit external MCP capabilities

- `apps/body/src/external-mcp-capabilities.ts` is the authority for account-backed tools deliberately granted to one agent. Runtime records store profile names only (`externalMcpCapabilities`), never copied operator MCP config, commands, environment values, or credentials. The first profile is `squire`, selected at pairing with `--mcp squire`; account capabilities require `--access creator`, are re-expanded on every Room/corner session and restart, and are omitted again defensively for any non-creator config.
- A Room permission callback may allow an explicitly mounted external server even though the Room filesystem stays read-only. Identification accepts the measured codex-acp/claude-agent-acp MCP title shapes and exact `rawInput.server`, but rejects shell payloads and native mutation kinds before title matching so a command/edit cannot spoof an external MCP call.
- Mobile draft/final reconciliation happens in `upsertChatMessages` (`apps/mobile/sources/sync/transport/buzz-event-projection.ts`). When a final `agent-message` settles an already-visible `isAgentDraft` bubble, strip `isNew`: otherwise `LedgerEntry`'s typewriter blanks the fully streamed draft and retypes the final text from scratch, which looks like two competing renderers.
- **`isNew` is a transient "arrived this session" signal — never persist it, and the entrance animation is consume-once.** It drove the new-message entrance (`NewMessageMaterialize`, `MonoHull.tsx`) but was written verbatim into the MMKV snapshot by `persisted()` and re-stamped on already-seen messages by warm revalidation's inclusive cursor edge (`local-cache-sync.ts`), so old rows replayed their entrance on every Room re-entry / FlatList remount. Three load-bearing halves: `persisted()` strips it at serialization; `restoreChannels()` strips stale flags caches written by pre-strip builds (same floor as retired-agent notices); and `buzz/message-reveal.ts` holds the module-scoped, never-persisted revealed-id set that makes `NewMessageMaterialize enabled messageId=<id>` animate at most once per id per app session (decision frozen per instance via ref so a mid-animation re-render can't flip the wrapper; marked in an effect, not during render). The typewriter is on the same contract (it was the second half of the same replay bug, fixed separately): `Ledger.tsx`'s `TypewriterMarkdown` gates its one type-out per message id through the SAME `message-reveal.ts` registry (same freeze-per-instance + mark-after-commit care), so warm revalidation / WS replay re-stamping `isNew` cannot re-type already-seen prose either — do not reintroduce a raw `Boolean(item.isNew)` animation gate outside the component. Coverage: `local-cache.test.ts`'s persist/restore isNew tests, `components/buzz/NewMessageMaterialize.test.ts`, `components/buzz/Ledger.test.ts`'s typewriter reveal-lifecycle block.

## Local relay stack vs canonical clones (demo/live-testing sharp edge)

- `repository-truth.ts`'s `cloneUrl` maps the `git://host[:port]/path` origin marker to `https://…` — correct for production but UNUSABLE against the local docker stack (`relay-stack/compose.yml`, plain HTTP on 127.0.0.1:3010): a paired repository Room's daemon cannot materialize its canonical checkout and parks the Room with `could not clone canonical cache … gnutls_handshake failed`. When live-testing daemons against the local stack, pair repo-less (`beeline pair <code>` with no `--repo`) and invite top-level Rooms instead — Room lifecycle, serving, quarantine, presence and restart behaviour are all exercisable without git hosting. Gate helpers (`createCommunity`, `createChannel`, `queryEvents`, …) resolve their relay from env AT IMPORT TIME: set `BUZZY_RELAY_HOST=127.0.0.1:3010`, `BUZZY_RELAY_SCHEME=http`, `BUZZY_RELAY_URL=http://127.0.0.1:3010`, `BUZZ_RELAY_URL=ws://127.0.0.1:3010` BEFORE importing `@beeline/gate`, or reads/writes silently go to PRODUCTION (usebeeline.app) — this bit once and littered a handful of empty test Workspaces onto the production relay.
