## Branch conventions

- `fm/*` feature branches often stack on each other (PR base is another `fm/*` branch, not always `main`) — check `gh pr list --json baseRefName,headRefName` before assuming a task's target file exists on `main`.
- The local-only `fm-integration-verify` branch (many `fm/*` branches merged together for cross-branch verification) has a pushed origin counterpart: `fm/buzzy-integrated`. If a task references a file that doesn't exist on `main`, check `fm-integration-verify`/`origin/fm/buzzy-integrated` before concluding the task's premise is wrong; find the originating single `fm/*` branch with `git branch -a --contains <commit>` to pick the correct PR base rather than opening against `main`.
- Cherry-picking a single commit off a `feature/*` branch that has other, superseded commits ahead of it in the same lineage: the target commit's diff can still reference state (a JSX identifier, a style key) introduced by one of those earlier, unwanted commits, because that state is unchanged context between the cherry-picked commit and its parent and so is never part of the applied patch. `git cherry-pick` resolves the surrounding hunks fine but silently omits the declaration, leaving a dangling reference — `npm run typecheck` catches it (`Cannot find name`), but a plain merge-conflict resolution pass will not. Diff the target commit against its own parent (`git show <parent>:<file>` vs `git show <commit>:<file>`) to see exactly what it adds versus what it merely touches as context, and drop the JSX/state that belongs to the unwanted ancestor commit rather than reintroducing it.
- Reconciling two independent corner branches that each add a new trailing optional parameter to the same shared function (e.g. two different `feature/*` branches both extending `activity.ts`'s `buildAgentMessage`/`postAgentMessage` signature) produces a real conflict on the parameter list, not an auto-mergeable one — git cannot infer the combined order. Resolve by grepping every call site of the function on the pre-merge `origin/main` (`git show origin/main:<file> | grep -n '<fn>('`) to see which positional slot each already-auto-merged caller (git 3-way merges call sites cleanly even when the signature itself conflicts) assumes for its own new argument, then place each conflicting branch's parameter to match what call sites already assume rather than inventing an order and having to re-edit every call site afterward.
- Merging `origin/main` into a stale `fm/*` PR branch: the only conflicts are usually the committed generated release-bundle artifacts under `relay-stack/web/dl/` (`beeline-linux-x64.tar.gz`, its `.sha256`, `manifest.json`) — `git merge` reports "Cannot merge binary files" plus a text conflict inside `manifest.json`'s hash/byte-count fields, even when every real source file (`apps/body`, `apps/mobile`, `packages/buzz-client`) auto-merges cleanly with no conflict markers. Don't hand-resolve the binary/hash content — pick either side to unblock the commit (content is stale regardless of pick), then regenerate for real with `npm ci && npm run bundle:beeline` and commit the freshly built artifacts in a follow-up commit; the sha256/bytes will differ from both merge parents since they now reflect the merged source tree.

## Body (@beeline/body) — agent session manager

- `apps/body/` — agent body service (see `apps/body/README.md`).
- **Room delivery is WS-push, not polling**: `Body.runRoomPushLoop` (`apps/body/src/body.ts`) holds one authenticated WS subscription per Room (`since`-cursor reconnect, HTTP `pollChannelRequests` only as a one-shot backstop after each (re)subscribe, plus a low-rate maintenance timer for child steering/merge closure). `WorkspaceSupervisor`'s watchdog (`apps/body/src/supervisor.ts`, `DEFAULT_ROOM_WATCHDOG_STALE_MS`) force-recycles a Room whose `lastPollAt` goes stale — so the push loop must keep calling `onRoomPollSuccess` for the *life* of a healthy socket, not just once at subscribe time: it fires on every delivered event and on the maintenance tick whenever `client.socket?.connected`. Getting this wrong (as the original WS-push landing on `main` did) makes a perfectly healthy, silent WS Room get killed and reconnected every `watchdogStaleMs`, which is a self-inflicted request-volume storm, not an ingress problem — see `room-ws-push.live.test.ts` and the liveness-signal test in `body.test.ts`.
- **One mention → at most one corner**: `Body.processChannelRequestEvents` (`apps/body/src/body.ts`) is entered concurrently for the same relay event — the WS-push delivery callback and the one-shot HTTP backstop query above both call it, and `pollRoomMaintenance`'s per-tick invocation can overlap a still-running prior tick. The relay-backed `requestAlreadyOpened` idempotency check has a network round-trip race window, so two concurrent calls can both pass it and both call `openSubchannel`, producing duplicate corners from a single mention. `inFlightRequestIds` (a same-process `Set`, checked-and-set synchronously with no `await` in between, released in a `finally`) closes this: the loop body is claimed per event id before any async work, so a second concurrent call for the identical event id no-ops instead of racing. It is deliberately separate from `processedRequestIds` (only set on success, so a failed attempt still retries on a later poll) — see the "creates exactly one corner" test in `body.test.ts`.
- **Query retry policy**: `packages/buzz-client/src/http.ts`'s `requestQueryEvents` retries 5xx/transport errors (3 attempts, 10s/attempt, linear backoff), mirroring `apps/gate/src/relay.ts`'s `createRelayClient().queryEvents` so every `createBuzzClient()` read (mobile + Body's non-`agentRelay` call sites) tolerates a transient ingress 502/429 instead of failing the turn. `WorkspaceSupervisor.reconcile`'s membership/role reads (`isMember`/`listMembers`/`latestRoleProjection` in `packages/buzz-client/src/channel.ts`) go through this same `queryEvents`, so they inherit the retry for free.
- **Query volume attribution (off by default)**: `http.ts`'s `queryEvents()` carries built-in call-site instrumentation — `getQueryInstrumentation()` / `setQueryInstrumentationEnabled()` / `resetQueryInstrumentation()`, or `BUZZ_QUERY_INSTRUMENT=1` in a Node process like Body. `networkRequests` counts actual `/query` POSTs 1:1 with relay access-log lines; `callSites` groups logical `queryEvents()` calls (cache hits included) by `{kinds, tagKeys, callerLabel}` via a best-effort stack-trace label, so it's always >= `networkRequests` — that gap is the batching/caching win, not a bug. Zero-cost when disabled (single boolean check). Immutable-read caching in the same file (`queryCacheTtl`) also covers a single scoped kind:39000 metadata read once non-empty (same 5-minute TTL as a scoped kind:9007 create), and a genuinely-unscoped scan (no `#h`/`#d` — e.g. `listSubchannels`'s child-discovery scan) gets 10s instead of 500ms.
- **`waitUntilMember`/`waitUntilMemberRole`/`waitUntilNotMember`/`waitUntilRoomArchived` (`packages/buzz-client/src/channel.ts`) are WS-primary, not fixed-cadence pollers**: the shared `waitForRelayProjection` helper subscribes to the relevant 39000/39001/39002 kind(s) scoped to the channel (`#d` and `#h`, matching this file's existing dual-tag read fallback) over `ChannelOpsContext.ws` — an optional live-socket accessor `BuzzClient` wires to its own `this.ws` in `client.ts` — and re-runs the same `isMember`/`getChannelRole`/`getChannelMetadata` check whenever a live event arrives, instead of polling every 300ms. WS is opportunistic only (gated on `ws.connected`, never forces a connect): a `RELAY_PROJECTION_BACKSTOP_POLL_MS` (5s) poll of the same check runs concurrently for the whole wait as the correctness backstop, so an absent/never-authenticated/dropped socket just resolves on the next backstop tick instead of stalling — same technique as `apps/body`'s `waitForWritePermissionDecision` below. A raw hand-built `ChannelOpsContext` with no `ws` field (e.g. `Body.agentClientContext()`) transparently falls back to the original fixed-interval loop, which is why that one Body call site and `apps/gate`'s separate HTTP-only client were deliberately left unwired rather than migrated — see `channel.test.ts`'s `waitUntilMember (WS-driven)` suite for both paths.
- **`query(ctx, filters)` (`packages/buzz-client/src/query.ts`) is the WS-primary read funnel every `queryEvents(ctx.http, ...)` call site in `channel.ts`/`community.ts`/`agent.ts`/`direct-message.ts`/`person-profile.ts`/`repo-room.ts`/`client.ts` now goes through**: opportunistic on `ctx.ws?.().connected` (same gate as `waitForRelayProjection` above — never forces a connect, so cold-start reads stay on HTTP), one-shot NIP-01 REQ→EOSE via `wsQueryEvents` (`ws.ts`) on any hit, HTTP `queryEvents` fallback on literally any WS failure (no WS, not connected, throw, timeout, or a close before EOSE). `enqueueWsQueryEvents` in `query.ts` ports `http.ts`'s same-tick microtask batching (`canPartitionFilter`/`selectQueryEvents`, both exported from `http.ts` for reuse) so concurrent same-tick `query()` calls on the same socket collapse into one multi-filter REQ, split back apart per caller exactly like the HTTP batcher. **Sharp edge proven by a live regression test (`ws.test.ts`)**: `wsQueryEvents` must call its `subscribe()` unsubscribe on every exit path (resolve/timeout/close) or the one-shot REQ's subId is left in `RelayWs.subscriptions` and gets wrongly replayed as a live REQ by a later reconnect's `resubscribeLiveRequests()`. `community.ts`'s `findCommunityInvite` is deliberately NOT wired to this funnel — it takes a bare `http`/`readerPubkey` pair (invite redemption can run before a full `ChannelOpsContext`/socket exists), not a `ctx`, so it stays HTTP-only. `apps/gate`'s independent HTTP-only client is likewise untouched (still no WS support there — see `waitForRelayProjection`'s note above).
- **`Body.isRoomAgentOnline()`'s presence cache cannot reuse `roomSockets`**: `apps/body/src/body.ts`'s `presenceCaches` (keyed by channelId; each entry owns its own `createBuzzClient()` + `agentPresenceSubscribe` subscription, seeded once via a single `agentRelay.queryEvents` read since a fresh subscribe's backfill replay isn't guaranteed to have landed yet) exists because its sole caller, `processChannelRequestEvents`'s agent-exchange online/offline gate, is reachable both from `runRoomPushLoop`'s live socket (where `roomSockets.get(channelId)` is populated) *and* from `pollChannelRequests` called directly with no push loop running at all — every live test exercising this path (`agent-exchange.live.test.ts`) does exactly that, so `roomSockets` is not a reliable source there despite looking like a "straight swap" target. Torn down in `dispose()` alongside `roomSockets`.
- **Reconcile never crash-loops the fleet**: `WorkspaceSupervisor.run` (`apps/body/src/supervisor.ts`) wraps each `reconcile()` call in try/catch — a reconcile rejection (e.g. the relay retry budget above is exhausted) backs off via `reconcileRetryMs` and loops again instead of throwing out of `run()`. Because the failure happens before `reconcile()` ever touches `this.running`, already-active Rooms/corners are untouched by a failed tick. Coverage: `apps/body/src/supervisor.test.ts` → `WorkspaceSupervisor transient relay resilience`.
- **`reconcile()` is wake-driven, not a 5s forever poll**: `WorkspaceSupervisor.run` (`apps/body/src/supervisor.ts`) opens one persistent control-plane WS per daemon subscribed to `{kinds:[KIND_PUT_USER, KIND_REMOVE_USER], '#p':[agent.publicKey]}` (9000/9001, the durable NIP-29 mutation log) and calls `reconcile()` only on startup, on a pushed event, or every `reconcileHeartbeatMs` (default `DEFAULT_RECONCILE_HEARTBEAT_MS` = 60s) as a correctness backstop — not every `pollMs` tick. **This is deliberately 9000/9001, not the 39001/39002 role projections**: a removal republishes the projection *without* the agent's `p` tag, so a `#p`-filtered subscription on the replaceable projection would never notice its own removal; the raw put/remove-user event always carries the affected pubkey. The Room watchdog stays on the tight `pollMs` tick (default 5s) since it only reads already-local `RunningRoom` timestamps — no relay cost either way, so decoupling its cadence from `reconcile()`'s costs nothing. If the control-plane WS never connects (or drops), `run()` logs and falls back to the heartbeat alone; it must not call `.disconnect()` on a client whose `.connect()` never resolved (`supervisor.test.ts`'s existing `mocks.createBuzzClient.mockReturnValue({...})` fixtures reuse one shared mock object across every `createBuzzClient()` call in a test, including this new control socket, so an unconditional `finally`-block disconnect there would silently double the disconnect count and break unrelated assertions). Coverage: `apps/body/src/supervisor.test.ts` → `WorkspaceSupervisor control-plane wake signal`.
- **Write-permission decisions resolve off the Room's own WS first, HTTP poll is the backstop**: `Body.waitForWritePermissionDecision` (`apps/body/src/body.ts`) subscribes on `this.roomSockets.get(tlcChannelId)` (the same live socket `runRoomPushLoop` already holds open) for the `WRITE_PERMISSION_RESPONSE_TAG` kind:9 event, instead of polling `agentRelay.queryEvents` every 500ms. The WS path is opportunistic only — a `WRITE_PERMISSION_BACKSTOP_POLL_MS` (5s) HTTP poll runs concurrently for the whole wait regardless of socket state, so a Room driven without a live socket (e.g. `pollChannelRequests` alone, as `room-conversation.live.test.ts` does) still resolves correctly, just off the backstop instead of instantly.
- **The Room/Corner write boundary is ONLY as strong as the harness's permission callback — and one shipped harness has none.** `apps/body/src/session-sandbox.ts` is the fail-closed policy both handlers use: a Room denies every write/edit/delete/move/execute request outright *regardless of the path it names* (cwd isolation constrains the default directory, not absolute-path reach — the observed breach was a Room session editing `/home/lunchbox/proj-buzzy/...` by absolute path while its cwd was correctly the canonical checkout), and a corner denies a mutating request whose target resolves outside its own worktree (absolute, `..`, or symlink — `physicalPath` realpaths the deepest existing ancestor before comparing, so a symlink inside the worktree cannot launder a write out). Reads are untouched on both surfaces. Per-harness flow, read out of the installed adapters and pinned in `apps/body/src/harness-capabilities.ts`: **codex-acp** routes every command/file change through `session/request_permission` AND advertises a real `read-only` mode backed by Codex's own OS sandbox (strongest); **claude-agent-acp** routes every tool through `canUseTool`→`session/request_permission` but advertises no read-only mode (its modes are `default`/`acceptEdits`/`plan`/`dontAsk`/`auto`), so the daemon callback is the whole boundary; **pi-acp NEVER calls `requestPermission` for a tool** — its only permission requests are pi's own extension-UI `select`/`confirm` events, and read/write/edit/bash are emitted as `tool_call` telemetry *after* pi ran them. pi ships no sandbox (its own `docs/security.md` says so), exposes no permission flag/env/setting, and `pi-acp` hard-codes `pi --mode rpc --no-themes`, so there is nothing to pass at spawn: **a pi-backed Room's read-only rule is advisory, not enforced** (`roomSandboxWarning` logs this at Room provision). ACP's permission response carries only an option id — no reason field, and every adapter hard-codes its own denial text — so the "open a corner instead" steer rides `ROOM_READ_ONLY_STEER` into the Room system prompt and the durable conversation, never the rejection itself. Coverage: `session-sandbox.test.ts`, `harness-capabilities.test.ts`, and `body.test.ts`'s `Room sessions cannot write or execute at all`.
- **Read-only boundary = ACP mode + MCP capability boundary**: Room sessions request a supported read-only ACP mode and mount only Beeline's `buzz-readonly-mcp` (`apps/body/src/read-only-mcp.ts`), whose fixed repository-contained list/read/literal-search/local-history tools expose no shell, raw git args, or mutation. Pure information requests are locked to read-only Room answers and cannot project ALLOW even if the agent asks for a mutating permission. An explicit human open-a-corner command creates the isolated edit corner directly; for non-research work, the first actual mutating ACP request requires a current human member to sign ALLOW. A repo-less normal Room must name an exact `owner/repo` in that signed request and may materialize it only after ALLOW; no target, DENY, or clone failure stays read-only. Edit sessions alone mount `buzz-dev-mcp`. Each human-triggered Room turn includes attributed recent messages from every participant. Non-addressed and agent-authored messages remain context-only except for a signed human-opened peer exchange: `apps/body/src/body.ts` authenticates the opening event and caps the visible exchange at two messages per agent; `apps/body/src/agent-exchange.live.test.ts` is the relay-backed proof. All other agent-to-agent turns remain disabled. Authority: `apps/body/src/body.ts` (`isReadOnlyInformationRequest`, `isChannelWorkIntent`, `replyInRoom`) and `apps/body/src/repository-target.ts`.
- Body drives `buzz-agent` directly over stdio (NOT `buzz-acp`), because `buzz-acp` auto-approves permissions and doesn't expose `session/update` to the relay.
- **`ROOM_AGENT_PROMPT_TIMEOUT_MS` (`apps/body/src/body.ts`) is an idle window, not a hard cap on turn length.** `AcpClient.sessionPrompt` (`apps/body/src/acp.ts`) re-arms the timeout on every `session/update` for that session (message chunk, tool call, anything) via `resetPendingIdleTimeout`; only zero activity for the whole window cancels + force-suspends the session. This covers both the quick read-only Room reply path and the long corner edit-session path since both go through `Body.promptAgent`. A fixed (non-idle) deadline here previously killed every corner task past ~1 minute regardless of progress — see `acp.test.ts`'s "does not time out a turn that keeps streaming activity past the idle window" / "cancels a turn that goes fully idle" tests for the contract.
- **A stalled backend gets an honest early notice and a bounded blind-retry cap, both layered on top of the idle timeout above, not a replacement for it.** `Body.promptAgent` arms a much shorter `ROOM_AGENT_STALL_NOTICE_MS` (20s) timer off `AcpClient.sessionPrompt`'s new `onActivity` hook — the identical per-`session/update` trigger `resetPendingIdleTimeout` already uses — so it only fires on genuine zero-output inactivity and never on a slow-but-active turn; on fire it publishes a one-time `postAgentStallNotice` (`apps/body/src/activity.ts`) as an ordinary visible message, so the stall is visible tens of seconds in, not only after the full `ROOM_AGENT_PROMPT_TIMEOUT_MS`. Separately, the two call sites that retry a failed turn from scratch on a later poll — `processChannelRequestEvents` (Room turns) and `pollMembers` (corner follow-ups) — now read the attempt count `DurableBodyState.failed()` already tracked but nothing previously consulted, and once a genuine ACP idle-timeout (`isAcpPromptStallError`) has recurred past `ROOM_AGENT_STALL_MAX_ATTEMPTS` (3), they stop rethrowing and instead mark the item delivered/processed and publish a clean terminal failure — otherwise a wedged backend was re-driven from a brand-new session on every poll forever. Corner-open (`startAgentTask`) is a one-shot task with no retry loop above it, so it only picks up the stall notice, not the cap. See `body.test.ts`'s "surfaces an honest stall notice…", "never surfaces a stall notice for a turn that keeps producing genuine ACP activity…", and "bounds a stalled backend's blind retry loop…" tests.
- **A message that arrives while a turn is already running is QUEUED, acknowledged, and delivered next — it is never a stall.** `runOnSession`'s per-session FIFO (`SessionScheduler.run`, keyed on the session's channel) *is* the queue: a prompt issued mid-turn runs the moment the active turn releases the session, and both intake loops walk their durable pending list in order, so several steers deliver in order and exactly once. Three defects made a mid-turn steer read as swallowed, all fixed together. (1) `pollMembers` (`apps/body/src/body.ts`) rethrew a failed `sessionSteer` whenever no `runningAgentTasks` entry existed — true for every corner FOLLOW-UP turn, and `sessionSteer` fails as a matter of course since **none of the shipped ACP adapters advertise a steering channel** (`AcpClient.supportsStandardSteering` reads `initialize`'s `_meta.steering.supported`; the goose fallback needs a `_meta.goose.activeRunId` no shipped harness emits, so it rejects after `waitForActiveRun`'s 5s) — leaving the human's message durably `failed` and blindly re-attempted, with nothing said to them; it now falls through to a queued next turn instead. (2) `promptAgent` armed the `ROOM_AGENT_STALL_NOTICE_MS` timer *before* `runOnSession`, so a turn merely waiting in that FIFO published "my coding backend is taking longer than usual to respond" — a claim about a backend it had not yet sent anything to — directly under the message still waiting its turn; the timer is now armed inside the `runOnSession` callback, and additionally deferred (baseline re-sampled, timer re-armed) whenever `Body.inboundMessageSeq` for that channel has moved since the prompt started, so a stall notice can never be the answer to a fresh human message. (3) `pollMembers` had no re-entrancy guard: the maintenance timer fires `pollRoomMaintenance` without awaiting the prior tick, and a steer that waits for the running turn holds the loop long enough for the next tick to re-read the same still-pending event (neither in `processedMemberEventIds` nor durably `delivered` yet) and deliver it twice — `inFlightSubchannelPolls` closes it with the same synchronous claim/release shape as `inFlightRequestIds`. The user-facing receipt is `postSteerQueuedNotice` (`apps/body/src/activity.ts`): a `#t=steer-queued` **body-control** event, deliberately not an `#t=agent-message` (it is a receipt for the human's own input, not the agent speaking, so it must not join the agent's attributed voice run) and never NIP-10-threaded; de-duped to one per channel per active turn via `Body.steerQueuedChannels`. Rooms publish it from `noteRoomInboundMessage`, called OFF `runRoomPushLoop`'s `delivery` chain — that chain serializes handling behind the running turn (which is what makes the message a correctly-ordered next prompt), so an ack raised from inside it could only ever arrive after the answer it was meant to precede. Mobile projects it as an `isSystemNotice` line (`buzz-event-projection.ts`); before that branch existed the event projected to `{}` — durably published, invisible. Coverage: `body.test.ts` → `a message that arrives mid-turn is queued, acknowledged, and delivered`, `activity.test.ts` → `postSteerQueuedNotice`, `chat-event-projection.test.ts`'s queued-steer system-line test.
- **A stall notice must never thread a reply to an event outside the channel it publishes into.** The relay rejects a kind:9 reply whose `e`-tagged parent's `h` tag names a different channel ("parent event belongs to a different channel"), which `postAgentStallNotice` hit on a corner's *opening* turn: `startAgentTask` passes `promptAgent` the Room event that opened the corner as `requestId`, but publishes into the corner's own channel — a genuinely cross-channel pairing 3 of 4 `stream.requestId` uses were not. `promptAgent`'s `stream` param therefore carries `requestId` (channel-agnostic, only ever used as a plain `request` tag) and a separate optional `replyToId` (used only for the stall notice's actual NIP-10 reply, and only when the caller can vouch the referenced event lives in `stream.channelId`) — the three same-channel call sites (`replyToAuthorizedAgentExchange`, `replyInRoom`'s Room turn, `pollMembers`'s corner follow-up) pass both fields equal; `startAgentTask`'s corner-open call passes only `requestId`, so its stall notice — if any — publishes with no reply tag at all rather than a doomed cross-channel one. `postAgentStallNotice` (`apps/body/src/activity.ts`) takes an optional `replyTo` for exactly this reason. Regression: `body.test.ts`'s "never threads a stall notice to an event outside the channel it publishes into".
- **An agent never goes silently unresponsive — two distinct mechanisms cover a "down or errored" daemon, and they must not be conflated.** (1) A fully DOWN daemon can't publish anything, so its silence is explained client-side from detected `#t=agent-presence` staleness, not a published message: `addressedAgentOfflineNotice` (`apps/mobile/sources/buzz/agent-presence.ts`) is checked in `chat/[channelId].tsx`'s `handleSend` against the addressed agent (an explicit @mention in a Room, or the corner's own one agent via `cornerAgentPubkey` when `parentChannelId` is set) and, when stale/offline, inserts a client-only `isSystemNotice` transcript row (`ChatDisplayMessage.isSystemNotice`, `buzz-event-projection.ts`) — never a relay event, never counted in `ledgerSpeakerKey`'s attribution runs. **That notice is gated by `offlineNoticeForSend` (`agent-presence.ts`), not by the raw `addressedAgentOfflineNotice` text builder, and the three gates are each a separate confirmed spam source.** (a) *Addressed by the sent text* — `offlineNoticeAddressee` recomputes the addressee from the exact string handed to the relay (`selectedMentionAgentPubkey` / `mentionedAgentPubkey`, both in `room-participants.ts`), deliberately NOT from the screen's `mentionedAgent`: that variable also folds in `replyTarget?.isAgent`, which addresses an agent the reader never named, and it is the p-tag routing decision, not the notice's. A Corner still addresses its one agent implicitly (`cornerAgentPubkey`). (b) *Presence resolved* — `isAgentPresenceOnlineWithReconnectGrace(undefined, …)` is `false`, so an absent lease read as "offline" and accused a healthy agent during hydration; presence backfill is one independent `step()` of the room-entry fan-out and routinely lands after the cache-seeded first paint, so the notice must wait for `presenceResolved` exactly as the Room's OFFLINE banner does via `isAgentOfflineAfterPresenceResolved`. (c) *Not already said* — the notice restates a standing condition, so `offlineNoticedAtRef` (a `useRef` Map on the chat screen, agent pubkey → last notice) caps it at one per `OFFLINE_NOTICE_REPEAT_WINDOW_MS` (5 min); the row is written into the local cache, so without this every send left another permanent copy in the transcript. Coverage: `agent-presence.test.ts`'s `offlineNoticeForSend` suite plus source assertions in `transcriptSurfaces.test.ts` (`The offline-agent notice`). (2) A daemon that's UP but blocked speaks for itself: `apps/body/src/agent-state-messages.ts` holds `AgentErrorState` (`relay-disconnected` | `harness-auth-missing` | `harness-unavailable` | `repo-unavailable` | `rate-limited`) and its one-place hard-coded `AGENT_ERROR_STATE_MESSAGES` map, plus `classifyAgentErrorState(error)` — a regex classifier over an already-caught error's text, deliberately returning `null` (not guessing) for the existing ACP idle-stall shape (`isAcpPromptStallError`), which keeps its own separate notice path. `Body.notifyAgentErrorStateOnce(channelId, state, replyTo?)`/`clearAgentErrorState(channelId)` (`body.ts`) is the transition-dedup: a `Map<channelId, AgentErrorState>` skips a repeat of the same state and re-notifies only after a successful turn (`processChannelRequestEvents`'s Room-turn success, `pollMembers`'s corner-turn success, or `runRoomPushLoop`'s WS `reconnectBackoff.recovered()`) clears it — never per-poll. `relay-disconnected` fires fire-and-forget from `runRoomPushLoop`'s reconnect-failure catch (never awaited, so a slow best-effort publish can't add to the reconnect backoff delay); `repo-unavailable` closes a previously-confirmed real gap where `WorkspaceSupervisor.startRepositoryRoom`'s `resolveServingRepo` failure only ever `console.error`'d and the Room just silently never started (own dedup `Set` on `WorkspaceSupervisor`, since a `Body` for that channel doesn't exist yet at that point). `harness-auth-missing` vs `harness-unavailable` is classified from `AcpClient`'s exit-rejection text, which now carries a bounded stderr tail (`AcpClient.stderrTail`, `STDERR_TAIL_MAX_CHARS`, `acp.ts`) so a harness's own real "missing API key" stderr line is visible to the classifier instead of just a bare exit code — classification is never invented/guessed, only ever driven by real captured process output or an existing regex-detected error shape (rate-limit patterns reused from the same family as `relayRetryAfterMs`/`isTransientPermissionPollError`).

- **A repository is OPTIONAL at pair time, and `beeline pair` can pin a default model/effort.** `resolvePairRepository` (`apps/body/src/cli.ts`) resolves the binding: `--repo <path>` first (explicit intent, so a missing path or a non-git path is fatal), else the cwd only if it happens to be a git repository, else **none at all** — `tryInspectLocalRepository` (`runtime.ts`) answers `null` rather than throwing, and `pairRepositoryAgent`'s explicit `repo: null` writes a runtime with `rooms: []`, skipping `resolveRoom`/`validate`/`writeRuntimePointer`. That is a fully valid configuration since room-owns-repo: `WorkspaceSupervisor.reconcile` discovers every Room from relay membership and materializes each Room's own repository on demand, so a repo-less agent just serves the Rooms it is invited to. Two consequences worth knowing: a repo-less agent leaves no repo-anchored pointer, so `beeline start` outside any git repository scans the machine-local agent state home (same scope as `--all`) instead of erroring; and every remaining fatal precondition — the `--repo` checks and the S0 identity-reuse guard (`assertAgentIdentityUnpaired`, still re-checked inside `pairRepositoryAgent` for direct callers) — is deliberately raised in `runPairCommand` BEFORE the first interactive question, because the old ordering made the operator answer agent/model/access and only then lose the run. **There is no server-side way to infer an existing Room's bound repository from the pairing code alone** — a pairing code is Workspace-scoped only (`RedeemAgentPairingResult` carries `communityId`, never a Room/repo; confirmed via `packages/buzz-client/src/agent.ts`'s `createAgentPairingCode`/`redeemAgentPairingCode`), and `resolveRepositoryRoom` (`repo-room.ts`) looks Rooms up by `(communityId, repositoryKey)`, a hash of the LOCAL git binding — repo-key-first, not enumerable from communityId alone. - **Clack across the whole CLI, plus per-agent access-scope/auto-response pickers.** `apps/body/src/cli.ts`'s interactive helpers are split into dedicated modules so they're unit-testable without triggering `cli.ts`'s own top-level `main()` (importing `cli.ts` in a test runs the CLI): `clack-support.ts` (`unwrapPrompt` — the one cancel-on-Ctrl-C helper every picker uses; `withSpinner` — runs an action behind a spinner only when `interactiveUi`, otherwise plain, so a script/CI run is byte-identical to no-spinner code), `model-catalog.ts` (`fetchAgentModelCatalog`, extracted so both `cli.ts`'s `validateModelSelection` and the picker can share it), and `agent-settings-prompts.ts` (`pickModelAndEffort`, `pickAccessPolicy`, `pickAutoResponse`, `resolveAccessSettings`). The interactive pair flow's order is agent → model → effort → access → auto-response; `resolveAccessSettings` is the one orchestration point — each flag (`--access`/`--auto-response`) skips its own prompt, the auto-response prompt only ever fires once access has resolved to `creator` (via flag or picker), and neither prompt fires when `interactiveUi` is false (non-TTY never blocks). **At most ONE clack spinner may be live at a time, and never underneath a prompt**: each `clack.spinner()` drives its own ~80ms `setInterval` that erases and rewrites the same stdout line, so two concurrent ones flicker rapidly between their messages and one left running under a `clack.select` fights the prompt for that line. The pair flow's rule is therefore ask-every-question-first, start-the-working-spinner-last — `pairOneAgent` owns the only spinner and starts it after `pickModelAndEffort`/`resolveAccessSettings` return, and `runPairCommand` starts none of its own (it passes `progressLabel`/`progressDone` down instead). The top-level `main().catch` is TTY-aware too: `clack.cancel(message)` interactively, the original `console.error('[body] fatal:', err)` (picocolor-tinted, auto-disables when not a TTY) otherwise — unchanged non-interactive byte shape, verified via `pair-cli.test.ts`'s existing "not a stack trace" assertions plus new `--access`/`--auto-response` non-interactive-never-blocks cases.
- **Testing `beeline start`/`pair` by hand in a treehouse-style worktree of this repo can start a REAL production daemon.** A worktree normally shares its git *common* dir with the primary checkout it was branched from, and runtime pairing state is deliberately stored under `<gitCommonDir>/beeline/agents/<pubkey>/runtime.json` (see `runtime.ts`'s "Runtime root" bullet above) — so `findRuntimeConfigPaths(process.cwd())` run from inside such a worktree can resolve to the *operator's actual paired agent* and `beeline start` will launch its real daemon (connecting to the real relay, under the real agent identity) as a side effect of what looks like a harmless smoke test. Hit this by manually running `beeline start` from an `apps/body` worktree cwd with no `--repo`/isolated `XDG_STATE_HOME` override; caught and killed it (SIGTERM didn't land in time, SIGKILL did) with no lasting effect since no daemon had been running for that agent moments before. Automated tests are unaffected (`pair-cli.test.ts` et al. always `mkdtemp` a fresh git-inited repo *and* pass an isolated `XDG_STATE_HOME`) — the hazard is specific to ad-hoc manual CLI invocations. Always pass an isolated `XDG_STATE_HOME` (and, for `pair`, `--repo` pointing at a throwaway git repo) when hand-testing these commands in any worktree of this repo.

## Grok Mono Hull UI theme

- **Single source of truth**: `/DESIGN.md` (repo root) is the concise, committed unified-language doc — palette, the one shape rule, identity-mark rule, the obsidian-slab rule, the shared Room/Corner ledger, motion primitives, and the two sanctioned color exceptions. Read it before any Buzz visual work; it supersedes prose description here.
- **Design tokens and mark authority**: `apps/mobile/sources/buzz/groknight.ts` owns grayscale semantic roles, the one accent (`accent`/`agentAccent`, `#d7af5f`), the one shape radius (`radius: 3` — most call sites use the literal `3`, matching the codebase's existing convention, rather than referencing the token), and the two sanctioned diff colors (`diffAdded`/`diffRemoved`, `#3FB950`/`#F85149`, also mirrored in `theme.ts`'s legacy `darkTheme.colors.diff` for the background-tint values `ChangeReviewPanel.tsx` still reads from there). `apps/mobile/sources/buzz/brand.json` owns the light mark color; `apps/mobile/sources/buzz/beeline-mark.json` locks the approved continuous-line outline used by in-app and SVG assets. Regenerate platform art and both theme lockups with `apps/mobile/scripts/generate-monochrome-assets.sh`.
- **Design authority**: Grok Mono Hull. No chromatic state or brand color survives in Buzz except the two DESIGN.md exceptions. State is redundant through text, glyph, contrast, geometry, faint deterministic texture, reduced-motion-aware mechanical signals, and haptics. A box (border+fill+radius) only ever wraps something the user must find and act on, or a small number of genuinely distinct non-repeating regions (merge-approval panel, a safety notice) — never a repeating content unit (chat message, list row, avatar); those get whitespace and, for list rows only, a single hairline divider (`MonoHull.tsx`'s exported `hairlineDivider` style — spread it into a row's own style rather than re-declaring `borderBottomWidth`/`borderBottomColor` inline). Shared primitives live in `apps/mobile/sources/components/buzz/MonoHull.tsx`.
- **Rooms and Corners render ONE ledger primitive** — `apps/mobile/sources/components/buzz/Ledger.tsx` (`LedgerEntry` / `LedgerSteer` / `LedgerMarginalia` / `LedgerGhostLine`), fed by one branch in `chat/[channelId].tsx`'s `renderItem` (search `── The ledger`). There is no Room row component and no Corner component. **The transcript's one governing rule is: weight goes down, tone and indentation do all the work.** Everything is `Typography.ledger()` (Plex Mono regular) at 16/26 — one face, one size, one weight — and the entire hierarchy is `groknight.ledgerBright`/`ledgerBody`/`ledgerQuiet`/`ledgerGhost` plus where the block sits. Bold is banned outright, including markdown `**strong**` and headings, which resolve to a luminance step in `MonoMarkdown` instead (`transcriptSurfaces.test.ts` asserts no `'semiBold'` and no `fontWeight` survives in `Ledger.tsx`/`MonoMarkdown.tsx`). Agent output is `ledgerBright` plus a wide low-alpha zero-offset `ledgerGlow` halo; everyone else in the left column is `ledgerBody`; your own turn is `LedgerSteer` — right-inset 86%, `ledgerBody`, **no caption, no signature, no rule** (inset + dimmer *is* the signal). **There are no delimiters anywhere in the transcript** — not between turns, not above a steer, not under a system row; `transcriptSurfaces.test.ts` asserts `Ledger.tsx` contains no `border*Width` and no `hairline` at all. A voice's handle is set *inline*, nested inside the first paragraph's own `Text` via `MonoMarkdown`'s `leadingInline` prop (never a sibling row — that is also the Android blank-flex-Text shape), only on speaker change, and **only in a Room**. **A Corner's zero-handle rule is derived from the surface, not from a roster lookup**: a Corner is one administering agent (`openSubchannel`, `apps/body/src/body.ts`) plus you, so `isCornerAgent = isCorner && !isSelfSteer` and the handle gate is `isCorner` alone. Gating it on `isCorner && isAgent` is a live bug — `isAgent` is `item.isAgentAuthor || item.isAgentActivity || Boolean(agentByPubkey.get(pubkey))`, so a corner message that is neither `#t=agent-message`-tagged nor from a roster-known signer goes false, and the Corner then prints the signer's bare npub as a handle *and* drops the agent's own words from `ledgerBright` to the ordinary grey tier. Everything downstream that means "the agent is speaking" reads `speaksAsAgent`, not `isAgent`. `transcriptSurfaces.test.ts` pins all of it as source assertions; a second transcript implementation is exactly what it exists to prevent.
- **`LedgerSteer`'s block needs an explicit `width`, not shrink-to-fit**: `MonoMarkdown`'s own root is `width: '100%'`, so an `alignSelf: 'flex-end'` parent with auto width has nothing to derive its intrinsic size from and collapses to a few characters wide. That is why `steer` is `width: '86%'` rather than `width: 'auto'`.
- **`marginBottom` on a ledger entry is the gap that appears *above* it on screen.** The transcript `FlatList` is `inverted`, which applies a flip transform to the scroll container *and* to each cell (`@react-native/virtualized-lists`), so an item's own bottom margin lands at its visual top. `continuedSpeakerIds` describes the entry immediately above, so `entryContinued`/`entryOpens` spend the run-vs-stanza distinction on `marginBottom`, not `marginTop`. A child rendered first in layout order likewise appears at the *bottom* of its cell — which is how the retired steer's "hairline rule above" was in fact drawing below it.
- **Ledger metadata hangs in a right gutter, absolutely positioned.** `LedgerMarginalia` is `position: 'absolute'; right: 0` inside the entry, and the entry reserves `paddingRight: LEDGER_MARGINALIA_WIDTH` (36) so prose never runs under it — a flex row would have cost the Android blank-flex-Text bug *and* let the stamp reflow the column. It carries a fixed-width 24h `ledgerStamp` (`buzz/relative-time.ts` — deliberately absolute, not `compactRelativeTime`, because a relative age changes under the reader) and, for a Room speaker, `ledgerFingerprint` (`buzz/member-display.ts`): the six discriminating characters of the npub, because `shortMemberNpub`'s `npub1` prefix plus ellipsis is 3 of 9 characters of pure noise and does not fit the gutter.
- **Tool output is one GHOST line on both surfaces** — `⋯ <what happened> · tap to expand`, dimmest tier (`ledgerGhost`). Two independent sources feed it. (1) `ActivityTimeline` (`components/buzz/ActivityTimeline.tsx`): a single boxless summary row with the agent's mid-run notes (`buildTurnActivity`'s `updates`), commands, inputs, raw output, *and* the objective checklist all behind its disclosure — do not reintroduce the `UPDATE` prose blocks or the bordered `node` square it used to print. - **Diff added/removed coloring is a deliberate, in-code-documented exception to Grok Mono Hull's zero-chroma rule ("captain override"), not a violation to grayscale-ify.** `ChangeReviewPanel.tsx`'s `diffAddedLine`/`diffRemovedLine` and `ActivityTimeline.tsx`'s `diffAdded`/`diffRemoved` (its own inline per-file diff drill-down) both source the same conventional green/red from `darkTheme.colors.diff` (`theme.ts`, Happy's legacy palette) — one shared source, not two independently hand-picked palettes, after a fix that found `ActivityTimeline.tsx` had drifted onto a second, slightly different pair of hex values. Hunk headers and context lines stay on the neutral grayscale palette in both (`groknight.bgHover`/`bgTerminal`, `groknight.textMuted`/`textSecondary`) — only added/removed lines get color; `groknight.ts`'s `danger`/`success` tokens still deliberately share one gray, since that rule has no carve-out for chrome/state elsewhere in the app. **Corner change-review diff (`ChangeReviewPanel.tsx`) does not use the legacy Happy diff renderers** (`components/diff/PierreDiffView.tsx`, `DiffView.tsx`) despite sourcing the same color values — those components render a different diff UI shape entirely, not because of the color exception. The per-file diff sits inside the parent Room's *inverted* transcript `FlatList` (as `ListHeaderComponent`). **Android nested-scroll direction matters**: a vertical `FlatList` nested inside a horizontal `ScrollView` never receives vertical drags on Android regardless of `nestedScrollEnabled` — that shape (shipped in #173) left the diff unscrollable vertically. The working shape is vertical-outer, horizontal-inner: a bounded (~300px) vertical `ScrollView` (`testID="change-review-diff-scroll"`, `nestedScrollEnabled`) wrapping a horizontal `ScrollView` (`nestedScrollEnabled`) wrapping a plain column of `Text` rows — same-axis nesting (vertical diff inside the vertical transcript) hands the gesture off correctly via `nestedScrollEnabled`, cross-axis does not. Rows are plain `Text`, not a virtualized `FlatList` (the previous vertical `FlatList` is exactly the piece that broke), capped at `DIFF_MAX_RENDERED_LINES` (1500) with a truncation footer to bound memory; long lines use `numberOfLines={1}` plus an explicit width estimated from the longest line (`DIFF_CHAR_WIDTH_PX`) rather than wrapping, so the horizontal `ScrollView` has real content to scroll.

Add a new relay read as another independent `step()` in the fan-out; never as a link in a chain. **Two related whole-app re-render traps in `local-cache.ts`**: `updateListSummaries`/`updateListCornerStatus` must stay identity-preserving when nothing actually changed (the room list stays subscribed to this store while a Room covers it, so a rebuilt `channelLists` map re-renders and re-sorts it once per delivered live batch), and any live subscription must coalesce into `cacheLiveSessionEvents` per animation frame — measured 72.6x more array work feeding it one event at a time, before counting the store notification per event.

- **Leaving a corner is a lookup, not a stack pop** (`sources/buzz/corner-navigation.ts`, `chatBackAction`). A Room and a Corner are the *same* Expo Router route (`buzz/chat/[channelId]`), so "the screen underneath" is not reliably the parent Room, and `router.back()` from a corner could walk into another corner: the notification handler uses `router.navigate(..., { dangerouslySingular: true })`, which expo-router's forked StackRouter implements as *filter the matching route out of the middle of the stack and re-append it on top* (`node_modules/expo-router/build/layouts/StackClient.js`) — it reorders rather than pops, so a Room can end up above its own corner. Two more failure modes: the Room-list corner dropdown pushes a corner with the Room never on the stack, and a notification cold start can leave the corner as the only route, where `router.back()` is a silent no-op. `chatBackAction` finds the parent Room *by channel id* and pops exactly to it, opens it in place when it is absent, and falls back to the Room list rather than a no-op. `router.dismissTo` is **not** usable here: with no `getId` on the screen, React Navigation's `POP_TO` matches by route *name*, which the corner itself also has, so it would just rewrite the corner's own params. Every corner push goes through `cornerHref(cornerId, parentId, name?)` so the destination always knows its parent (and its title) on frame one.

## NIP-05 handles (display + verify + Buzz-issued `name@buzzrouter.com`)

- `packages/buzz-client/src/nip05.ts` owns parsing (`parseNip05Identifier`/`normalizeNip05Identifier`) and client-side verification (`verifyNip05`, fetches `https://<domain>/.well-known/nostr.json?name=<local>` and checks it maps back to the expected pubkey) of a `name@domain` identifier. It never throws — every failure mode (bad format, unreachable domain, malformed response, name/pubkey mismatch) resolves to a distinct honest status (`verified`/`mismatch`/`unreachable`/`invalid`), consumed by `apps/mobile/sources/buzz/nip05-verification.ts`'s cache/hook so a label only ever renders the nip05 string once *that viewer's own client* has independently confirmed it — the profile's `nip05` field itself is never trusted at face value.
- `PersonProfile.nip05`/`PersonProfileInput.nip05` (`packages/buzz-client/src/types.ts`, wired in `person-profile.ts`) round-trips through the standard NIP-01 kind:0 `nip05` content key, same optional-field pattern as `avatar`/`handle`.
- `apps/mobile/sources/buzz/member-display.ts`'s `personIdentityLabel` is the one shared display waterfall (verified nip05 → `@handle` → name → truncated npub); it is wired into `MembersScreen.tsx` (central per-render verification map keyed by pubkey) and `settings/identity.tsx` (own-profile editor + verification badge, `useVerifiedNip05Status`). The chat transcript (`chat/[channelId].tsx`) only got the DM peer room-title spot wired (the one self-contained async call site); its many other `shortMemberNpub` call sites (message author, participant list, mention dropdown) were deliberately left on the pre-nip05 fallback chain — wiring those in means either extracting per-row list components to host `useVerifiedNip05Status` or growing this already 2800+ line file's central `personProfileByPubkey`/effect graph, and was scoped out of the initial landing as a fast-follow rather than risked blind.
- **Issuance** (a first-come-first-served, Buzz-minted `name@buzzrouter.com` handle) is owned by `apps/auth` (`@beeline/auth`), the same deployed TS service that already owns the DB and sits behind `buzzrouter.com` via `relay-stack/nginx.conf`'s `/auth/` proxy — not `apps/gate`, which has no persistence layer. `apps/auth/src/protocol.ts`'s `isValidNip05Name` (lowercase alnum + `-`/`_`, 1-30 chars, reserved-name blocklist) gates a flat `beeline_nip05_names` table (`apps/auth/src/store.ts`'s `claimNip05Name`/`resolveNip05Name`; name is the primary key, so FCFS is enforced by the unique constraint itself — no explicit transaction needed). `POST /nip05/claim` (`apps/auth/src/server.ts`) is NIP-98-authenticated (reuses the same `verifyNip98Header` + `claimNip98Event` replay guard as `/auth/oidc/links/:pubkey`) and reachable through the existing `relay.buzzrouter.com` tenant — it needs no new `BUZZY_AUTH_TENANTS_JSON` entry. `GET /.well-known/nostr.json?name=<name>` deliberately bypasses the tenant/Host map entirely (it's a single flat namespace for the whole product, not per-community) and sets `access-control-allow-origin: *` for cross-origin NIP-05 fetches. **Both routes are new top-level paths, not nested under the existing `/auth/` prefix, so they are not yet reachable in production** — `relay-stack/nginx.conf` needs two new proxy locations to `auth:8789` (`/nip05/` and the exact-match `/.well-known/nostr.json`, mirroring the existing `/auth/` block's headers), and the bare apex hostname `buzzrouter.com` (not just `relay.buzzrouter.com`) must reach the same `relay-front` container for the well-known route to resolve at all, since that's the literal domain NIP-05-verifying clients fetch. `packages/buzz-client/src/nip05.ts`'s `claimNip05Handle` is the SDK call site (same `endpoint`/`nip98AuthHeader`/typed-error shape as `oidc-bind.ts`'s `lookupRecovery`), wired into `apps/mobile/.../settings/identity.tsx`'s "BEELINE HANDLE" section, which writes the claimed `<name>@buzzrouter.com` onto the profile via the existing `setGlobalPersonProfile` immediately (same immediate-write pattern as `changeAvatar`, not the deferred "Save identity" button) so the already-shipped verify/display path lights up as soon as the well-known route is wired.

## Direct messages

- SDK authority: `packages/buzz-client/src/direct-message.ts`. A DM is a deterministic, private NIP-29 Room marked `t=buzz-dm`, bound immutably to one Workspace and two sorted participant pubkeys; SDK discovery requires the current projection to contain exactly those two members.
- Workspace membership propagation and Room/agent invite APIs skip or reject DMs, and mobile hides the Room member picker in DM chat. Agent DMs are discovered by `apps/body/src/supervisor.ts` but remain strictly conversational/read-only: they never borrow another Room's repository, request write permission, or open an edit corner.
