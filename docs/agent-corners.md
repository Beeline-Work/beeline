# Corner authority and lifecycle invariants

Paths and commands below are relative to the repository root. Read these invariants before editing this area; named code and tests hold implementation detail.

## Authority and lifecycle

- **The merge gate is one rule, PR/head-scoped and GitHub-authoritative:** `mergeAllowed = live checks green AND a yes on the exact head AND no hold`. `GitHubOperations.prChecksStatus` reads the live PR head's GraphQL `statusCheckRollup`; webhooks only trigger re-reads. Registered unfinished workflow runs, and check suites that already contain check runs, keep a head pending even when every existing context passed; both registration lists are paginated. A suite with zero check runs does not, unless a branch-protection required status check is still missing from the head. The required GitHub App must report that context; the same name from another app stays pending (`pr-checks-status.test.ts`, `github.test.ts`, EMPTY-SUITE-1). Open corners stored as pending are re-read once after a leader starts, so a deploy applies this without waiting for another check event. Check-event wakes with a different head SHA are ignored under the lifecycle lock. Checks-read prose follows the live verdict, including pending registration with green contexts (`pr-checks-status.test.ts`, CHECK-HEAD-1). GitHub workflows that have not registered at all remain invisible to this read. Reopened PR webhooks re-read the live head and its check rollup; a green fact is scoped to head and attempt, so an old head cannot suppress the new review or leave its totals on the card (`github-operations.test.ts`, R1). The yes (`cornerMergeGate`, `apps/server/src/corner-lifecycle.ts`) is a configured reviewer agent's `approve_merge` PASS or a current Workspace owner or admin's yes (`record_merge_yes` or the phone's `approveCornerMerge`, both `recordPersonMergeYes`), or the recorded agent commander's `approve_merge` on a completed zero-check head with no reviewer (`isZeroCheckCommander`, `corner-merge-approval.ts`); all live in `corner_merge_approvals` (one row per corner). The server refuses a PASS from the current implementer or a PR commit author. Author checks read all PR commits from GitHub using Beeline git identities, fail closed on unavailable evidence, and recheck the live head before recording PASS. A new commit cancels the yes; a brief edit does not. A hold is the only veto. Yolo is not a merge condition. `read(facet:checks,address)` returns facts only (`stage`, `checks`, `approved`, `held`, `mergeAllowed`), no prose rule. An archived corner reports `stage: closed` (or `merged` when GitHub confirms it) and `mergeAllowed: false`, even with passing checks and a current yes. `merge_corner` returns `blocked: the corner is closed` for a reachable archived corner, including one without a recorded PR; it does not hide the corner as missing. Coverage: `github-operations.test.ts` and `scripts/prove-closed-corner.mjs` (`CLOSED-1`).
- **Holds follow human provenance and Room access.** `setCornerHold` resolves the human from the active command's `root_source_message_id`, through commander orders from any Room or DM. `corner-holds.ts` requires active parent Room and Workspace membership plus a human identity; copied corner memberships are unnecessary. Only the holder or a person of higher Workspace standing can release a hold. Coverage: `corner-lifecycle.test.ts` (`consent-dm`, `consent-root`, `hold-room`).
- **One merge path: `GitHubOperations.landCorner`.** A reviewer's PASS wakes the implementer, whose `merge_corner` calls it; the phone's yes calls it at once, while the agent's record_merge_yes only records consent and merge_corner lands. It first refuses (`assertCornerBriefAllowsMerge`, `corner-brief.ts`, throwing `CornerBriefMergeRefusedError`) unless the corner's current brief assigns repository work: no brief revision, or `repositoryWork: false`, blocks landing through `merge_corner` and the phone's approve alike; recording a yes alone does not land (an unset `repositoryWork` is allowed; the reviewer's `approve_merge` PASS is still recorded). It then reads the gate live, claims the head (`claimCornerMergeAttempt`, one unresolved attempt per head, no run-state requirement) and squash-merges; a refusal returns the corner to `implement`. When GitHub confirms the same head and branch are unmerged, the refusal releases the claim under the lifecycle lock so a fresh gated attempt can retry; unknown outcomes keep the claim. No instruction may contain `gh pr merge`. A successful merge is confirmed against GitHub and archives the corner through the same idempotent path as the merge webhook. The leader repeats unfinished-claim recovery and merged-PR reconciliation on every background reconciliation interval, including merges outside Beeline and missed webhooks; claim grace and retry deadlines remain database-owned. Recovery never calls the merge API: a provider-confirmed unmerged attempt releases its claim for a fresh explicit gated request. Coverage: `corner-lifecycle.test.ts` and `background-shutdown.test.ts` (`MA-1`).
- **Merge queues preserve the same gate.** `GitHubAppClient.mergePullRequest` reads the base branch's GitHub merge queue and uses `enqueuePullRequest` with `expectedHeadOid` when configured; otherwise it keeps the squash REST path. A queued result is not a merge. `lifecycle.mergeQueue` drives the corner's queued status; background and webhook reconciliation confirm merges through the existing archival path, dequeue on a hold or withdrawn approval, and return removed entries to implementation once with the combined commit's failing check names. Recovery checks for an accepted enqueue before releasing an unresolved claim. Required workflows run on `merge_group`, filtering its head against its base. Enable the main ruleset only after this support is merged and deployed; keep existing required check names, squash merging and build concurrency of at least three. Activation and a real merge-group run remain operational proof, not something a local provider fixture can establish. Coverage: `corner-lifecycle.test.ts` (R1), `github.test.ts`, `workflow-change-filter.test.mjs`.
- **GitHub check-read rate limits are timed waits.** `GitHubHttpError` preserves `retry-after` or a primary reset with zero remaining budget. A documented 403 rate limit uses the existing `checkRefreshRetry` queue, leaves checks pending, and is excluded from Sentry capture; a plain 403 remains an error. REST check-read refusals retain the endpoint, bounded GitHub message, request ID and accepted-permissions header (SENTRY-1D in `github.test.ts` and `pr-checks-status.test.ts`); malformed error bodies retain status and retry classification. Live merge reads still fail closed. Coverage: `github.test.ts`, `github-operations.test.ts` (`R-GH-403`) and the real SDK collector in `sentry.test.ts`.
- **Corner reviewers use `corner_facts.reviewer_agent_id` when set, otherwise the parent Room reviewer and fallbacks** (`rooms.reviewer_agent_id`/`reviewer_fallback_ids`). Any member agent may set the override with `reviewer` on `open_corner` or `revise_corner`; metadata changes need no brief revision. Setting it refuses the implementer and PR commit authors, clears prior agent approvals, and posts one corner line. Room reviewer settings remain person-owned. Reviewer dispatch excludes the current implementer (including from fallback selection); when that leaves no candidate it uses the existing missing/blocked-review handback, without adding an approval gate. An unreachable reviewer reports to the commander (`reachableReviewer`). `approveCornerMerge` (`daemon-service.ts`, refusals as `CornerVerdictRejectedError` in `corner-merge-approval.ts`) accepts a configured reviewer's current-head PASS. Without a reviewer, a completed zero-check head goes to `review` with outcome `no_reviewer` and privately wakes its implementer to ask its commander for a yes using the normal report tool (`noteMissingReviewer`); the server never posts a merge-decision message to a person in this flow. Other green heads wake the implementer to arrange review or report a merge decision to the commander. Every background cycle runs the existing reviewer repair, skipping pending or claimed implementer commands; head-scoped dispatch and report keys keep repeats quiet. Green review gaps use `noteReviewBlocked` (`corner-lifecycle.ts`) to privately wake the implementer and report to the commander; coverage: `corner-lifecycle.test.ts` and `corner-reviewer-list.test.ts`.
- **Review dispatch persists its target** (`agent_commands.review_context`, `corner-lifecycle.ts`): PR number, head, brief revision and normalized check results. A standing reviewer failure (authentication, unavailable model, exhausted allowance) blocks automatic dispatch across heads until its configuration/sign-in snapshot changes or a later turn succeeds; legacy dispatches acquire a snapshot on first observation. The failure reports once to its commander; configured fallbacks retain their order. A completed review suppresses repeats for that target even when its source check event omitted the head; check refresh timestamps and run URLs do not constitute new results. Handbacks describe a completed review and carry its evidence; a needed continuation includes the prior reviewer text. Delivery and claim cancel superseded PR/head/brief targets. GitHub check refresh clears a confirmed closed PR; a newer open-PR webhook can replace it only after live confirmation that the prior PR closed without merging. Coverage: `corner-review-dispatch.test.ts` (`REVIEW-QUIET-1`, `REVIEW-PR-1`) and `github-operations.test.ts` (`REVIEW-PR-1`).
- **`CORNER_LIFECYCLE_CONTRACT` (`corner-lifecycle.ts`) owns corner transitions.** It is TypeScript, never a saved Workspace workflow. Every corner starts `opened` → `implement`; repository work proceeds through `checks` → `review` → `landed`, with `closed` terminal and legacy `ask_human` resumable. `advanceCorner` validates under the run lock, writes the lifecycle card and wakes the reviewer on green, otherwise the implementer. A brief revision wakes only the implementer and changes only legacy `ask_human` state. CI failures, reruns, stalled checks and unconfirmed merges return to the implementer without a human escalation cap (`noteBlockedCornerChecks`, `refreshCheckRollup`; `corner-lifecycle.test.ts`). Failed worker/reviewer wakes report to the commander through `commander.ts`; merge watches replace PR merge subscriptions. Passive opened watches and legacy opened subscriptions do not wake agents; explicit event subscriptions carrying a task prompt still run.
- **A corner has one server-owned state vocabulary:** `working|review|waiting|idle|archived`, from `deriveCornerState` (`apps/server/src/corner-state.ts` over `packages/api-contract/src/corner-state.ts`). A live reviewer turn means Review; a dispatched review turn retains that role until its terminal receipt even if the Room reviewer settings change. Other live turns mean Working. Failed turns end Working immediately; a generation-free bootstrap failure also writes its bounded diagnostic in the corner even for a private order (`STARTUP-FAILURE-1` in `corner-attention.integration.test.ts`). Successful turn gaps retain Working for 30 seconds, including a newly dispatched optimistic turn's pickup gap. Running CI means Review for at most 30 minutes from its head's first pending observation. Unanswered blocked/needs-decision reports (including commanders outside the corner membership), indexed blocking requests, and merge holds also mean Waiting. Explicit waits take precedence over the gap; live turns take precedence over waits. CI failure without another blocker means Idle; workflow stages, schedules and subscriptions alone never establish activity. Clients render the server field verbatim and show only “Waiting”; its source target is a real human request, report or hold message. `inspect_corner.state` uses the same function; lifecycle remains the separate workflow stage.
- **Corner attention uses events and durable single-use deadlines** (`corner-attention.ts`, `corner-attention.integration.test.ts`). Turn/report/hold/CI changes recompute one corner. Startup and listener reconnect recover its turn-gap and stuck-CI deadlines. The span row lock commits each Idle transition and commander report together, once per Idle stretch across instances. Waiting sends no extra wake; subscriptions and schedules never suppress Idle. Commander batching uses `CommanderWakeDeadlines`, recovered once at startup and re-armed on command changes; no repeating corner/attention sweep remains. Helper connection and reconnect re-send stranded pending commands through the existing live trigger. `list_corners(activeOnly: true)` excludes archived corners.
- **Corner goals can be kept current with `rename_corner` and its `objective` field**, including agent-opened corners. Opening cards, lists and inspect reads render the current stored objective; goal/title edits never rewrite System messages or cards. This changes navigation, not the approved brief or work scope. Coverage: `commander.integration.test.ts`.
- **A repository corner starts from a brief authorized by the dispatching message, never its short objective.** Brief = Markdown spec (≤ `CORNER_BRIEF_SPEC_MAX_LENGTH`) + file manifest + optional human message or active private commander order resolved server-side; without either, opening records the opening agent as agent-initiated (`resolveCornerBriefApproval`, `corner-brief.ts`). The objective is navigation only; the approval quote wins conflicts.
- **Any human in the Room can direct an agent and approve brief revisions**, including in a DM shared with the reviser (`corner-brief.ts`). The corner commander (`rooms.created_by`) may revise directly without a citation; `commander-direct` records that agent as approver and cannot be reused by other agents. Human approvals require current membership in the corner's Room or the related message's Room. A newer conflicting human instruction wins; the agent revises the brief citing that message and states in the corner what changed. Opening needs no human approval; private commander-order rules are unchanged. Coverage: `commander.integration.test.ts` (`HUMAN-01`).
- **The brief's spec is the scope source.** `beeline-spec` (`apps/body/src/beeline-skill.ts`) writes intent, stories, criteria, non-goals, risks and references; `beeline-review` grades that outline. The dispatching message authorizes work; no separate spec/mock approval or Room post is required. Planning questions and mocks are agent judgment unless a person requests one before building (`CORNER_AUTHOR_CONTRACT`, `prompt-assembly.ts`). At each turn, the current brief replaces conflicting earlier delivered orders and review targets; prompt assembly labels older revision instructions as historical and binds the active reviewer target to the refreshed brief (`prompt-assembly.ts`; isolated R1/R2 in `corner-review-dispatch.test.ts`).
- **A corner is repository work exactly when its parent Room has a repository** (`rooms.repository_resolution='repository'` / `repository_key`); there is no `lane` column. A repository-backed corner, agent- or person-opened, opens on the code path directly (feature branch, PR, merge gate). A corner in a Room without a repository runs in `rooms/<corner>/scratch` with no token or checkout, never opens a pull request, and ends via human `requestCornerClose` or the `close_corner` of any agent that reaches it.
- **Orders go down; reports go one step up.** `apps/server/src/commander.ts` derives reports from the active order chain; the opening command is fallback provenance. `open_corner` records `openedFromCornerId` explicitly in `corner_facts.opened_from_corner_id` when a corner opens work; existing corners remain NULL without a backfill. Corner orders may name any other agent member at their own parent Room or a reachable corner; unnamed corner orders select the implementer. Peer recruitment consumes the depth-three budget; implementer handoffs retain depth. DMs, agent addresses, other Rooms and ancestor corners stay refused. Revisions and closes retain the parent and ancestor restrictions, following Room parent links and recorded opening provenance. Room/DM behavior and the single-agent requirement for Room orders remain unchanged. `order`/`report` use private `agent_commands` payloads; only human reports enter chat at the original order address. DMs can open, read and command member Rooms. `wake(action:create,trigger:lifecycle,address)` is lifecycle-only; opening auto-watches. Proof: `npm run prove:command-grammar`; coverage: `commander*.integration.test.ts`. Report/lifecycle final prose does not automatically answer the inherited order again. Order outcomes persist across generations; a delivered terminal result discharges that order, while explicit new blockers may still escalate. Identical corner failures collapse before delivery and claim (including batched and legacy pending reports); closed-corner reports are discarded. Explicit reports require `status: done|blocked|failed|needs_decision` matching their text prefix. A corner worker's done requires an opened or merged PR unless its brief says `repositoryWork: false`. It reports the finished assigned step while review or holds may still block merging; ordinary progress stays in the corner. Agent orders outside corners may report done when complete. Each agent owns one `immediate` (default) or `batch:<positive whole minutes>` wake-inbox setting (`set_wake_delivery` / `get_wake_delivery`), stored on `agents.wake_batch_minutes`. It applies to all nonhuman model wakes: system and subscribed events, lifecycle, orders, reports and schedules. Digests remain per Room/corner, preserve the recorded inbox sequence and rendered sources, and commit atomically (`commander-wakes.ts`). Original command rows retain order/report provenance: a combined report follows each distinct orderer’s own return route. Delivery and claim revalidate original workflow attempts; handoffs resolve absorbed attempt provenance and step outputs bind to every absorbed visit. Expiry and sender-scoped Stop rebuild the digest while preserving unaffected work. The quiet-corner gate covers absorbed reviewer commands at delivery and claim. Human messages and helper stop/restart controls stay immediate; human messages do not shorten a digest window. Existing windows keep their deadlines when the setting changes. Empty windows emit nothing; single-use commander wake deadlines release due windows after restart. Reviewer dispatch and merge gates remain immediate by default; only a reviewer who opted into batching delays its review turns. Coverage: `wake-inbox.integration.test.ts`.
- **A corner operates as a Room: membership is the authority, the branch is the shared artifact.** Only `agent_commands` authorize a turn (`agent-command.ts`); creation wakes only the selected implementer; `effective_memberships` derives corner access from current parent Room membership; corners have no `memberships` rows. `corner_person_state` stores explicit preferences lazily; keyed owed items and read marks stay in their existing sparse tables ([migration and reader audit](corner-membership-migration.md)). Each helper syncs to `origin/<feature_branch>` before every turn (`corner-branch-sync.ts`); a rebase conflict realigns to the remote and drops local unpushed commits, never force-pushes. `corner-wake.ts` is the sole wake predicate. `DAEMON_OPERATION_ROUTES` must stay exhaustive.
- **A human tag names a corner's implementer.** `corner_facts.worker_agent_id` (NULL = opener) is set by `routeHumanMessage`; agent tags in final replies and `post(address,text)` instead invite conversation in that place, never change the implementer or create a report obligation; never to the parent's reviewer or fallbacks; worker-scoped reads use `cornerImplementerSql` (`corner-worker.ts`). `owner_agent_id` stays opener and brief author; any current member agent may archive the corner (`archiveCorner` is membership-gated by `DaemonService.access`, like every other corner write); a person-opened corner (`kind='human'`) has no opener agent, so the first agent to take the implementer role becomes its owner (`setCornerImplementer`, `agent-command.ts`).
- **People can lock a corner through its actions menu.** `corner_facts.locked` defaults false; `setCornerLocked` uses the same human permission as `requestCornerClose`. Agents cannot change the lock or close a locked corner. A confirmed merge records its result but keeps locked corners open, preserves assignments and wake sources, and skips branch deletion. People can still close them, including after a merge. Coverage: `corner-lifecycle.test.ts` (`corner lock`) and the server-backed `CornerLockAction.test.tsx`.
- **A phone closes a corner only through `PhoneService.requestCornerClose`** (current member; a human-created corner closes for its creator or a Workspace owner/admin), which applies `closeCornerState` (`corner-close.ts`); never close by chat prose. Every path that archives a corner — a human close, an agent's `close_corner` (`closeCornerState`), and the GitHub merge webhook (`GitHubOperations.mergeCorner`) — cancels its pending/claimed `agent_commands` and `working` turns in the same transaction via `cancelCornerAgentCommands`, so landing a corner never leaves a stale assignment behind. Closing and landing also abandon live saved workflows and remove their timers via `abandonCornerWorkflowRuns` (`workflow-runs.ts`; `corner-lifecycle.test.ts`). Closing enqueues the recorded branch and repository in `corner_branch_deletions` in the archival transaction (`corner-branch-cleanup.ts`); merge archival does the same. The background leader deletes after commit, rechecking GitHub's live default/protection, open head/base PRs and all unarchived corners. Reserved and release branches stay. Failed attempts back off for up to eight attempts; missing refs (404/422) succeed. No historical cleanup is seeded. Explicit close checks authority, attempts to close the recorded unmerged PR through `GitHubOperations.closeCornerPullRequest` outside the archival transaction, then rechecks authority under the lifecycle lock and archives. GitHub failures are logged and never prevent archival (`closeCornerPullRequestBestEffort`, `corner-close.ts`); merge holds remain unchanged. Any agent that reaches a repository corner closes its PR without merging through `close_corner_pr(address)` (`GitHubOperations.closeCornerPullRequest`): the branch stays and `lifecycle.pr` is cleared so the merge gate reads no PR. This also repairs legacy archived corners without reopening them or waking work; merged corners are excluded.
- **An agent reaches a corner when it is a current member of its parent Room** (`DaemonService.reach`). Reach authorizes closing, renaming, ordering, revising the brief, reading (status, transcript, brief, checks, PR discussion, members) and corner posting via `post`. Room posting requires current membership in the addressed Room; omitted address uses the active corner. Any reachable member agent may merge through the same live merge gate. Check reach on the target `cornerId`, never only on the turn's `roomId`. A Room and its corners always read each other's history (`AUTHORIZED_ROOMS_CTE`).
