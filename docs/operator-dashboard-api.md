# Private operator dashboard API (v1)

`GET /v1/admin/dashboard?platforms=ios,android,macos,windows,linux` is a server-to-server, read-only totals API. Omit `platforms` for all five. The caller sends `Authorization: Bearer <BEELINE_DASHBOARD_SECRET>`; the secret belongs only in the Cloudflare same-origin proxy, never in browser JavaScript. An unset or wrong secret returns `403`. This route emits no CORS permission. Unknown, duplicate, empty or repeated query parameters return `400`. No request body or message text is read into the result. Every count below is rounded **down to a multiple of five**; cells smaller than five are `null`. Do not use this API for individual lookup.

Response envelope: `{ "schemaVersion": 1, "measuredAt": ISO8601, "platforms": string[], "usage": ..., "health": ..., "ops": ... }`. Each section has `state: "measured" | "unmeasured" | "unavailable"` and `measuredAt` (or `null` after a failed read). Reads fail independently; one unavailable section does not remove the others. No exception detail or stored text is returned.

## Usage

`usage.people` and `usage.agents` are arrays with six objects ordered `signup`, `workspace`, `paired`, `reply`, `corner`, `merged`. Each object has `{ stage, count, previousStage, denominator, medianTimeToStepMs, timeToStepState }`. `count` is a rounded unique person or agent count; `denominator` is the rounded previous stage count. Stage predicates are cumulative. People enter the cohort at identity creation; agents enter through their owner. Workspace means current top-level membership; paired means a non-revoked daemon token; reply means a surviving agent message; corner means a commissioned/opened corner; merged means its corner lifecycle contains a merged PR timestamp. For each transition the dashboard computes the median elapsed time between the two actual step timestamps, only when at least five valid ordered pairs exist. A missing or reversed timestamp leaves that pair out; a stage with fewer than five pairs remains `unmeasured`.

`usage.platformCoverage` lists the static mobile labels and desktop labels observed for at least five distinct people. The all-platform request, including an explicit list of all five labels, includes every human and every owned agent even when some people have no platform observation. A strict subset includes people with a matching push registration or `reportRunningUpdate` receipt and their agents. The same person may appear in more than one platform subset; subsets must not be summed. Phone and Tauri desktop clients now send a platform-only update receipt through the authenticated monolith operation; historical receipts can lack it. A strict subset requesting a desktop platform with fewer than five observed people makes `usage.state="unmeasured"`, `people=null`, and `agents=null`, with `reason="desktop_platform_not_recorded"`; updated desktop clients must report before that cohort becomes measured. This is not a zero-person result.

## Health

`health.server` is green after a successful DB round trip and red if that read fails. `health.slow` uses completed app queries and pool checkouts in a process-local ten-minute window. It exposes query p95/p99, checkout wait p95/p99, observed waiter p95/p99, current waiters, and the oldest current query for diagnosis; current waiters and the oldest query do not alone set a red verdict. At least 20 queries and checkouts are required. Query p95 over five seconds or checkout wait p95 over 100 ms is red. The bounded query name is `database.query`.

`health.functions` contains ten-minute latency and failure observations for five named operations. `page_load` is phone navigation to the first painted Room frame or a failed Room read; `message_delivery` is a subscribed phone's paint acknowledgement of a committed message (failed message writes also count); `corner_open` is a completed human or agent corner-create request; `push_delivery` is the settled push claim's claimed-to-completed interval; `attachment_upload` is a finished phone media or daemon upload request. These are events, never timer-generated samples. The first, second, third, and fifth observations carry no identity or content in `operator_function_events`; push claims are read from their existing ledger. Each function includes sample count and failures rounded to five-event buckets, p95/p99 after five samples, and a failure rate after 20 samples. A five-second p95 among at least 20 samples is slow red; a failure rate of at least 5% among at least 20 samples is failing red. `health.failing` also reads the last 24 hours of `agent_turns` and retains its existing 20-turn minimum and 5% threshold. Both verdicts are `unmeasured` when required coverage is missing and no measured function is red; green requires measured coverage for every named function. Data is initially unmeasured after deploy until real events arrive.

## Ops

`ops.release` has `latestVersion`, `activeWindowDays: 30`, `activePhones`, `latestPhones`, `unknownBuildPhones`, `latestShare`, `storeUpdateOnlyPhones`, `storeUpdateState`. The unit is a unique `(identity, deviceId)` iOS/Android receipt active in 30 days; desktop receipts are excluded. `latestShare` is null when any active receipt lacks a release version, when the release version is unknown, or when either side of the split is under five. The latest mobile version defaults to `BEELINE_RELEASE_VERSION` and can be overridden by `BEELINE_DASHBOARD_LATEST_MOBILE_RELEASE`. `storeUpdateOnlyPhones` uses the active receipt's platform/runtime against both `BEELINE_DASHBOARD_MIN_RUNTIME_IOS` and `BEELINE_DASHBOARD_MIN_RUNTIME_ANDROID`; without both thresholds and complete runtime observations it is null with `storeUpdateState="unmeasured"`. The release pipeline must supply the current minimum OTA-compatible runtimes. A missing threshold is not zero.

`ops.memory.repeatCorrections` has `windowDays: 30`, bucketed `current` and `prior` counts, and `trend` (fractional change, null when either bucket is under five). A repeat is a correction of the same scoped lesson within the preceding 30 days; the windows are adjacent. `ops.memory.tokenShare` has `windowDays: 30`, `share`, `state`, bucketed `sampledServes` and `missingServes`. The share attributes institutional block bytes proportionally to actual prompt input tokens, over live served prompts. If _any_ prompt lacks actual token count or prompt byte length, the share is null and `state="unmeasured"`; Codex's currently null token reports are never treated as zero. Output tokens are not recorded for this ratio, so this is an **input-token share**, not a claim about all model spend.
