# Project agent memory

Committed home for project-intrinsic agent knowledge: rule + authoritative file + coverage pointer. The named code and tests hold the detail; do not re-expand prose here. UI rules live in [DESIGN.md](DESIGN.md).

**Naming.** The product is **Beeline**; write "Beeline" in prose, docs, and UI copy. `buzz`/`Buzz` survives only as a legacy code identifier (`apps/mobile/sources/buzz/`, `components/buzz/`, `@beeline/buzz-client`, `BuzzClient`, `BuzzRigTransport`, `theme.buzz`, `BUZZY_RELAY_*`, the `buzz-dm`/`buzz-community-invite` wire tags). Quote those verbatim; never call the app Buzz or Buzzy. Wire tags must not be renamed.

## Core invariants (read first)

- **A bad read fails alone, and a bad release contains itself.** `apps/server/src/database.ts` keeps bounded app/enrichment/health pools apart from long-running migration pools; `PhoneService` projects core Room data before degradable enrichment; boot asserts only `beeline_schema_state` (written last by migration). `.github/actions/server-leg/action.yml` canaries one of two Fly Machines for five minutes, then updates the peer or restores the previous image; `server-rollback.yml` is manual recovery.
- **ACP scopes bind to the helper's lifetime without ordering after its readiness.** `AcpResourceScope` (`apps/body/src/acp-resource-scope.ts`) keeps `BindsTo` without `After`: the notify helper can initialize ACP before READY, so ordering its scope after readiness can deadlock startup (`acp-resource-scope.startup.test.ts`).
- **The merge gate is one rule, PR/head-scoped and GitHub-authoritative:** `mergeAllowed = live checks green AND a yes on the exact head AND no hold`. `GitHubOperations.prChecksStatus` reads the live PR head's GraphQL `statusCheckRollup`; webhooks only trigger re-reads. The yes (`cornerMergeGate`, `apps/server/src/corner-lifecycle.ts`) is a configured reviewer agent's `approve_merge` PASS or a current Workspace owner or admin's yes (`order_corner_merge` or the phone's `approveCornerMerge`, both `recordPersonMergeYes`); both live in `corner_merge_approvals` (one row per corner). The server does not referee whether a reviewer is the corner's opener or author — that is prompt discipline (`corner.implementer`/`cornerReviewerInstruction`, `apps/body/src/prompt-assembly.ts`), not a gate; a builder made reviewer could approve its own code if it ignored the prompt. A new commit cancels the yes; a brief edit does not. A hold is the only veto. Yolo is not a merge condition. `pr_checks_status` returns facts only (`stage`, `checks`, `approved`, `held`, `mergeAllowed`), no prose rule.
- **One merge path: `GitHubOperations.landCorner`.** A reviewer's PASS wakes the implementer, whose `merge_corner` calls it; a person's yes calls it at once. It first refuses (`assertCornerBriefAllowsMerge`, `corner-brief.ts`, throwing `CornerBriefMergeRefusedError`) unless the corner's current brief assigns repository work: no brief revision, or `repositoryWork: false`, blocks the land for `merge_corner`, `order_corner_merge` and the phone's approve alike (an unset `repositoryWork` is allowed; the reviewer's `approve_merge` PASS is still recorded). It then reads the gate live, claims the head (`claimCornerMergeAttempt`, one attempt per head, no run-state requirement) and squash-merges; a refusal returns the corner to `implement`. No instruction may contain `gh pr merge`. The merge webhook archives the corner and reaps its worktree.
- **Corner reviewers come only from the parent Room** (`rooms.reviewer_agent_id`/`reviewer_fallback_ids`). A non-member reviewer posts a note (`reachableReviewer`). `approveCornerMerge` (`daemon-service.ts`, refusals as `CornerVerdictRejectedError` in `corner-merge-approval.ts`) accepts any current-head PASS from a configured reviewer — the server does not check whether that reviewer opened the corner or wrote its code, only prompt discipline does; When no reviewer is configured, green checks go to `review` with outcome `no_reviewer` and wake the implementer to arrange review or explicitly ask for a merge decision.
- **`CORNER_LIFECYCLE_CONTRACT` (`corner-lifecycle.ts`) is the one authority for corner transitions.** It is plain TypeScript, never stored as a Workspace workflow; workflow pages show only saved workflows, never corner lifecycle cards. Every corner opens `opened` -> `implement`; there is no lane and no upgrade. States: `implement` (building) -> `checks` (checking) -> `review` (waiting for a yes) -> `landed`, plus `closed` (legacy `ask_human` cards can resume); `pr_checks_status.stage` reports the same from live facts. Every state change goes through `advanceCorner(db, cornerId, event)` under the run lock: it validates the edge, writes a `@system` card, and issues the only lifecycle wake (reviewer on green, implementer otherwise). A brief revision wakes only the implementer and never moves the run (except `ask_human` → `implement`). CI failures, completed reruns, stalled checks and unconfirmed merges return to the implementer without a human escalation cap (`noteBlockedCornerChecks`, `refreshCheckRollup`; `corner-lifecycle.test.ts`). People are pulled in only for an explicit agent decision/approval or a failed agent wake. Landing wakes no one in the parent Room; agents with follow-up work subscribe to `merged`.
- **A corner has one server-owned state vocabulary:** `working|waiting|idle|review|archived`, from `deriveCornerState` (`apps/server/src/corner-state.ts` over `packages/api-contract/src/corner-state.ts`). `waiting` needs an unexpired `corner_owed` row for a human member; triggers maintain `corner_owed` in the writer's transaction and readers use `cornerOwedLookupSql`, never a per-read `messages` scan. Clients render `CornerListItem.state` verbatim.
- **A repository corner starts from a brief authorized by the dispatching message, never its short objective.** Brief = Markdown spec (≤ `CORNER_BRIEF_SPEC_MAX_LENGTH`) + file manifest + one approving human message resolved server-side (`resolveCornerBriefApproval`, `corner-brief.ts`). The objective is navigation only; the approval quote wins conflicts.
- **The brief's spec is the scope source.** `beeline-spec` (`apps/body/src/beeline-skill.ts`) writes intent, stories, criteria, non-goals, risks and references; `beeline-review` grades that outline. The dispatching message authorizes work; no separate spec/mock approval or Room post is required. Planning questions and mocks are agent judgment unless a person requests one before building (`CORNER_AUTHOR_CONTRACT`, `prompt-assembly.ts`).
- **A corner is repository work exactly when its parent Room has a repository** (`rooms.repository_resolution='repository'` / `repository_key`); there is no `lane` column. A repository-backed corner, agent- or person-opened, opens on the code path directly (feature branch, PR, merge gate). A corner in a Room without a repository runs in `rooms/<corner>/scratch` with no token or checkout, never opens a pull request, and ends via human `requestCornerClose` or the `close_corner` of any agent that reaches it.
- **A corner operates as a Room: membership is the authority, the branch is the shared artifact.** Only `agent_commands` authorize a turn (`agent-command.ts`); creation wakes only the opener; `membership-join.ts` copies Room joins without resurrecting removed members. Each helper syncs to `origin/<feature_branch>` before every turn (`corner-branch-sync.ts`); a rebase conflict realigns to the remote and drops local unpushed commits, never force-pushes. `corner-wake.ts` is the sole wake predicate. `DAEMON_OPERATION_ROUTES` must stay exhaustive.
- **A human tag names a corner's implementer.** `corner_facts.worker_agent_id` (NULL = opener) is set by `routeHumanMessage`, and by `routeAgentResult` when an agent's turn, requested by a person who is a corner member, tags another agent (a hand-over the person asked for); never to the parent's reviewer or fallbacks; worker-scoped reads use `cornerImplementerSql` (`corner-worker.ts`). `owner_agent_id` stays opener and brief author; any current member agent may archive the corner (`archiveCorner` is membership-gated by `DaemonService.access`, like every other corner write); a person-opened corner (`kind='human'`) has no opener agent, so the first agent to take the implementer role becomes its owner (`setCornerImplementer`, `agent-command.ts`).
- **A phone closes a corner only through `PhoneService.requestCornerClose`** (current member; a human-created corner closes for its creator or a Workspace owner/admin), which applies `closeCornerState` (`corner-close.ts`); never close by chat prose. Every path that archives a corner — a human close, an agent's `close_corner` (`closeCornerState`), and the GitHub merge webhook (`GitHubOperations.mergeCorner`) — cancels its pending/claimed `agent_commands` and `working` turns in the same transaction via `cancelCornerAgentCommands`, so landing a corner never leaves a stale assignment behind. Any agent that reaches a repository corner closes its PR without merging through `close_pull_request` (`GitHubOperations.closeCornerPullRequest`): the branch stays, the corner stays open, and `lifecycle.pr` is cleared so the merge gate reads no PR.
- **An agent reaches a corner when it is a current member of the corner or of its parent Room** (`DaemonService.reach`). Reach authorizes closing, renaming, steering, revising the brief, reading (status, transcript, brief, checks, PR discussion, members) and `post_to_corner`. Check reach on the target `cornerId`, never only on the turn's `roomId`. A Room and its corners always read each other's history (`AUTHORIZED_ROOMS_CTE`).
- **An exact tagged lifecycle command is server control, never a model prompt.** `routeHumanMessage` treats a whole message `@agent restart|status|stop|retry|debug|help|login` (or `@agent /restart`, `/login`) as control. Status/help follow access policy; debug/restart need the agent owner or a Room manager; stop/retry also allow the requester; login is owner-only. Restarts coalesce per agent in `agent_commands` until `ConnectionPresence` sees a new lifecycle id.
- **Composer commands keep two authorities separate.** `BEELINE_SLASH_COMMANDS` (`packages/buzz-client/src/slash-command.ts`) owns Beeline actions, filtered by live permissions; an agent's ACP `available_commands_update` snapshot (`agentCommandCatalogPublisher` → `agents.commands`) owns its commands. Picking one keeps the `@agent` mention, so routing and access policy still gate it. Owner-only `/fast-mode` (`fastModeCommandState`) calls `updateAgentModelSelection`.
- **Agent Grants have one vocabulary and one authority axis.** `packages/api-contract/src/agent-grants.ts` owns kinds, statuses, the command-rule parser (`parseCommandGrantTarget`; `commandGrantMatches` is an argv prefix) and the decision line; policy follows `docs/approval-matrix.md`; `surface-capabilities.ts` lets a corner dominate a Room. Yolo defaults on (`backfillYoloModeDefault`) and is forced off in public Workspaces; credential-file argv and unread scripts (>4096 B/120 lines) still stop. Human profiles show the grant ledger (`readWorkspaceMembers`, `MemberGrantRow.tsx`, wording in `grantProvenanceLine`); an active `shared_asset` row alone offers revocation there. The agent settings page shows none.
- **Removing an agent retires it; its work survives.** `PhoneService.removeAgent` → `retireAgentFromWorkspace` (`agent-retirement.ts`) ends memberships, revokes all its daemon tokens and grants, hides the identity, clears configuration, and deletes schedules; corners, turns and messages stay. A helper retires only on 403 `agent_removed` (`isAgentRemovedError`), never on transport errors, 5xx, or plain 401.
- **`deleteWorkspace` is owner-only and a real `DELETE`** relying on FK cascades. It checks existence before ownership (idempotent retries), writes `workspace_deletions` + per-member notices, revokes tokens only for agents with no other membership, and leaves media to `media-ttl.ts`. Every FK column into `messages`/`rooms`/`workspaces` must carry a leading-column index — an unindexed one forces Postgres to sequentially scan that whole child table per deleted row during the cascade, which is slow enough on a real table to blow the app pool's `APP_STATEMENT_TIMEOUT_MS` and leave the client's delete request hanging with no answer. Guarded by the `cascade-path foreign keys stay indexed` test in `database.test.ts`; `messages` itself is busy enough that a new index there goes through `createIndexConcurrently` in `migrate()`, not inline schema SQL.
- **Leaving a Room.** Any human can leave a top-level Room (`PhoneService.leaveRoom`, under the Room row lock); the last Workspace owner/admin in it deletes it for everyone and must pass `confirmDelete: true`. `leaveDeletesRoom` drives `buzz/room-leave.ts`. Swiping a DM writes a per-viewer `chat_dismissals` row hidden only until newer inbound activity.
- **Institutional memory has two scopes and stays optional to every turn.** On by default; only an explicit `false` on `BEELINE_INSTITUTIONAL_MEMORY_ENABLED`/`_SHADOW_ENABLED` disables it. No background review: the answering agent maintains it with `search_memory`/`save_memory`/`update_memory`/`delete_memory`/`report_memory_used` (versioned, active-command-bound). Snapshot and search are hybrid (word overlap + vector recall over memory items and `workspace_skills`). Each turn's snapshot is capped at `INSTITUTIONAL_CONTEXT_HARD_MAX_BYTES` (1 KB) and fetched alongside harness activation (`institutional-context.ts`); a miss says so. Only agent-saved Workspace facts expire (`institutional-curator.ts`, default 90 days). Procedures are staled by their code anchor's blob changing (`institutional-skill-anchors.ts`, fail-open). Contracts: `packages/api-contract/src/institutional-memory.ts`.
- **A workflow is a `workspace_skills` row with `kind='workflow'`, with no run-state tables.** `readWorkflowContract` (`packages/api-contract/src/workflow-contracts.ts`) validates it; `apps/server/src/workflow-runs.ts` is the whole runtime. The start card's id is the run id, state is the latest `workflow-handoff` card, and the run's status (`live`/`done`/`failed`/`abandoned`) is saved once on the start card as `runStatus` by `saveRunStatus` whenever the run moves; every reader and live check uses it (`workflowRunIsLiveSql`, indexed by `messages_workflow_run_live_idx`), and `migrateData()` re-arms missing timers of live runs on every release; wakes go through `systemLine`, saves use `applySkillRevision` and (since PR #2083) must carry a `summary` and each state's `does` (`validateSavedWorkflow`); `backfillWorkflowSkillDescriptions` fills those into every pre-#2083 version so a pinned legacy run keeps reading cleanly, and `describedLegacyWorkflowContract` is its pure half for describing one before a fresh save. A wake names its run and attempt (`workflowWakeDetail`, `agent-command.ts`); a step's attempt is the `seq` of the card that dispatched it, and every run writer (handoff, `blocked`, step expiry, gate answer/Skip/default, deadline, cancel, reassign) goes through `openRun` → `enterState`/`moveRole`/`closeRun` under the run lock, so a stale or repeated call returns `alreadyAdvanced` and cancels nothing twice. `startWorkflow` allows one live run per workflow per Room under a `workflow-start:` lock; a schedule tick that finds one posts a skip line. New saves need `timeoutSeconds` on every agent step and `timeoutSeconds`+`default` on every gate (`validateSavedWorkflow`), and a turn that answered the current attempt and ended without the run moving counts as `blocked` (`failOverUnansweredTurn`, from the terminal `complete` receipt). Step timeouts, gate defaults and run deadlines (default 24 h) are `agent_schedules` rows with `workflow_run` set, owned by the system identity and fired by `fireWorkflowTimer`. Roles and corner reviewers may be ordered agent lists; `agent-health.ts` picks the first healthy current member, failover walks the list forward once per state visit (`tried` on the card; exhausted steps without a `timeout` outcome retry the full list after the normal lease), and an exhausted list names each agent's reason and wakes an agent starter. A gate always posts its choice card; only a person's answer, Skip or the gate default leaves it, and defaults notice the run owner (`ownerId` on the start card). A gate's open choice closes the moment its run leaves that gate or ends (`closeRunChoices`, `room-choice.ts`), reused by `postRoomChoice`'s lazy sweep and `closeStaleWorkflowGateChoices` (`migrateData()`). `assign_workflow_role` rebinds any role, list-bound or not. Inside a corner, every workflow-run MCP tool (`start_workflow`/`get_workflow_run`/`handoff`/`cancel_workflow_run`/`assign_workflow_role`) must resolve the Room id through `agentScheduleRoomId()` (corner id first), never the bare `BEELINE_DAEMON_ROOM_ID` parent — a run's cards live under the corner's own `room_id`. Proof: `npm run prove:workflow-run`; corner case end-to-end through the real MCP tool handlers: `apps/body/src/workflow-corner-e2e.integration.test.ts`.
- **Wallet transaction notices belong to the owner's @System DM.** `wallet-notices.ts` owns one notice per owner/chain/transaction and monotonic provider settlement; `wallet-webhooks.ts` verifies CDP push. Plain system rows qualify for DM push. Coverage/activation and external-chain/venue limits: `docs/wallet-tools.md`; regressions: `wallet.integration.test.ts`, `push-sensitivity.test.ts`. Balance deltas are history enrichment, never a substitute for push.
- **Beeline feedback has one store and one sweep.** Agents file friction with `report_feedback` (10/agent/UTC day, 24h dedupe, never fails the turn); people use a bare `@system` tag or Report issue. Store/notify: `apps/server/src/feedback.ts`. Triage is the seeded `feedback-triage` workflow (`docs/workflows/feedback-triage.json`). The only closing write is `notify_feedback_fixed`, which needs a merged PR in `BEELINE_FEEDBACK_REPOSITORY`.
- **The GitHub star card stars only on the person's own tap and never gates anything** (`github-star-prompt.ts`, `StarPromptCard.tsx`; due at the 3rd/30th/300th agent reply, held mid-conversation or after a failure).
- **Corner Apps are installed data, never downloaded code.** `packages/api-contract/src/corner-apps.ts` owns the vocabulary and v1 permission manifest; `corner_app_installations` is the Workspace library; `corner_app_bindings` binds at most one app per corner via the manual `+` flow.
- **An agent's animal is its face, name and soul, assigned together by the server.** `assignSeededAgentIdentity` (`packages/api-contract/src/faces.ts`) gives the first animal no current Workspace member wears, else `defaultFaceForSeed` + a roman numeral, inside `PhoneService.claimAgentConnectPairing` under `workspaces … FOR UPDATE`. `confirmSeededName` offers a rename for 15 minutes. Face ids are pinned in two copies (`faces.ts`, `apps/mobile/sources/buzz/faces/index.ts`) so no screen needs a fresh SDK `dist/`. Handles: `availableAgentHandle`; human handles win collisions (`workspace-handles.ts`).
- **A model picker is a live account verdict.** `apps/body/src/model-catalog.ts` offers only models proved through the startup-validation setter; the phone renders `agents.model_catalog` + `selected_*` verbatim (`model-catalog-sync.ts`). A failing persisted selection becomes `agents.model_unavailable` and the `wrong-model` silence line. Transient 429/529/timeout/auth-shaped failures are hiccups, never a model verdict (`isTransientProviderText`, `isAuthShapedFault`); a vanished id falls back within its family (`resolveModelFamilyFallback`).
- **A non-agent system author is a hidden `kind='human'` identity** with a fixed id (`SYSTEM_IDENTITY_ID`, `REVIEW_IDENTITY_ID`, `SCHEDULE_SCHEDULER_ID`), never a new `identities.kind`. `system-line.ts` sends Workspace facts to each member's read-only `@system` DM (`assertRoomIsWritable`).
- **Deleted features stay deleted.** Chat-sentence tombstones: `isRetiredAgentNotice` (`packages/buzz-client/src/retired-agent-notices.ts`, exact set + bounded structural regexes), applied in push-gateway `projectEvent`, `room-list-row.ts`, and the mobile cache scrub. Photo overrides stay off (`PHOTO_OVERRIDES_ENABLED=false`). Repoint here; never restore the feature.
- **Dead code is baseline-gated.** After building workspace `dist/`, `npm run dead-code` runs Knip against `knip-baseline.json`; only run `dead-code:baseline` for an intentional API addition. Expo Router entries are declared in `knip.jsonc`.
- **Hand-testing `beeline start`/`pair` in a worktree can start a REAL production daemon** (runtime pointers live in the shared git common dir; `start-command.ts` converges the machine helper). Always set an isolated `XDG_STATE_HOME`, and `--repo` a throwaway repo for `pair`.

## Relay and client protocol

- **kind:30078 reads filter by `#d`, never `#h`** (a `#h` filter matches nothing). `agentPresenceKey` (`packages/buzz-client/src/agent-presence.ts`) builds presence keys. Test with `matchesFilterRelayFaithfully`/`deliverRelayFaithfully` (`client.test.ts`); generic stubs miss this.
- **Production relays may answer a multi-value `#h`/`#d` filter for one key only**, so every `packages/buzz-client` fan-out sends one single-key filter per key inside one batched query.
- **Local stack vs production.** `relay-stack/compose.yml` (http `127.0.0.1:3010`, the `relay-config.ts` default) has a credential-free materializer and cannot serve GitHub-backed corners (`githubHttpsRemote` maps `git://` remotes to GitHub HTTPS), so pair repo-less Rooms there. `BuzzClient` treats loopback/`10.0.2.2` relays as open. `@beeline/gate` reads `BUZZY_RELAY_*` at import. Gate live tests: `npm run stack:up`, then `cd apps/gate && npm run test:live`.
- **The phone has one write transport:** the authenticated monolith API. `BuzzRigTransport` is an alias of `MonolithRigTransport`; the `@beeline/buzz-client` HTTP bridge and `apps/gate` serve only the isolated relay stack and scripts.
- **A stalled request moves to a fresh connection.** RN Android's OkHttp (no read timeout) multiplexes onto a silently dead pooled HTTP/2 connection, and an abort never evicts it. `MonolithSession` repeats a repeatable request (`phoneOperationRequestOptions`) on `beeline-server.fly.dev` after `MONOLITH_STALL_PROBE_MS`; its certificate is disjoint, so OkHttp cannot coalesce onto the dead connection.
- **Community model.** `community.ts` maps NIP-29 (kind:9007 self-referencing `community=<h>`, 9000 roles, 39001/39002). Room tenancy is the server-stamped `channels.community_id`. Workspace membership means membership in every live top-level Room. Invites are signed kind:30078; DMs are deterministic Rooms; in a two-member agent DM every human message addresses that agent (`routeHumanMessage`). `invite-only` maps to NIP-29 `private`; outsiders redeem a pairing marker through `/agent-pairing/claim` (`apps/push-gateway/src/server.ts`); proof: `npm run prove:private-pairing`.
- **Key succession.** Roles resolve at the roster funnel (`communityMembers(…, {predecessors})` → `inheritRolesThroughSuccession`); the ledger is `beeline_key_successions` (`apps/auth/src/store.ts`).
- **App links** live in `relay-stack/web/.well-known/` (paths/packages: `scripts/app-associations.mjs`; drift: `app-association-drift.yml`). Store review uses `beeline://review/<secret>`; the HTTPS form is a fallback.

## System lines and events

- **One producer, one grammar.** `apps/server/src/system-line.ts` produces every `system`/`card` line as `<subject> <verb>[ <object>][ · <consequence>]` (past tense, `@handle` names, no colon/em dash/trailing period; `system-line.contract.test.ts`). The phone renders each system message separately with `LedgerSystemLine` (`buzz/system-lines.ts`), using two-line previews and brass More/Less only for measured overflow (`Ledger.test.ts`, `system-lines.browser.test.ts`); agent tool runs fold together, and consecutive GitHub PR cards and CI-check notices use separate latest-state accordions (`buzz/pr-lifecycle.ts`, `PrLifecycleCard.tsx`; `pr-accordion.test.ts`, `ci-accordion.test.ts` and their browser regressions).
- **A line's `kind` is the contract; its `verb` is prose.** `packages/api-contract/src/system-events.ts` owns `SERVER_EVENT_KINDS`/`RESUME_KINDS`/`CONTROL_KINDS`/`MAX_*`, plus one `SERVER_EVENT_KIND_DETAIL` line per kind (`eventKindCatalogLines`) — the single source `subscribe_events` and the agent rulebook both read, so a kind with no detail fails to compile rather than drift silently. `systemLine()` resolves `mentions ∪ subscribers`, and `routeSystemCommand` turns a kinded line into input/resume/stop with no sender access check. A `PER_ITEM_EVENT_KINDS` kind wakes its owner, never subscribable; `SUBSCRIBABLE_EVENT_KINDS` is.
- **Subscriptions are event-driven actions without approval.** `apps/server/src/agent-subscriptions.ts` stores a Room or covered repository event plus its prompt/optional workflow target; `systemLine()` emits one `subscription-fired` line per matching Room subscription and still reads legacy `memberships.event_subscriptions` for `subscribe_events`. Verified GitHub App deliveries emit one per matching repository subscription per delivery. `subscriptionActionPrompt` (`packages/api-contract/src/subscriptions.ts`) puts the trusted action before the quoted untrusted payload. The phone's Schedules and subscriptions page lists these with the same detail grammar and stop control. Connected Slack channel messages register a Composio webhook trigger on the existing account (`composio-apps.ts`); `/v1/connectors/events/composio` verifies the signed delivery and dedupes each subscriber wake. Linear and Stripe provider hooks run through the helper's official MCP credential and `provider-webhooks.ts` on both sides; the server verifies signatures and dedupes each subscriber wake. `list_subscription_events` advertises connected sources with a delivery path; Gmail and Squire-only connections are not offered yet.
- **An agent subscribes and emits for itself; the server owns the cause.** `subscribe_events` touches the caller's legacy membership list; `emit_event` acts only in its Room. `systemLine` derives cause/root/depth under an advisory lock and refuses past `MAX_EVENT_DEPTH`/`MAX_TURNS_PER_ROOT`. Caused lines sort at `GREATEST(now(), cause+1s)`.
- **An approval-style card that pauses a turn resumes it through a `RESUME_KINDS` event, never a typed human confirmation.** A Trusty Squire payment/credential/sign-in/vouch decision relays as `squire-approval-decided` over the task connection `SquireTaskRelay` already keeps open for exactly that wait (`pendingApprovals`, never polled); an unsolicited `notifications/approval_decided` on it fires `postSquireApprovalDecision`. Trusty Squire sends it on the originating connection (Squire #1017). Vault approvals (`fetch_credential`, `edit_credential`, `delete_credential`, `edit_payment_card`) have no browser session and are tracked too; at Squire's `expires_at` the relay itself posts `status: 'expired'`, because Squire sends nothing for an expiry. Coverage: `squire-task-relay.test.ts`, `squire-mcp-client.test.ts`, `integration.test.ts` ("wakes the paused turn with Squire's own decision").

## Branch conventions and CI

- `fm/*` branches stack: check `gh pr list --json baseRefName,headRefName` before assuming a file is on `main`. A stack merged base-first does not propagate; re-target to `main` and verify with `git grep <symbol> origin/main`.
- A cherry-pick off `feature/*` can drop a context-only declaration; root `npm run typecheck` catches it. Never stage the git-ignored `relay-stack/web/dl/` bundles.
- Resolve merges as one batch: list every textual conflict and semantic overlap, resolve them in one pass, then run one integration matrix.
- **`TYPECHECK` (root `npm run typecheck` = turbo + `apps/mobile` + `tsconfig.scripts.json`) and `SHARED PACKAGE TESTS` run on every PR.** Two green PRs can still merge into a red `main`; after changing a shared row type, merge `origin/main` and re-run typecheck.
- **In `checks.yml` a job `name:` is a required check context.** Never rename one; skip only with a job-level `if:`; every gate must execute something. Heavy suites filter by module path; `packages/**` runs everything. `npm run lint:workflow-paths` fails a workflow naming a test path nothing matches.

## Daemon self-update and CLI bundle

- **`<prefix>/lib/beeline` is the active bundle anchor**, a symlink into `lib/beeline-releases/<id>` swung by rename(2) (`self-update.ts`). `BEELINE_UPDATE_DISABLE=1` opts out of automatic updates. Never suggest `npx beeline` (an unrelated package); recovery is `npx usebeeline update`.
- **Routine updates wait at most five minutes for a quiet gap.** `ReleaseNotifier` (`apps/server/src/release-notify.ts`) pushes published helper releases; `MachineLink` (`apps/body/src/machine-link.ts`) reconciles the manifest once after the first registration on each socket, with no periodic update check. `ManagedUpdateDrain` and `quiesceHostedAgents` (`machine-helper.ts`) keep intake open until idle or the deadline, then activate and restart.
