# Corner authority and lifecycle invariants

Paths and commands below are relative to the repository root. Read these invariants before editing this area; named code and tests hold implementation detail.

## Authority and lifecycle

- **The merge gate is one rule, PR/head-scoped and GitHub-authoritative:** `mergeAllowed = live checks green AND a yes on the exact head AND no hold`. `GitHubOperations.prChecksStatus` reads the live PR head's GraphQL `statusCheckRollup`; webhooks only trigger re-reads. The yes (`cornerMergeGate`, `apps/server/src/corner-lifecycle.ts`) is a configured reviewer agent's `approve_merge` PASS or a current Workspace owner or admin's yes (`record_merge_yes` or the phone's `approveCornerMerge`, both `recordPersonMergeYes`), or the recorded agent commander's `approve_merge` on a completed zero-check head with no reviewer (`isZeroCheckCommander`, `corner-merge-approval.ts`); all live in `corner_merge_approvals` (one row per corner). The server does not referee whether a reviewer is the corner's opener or author — that is prompt discipline (`corner.implementer`/`cornerReviewerInstruction`, `apps/body/src/prompt-assembly.ts`), not a gate; a builder made reviewer could approve its own code if it ignored the prompt. A new commit cancels the yes; a brief edit does not. A hold is the only veto. Yolo is not a merge condition. `read(facet:checks,address)` returns facts only (`stage`, `checks`, `approved`, `held`, `mergeAllowed`), no prose rule.
- **One merge path: `GitHubOperations.landCorner`.** A reviewer's PASS wakes the implementer, whose `merge_corner` calls it; the phone's yes calls it at once, while the agent's record_merge_yes only records consent and merge_corner lands. It first refuses (`assertCornerBriefAllowsMerge`, `corner-brief.ts`, throwing `CornerBriefMergeRefusedError`) unless the corner's current brief assigns repository work: no brief revision, or `repositoryWork: false`, blocks landing through `merge_corner` and the phone's approve alike; recording a yes alone does not land (an unset `repositoryWork` is allowed; the reviewer's `approve_merge` PASS is still recorded). It then reads the gate live, claims the head (`claimCornerMergeAttempt`, one attempt per head, no run-state requirement) and squash-merges; a refusal returns the corner to `implement`. No instruction may contain `gh pr merge`. The merge webhook archives the corner and reaps its worktree.
- **Corner reviewers come only from the parent Room** (`rooms.reviewer_agent_id`/`reviewer_fallback_ids`). An unreachable reviewer reports to the commander (`reachableReviewer`). `approveCornerMerge` (`daemon-service.ts`, refusals as `CornerVerdictRejectedError` in `corner-merge-approval.ts`) accepts a configured reviewer's current-head PASS. Without a reviewer, a completed zero-check head goes to `review` with outcome `no_reviewer` and privately wakes its implementer to ask its commander for a yes using the normal report tool (`noteMissingReviewer`); the server never posts a merge-decision message to a person in this flow. Other green heads wake the implementer to arrange review or report a merge decision to the commander. Green review gaps use `noteReviewBlocked` (`corner-lifecycle.ts`) to privately wake the implementer and report to the commander; coverage: `corner-lifecycle.test.ts` and `corner-reviewer-list.test.ts`.
- **`CORNER_LIFECYCLE_CONTRACT` (`corner-lifecycle.ts`) owns corner transitions.** It is TypeScript, never a saved Workspace workflow. Every corner starts `opened` → `implement`; repository work proceeds through `checks` → `review` → `landed`, with `closed` terminal and legacy `ask_human` resumable. `advanceCorner` validates under the run lock, writes the lifecycle card and wakes the reviewer on green, otherwise the implementer. A brief revision wakes only the implementer and changes only legacy `ask_human` state. CI failures, reruns, stalled checks and unconfirmed merges return to the implementer without a human escalation cap (`noteBlockedCornerChecks`, `refreshCheckRollup`; `corner-lifecycle.test.ts`). Failed worker/reviewer wakes report to the commander through `commander.ts`; opened/merged watches replace PR merge subscriptions.
- **A corner has one server-owned state vocabulary:** `working|waiting|idle|review|archived`, from `deriveCornerState` (`apps/server/src/corner-state.ts` over `packages/api-contract/src/corner-state.ts`). Worker turns or queued commands mean working; running checks or reviewer turns/commands mean review. Waiting needs an unresolved human blocking item (an indexed `corner_owed.blocking` request or an active human merge hold); ordinary mentions and failed workflow stages alone do not qualify. Triggers maintain owed rows in the writer's transaction; readers use `cornerBlockerSql`, never a per-read transcript scan. Clients render `CornerListItem.state` verbatim. `inspect_corner.state` is the same observed state; lifecycle remains the separate workflow stage.
- **Corner attention is durable** (`corner-attention.ts`, `corner-attention.integration.test.ts`). The presence loop records an idle flag before delivering it one step up through commander provenance, once per idle span; new commands, turns and PR heads start a new span. Only the worker's own schedules/subscriptions/watches suppress it, never the commander's auto-watch. The newest unresolved human blocker gets a reminder every 24 hours; explicitly dismissing its reminder (or clearing the Needs-you section) stops reminders without deciding the underlying request. Opening a reminder clears that tray occurrence but preserves repeats; `clearNeedsYou.dismissReminder` persists explicit dismissal separately. No worker or reviewer wake is created by the idle flag. `list_corners(activeOnly: true)` excludes archived corners.
- **Corner goals can be kept current with `rename_corner` and its `objective` field**, including agent-opened corners. Opening cards, lists and inspect reads render the current stored objective; goal/title edits never rewrite System messages or cards. This changes navigation, not the approved brief or work scope. Coverage: `commander.integration.test.ts`.
- **A repository corner starts from a brief authorized by the dispatching message, never its short objective.** Brief = Markdown spec (≤ `CORNER_BRIEF_SPEC_MAX_LENGTH`) + file manifest + one approving human message or active private commander order resolved server-side (`resolveCornerBriefApproval`, `corner-brief.ts`). The objective is navigation only; the approval quote wins conflicts.
- **The brief's spec is the scope source.** `beeline-spec` (`apps/body/src/beeline-skill.ts`) writes intent, stories, criteria, non-goals, risks and references; `beeline-review` grades that outline. The dispatching message authorizes work; no separate spec/mock approval or Room post is required. Planning questions and mocks are agent judgment unless a person requests one before building (`CORNER_AUTHOR_CONTRACT`, `prompt-assembly.ts`).
- **A corner is repository work exactly when its parent Room has a repository** (`rooms.repository_resolution='repository'` / `repository_key`); there is no `lane` column. A repository-backed corner, agent- or person-opened, opens on the code path directly (feature branch, PR, merge gate). A corner in a Room without a repository runs in `rooms/<corner>/scratch` with no token or checkout, never opens a pull request, and ends via human `requestCornerClose` or the `close_corner` of any agent that reaches it.
- **Orders go down; reports go one step up.** `apps/server/src/commander.ts` derives reports from the active order chain; the opening command is fallback provenance. `open_corner` records `openedFromCornerId` explicitly in `corner_facts.opened_from_corner_id` when a corner opens work; existing corners remain NULL without a backfill. Corner turns may order, revise or close any reachable address except DM and agent addresses, their parent Room and all ancestor corners, following both Room parent links and recorded opening provenance. Self, sibling and child corners are allowed. Parent-target refusals direct the caller to report to its commander. Room/DM behavior and the single-agent requirement for Room orders remain unchanged. `order`/`report` use private `agent_commands` payloads; only human reports enter chat at the original order address. DMs can open, read and command member Rooms. `wake(action:create,trigger:lifecycle,address)` is lifecycle-only; opening auto-watches. Proof: `npm run prove:command-grammar`; coverage: `commander*.integration.test.ts`. Explicit reports require `status: done|blocked|failed|needs_decision` matching their text prefix. A corner worker's done requires the live merge gate or a merged PR, unless its brief says `repositoryWork: false`; ordinary progress stays in the corner. Agent orders outside corners may report done when complete. Each agent owns one `immediate` (default) or `batch:<positive whole minutes>` wake-inbox setting (`set_wake_delivery` / `get_wake_delivery`), stored on `agents.wake_batch_minutes`. It applies to all nonhuman model wakes: system and subscribed events, lifecycle, orders, reports and schedules. Digests remain per Room/corner, preserve the recorded inbox sequence and rendered sources, and commit atomically (`commander-wakes.ts`). Original command rows retain order/report provenance: a combined report follows each distinct orderer’s own return route. Delivery and claim revalidate original workflow attempts; handoffs resolve absorbed attempt provenance and step outputs bind to every absorbed visit. Expiry and sender-scoped Stop rebuild the digest while preserving unaffected work. The quiet-corner gate covers absorbed reviewer commands at delivery and claim. Human messages and helper stop/restart controls stay immediate; human messages do not shorten a digest window. Existing windows keep their deadlines when the setting changes. Empty windows emit nothing; the presence loop releases due windows after restart. Reviewer dispatch and merge gates remain immediate by default; only a reviewer who opted into batching delays its review turns. Coverage: `wake-inbox.integration.test.ts`.
- **A corner operates as a Room: membership is the authority, the branch is the shared artifact.** Only `agent_commands` authorize a turn (`agent-command.ts`); creation wakes only the selected implementer; `membership-join.ts` copies Room joins without resurrecting removed members. Each helper syncs to `origin/<feature_branch>` before every turn (`corner-branch-sync.ts`); a rebase conflict realigns to the remote and drops local unpushed commits, never force-pushes. `corner-wake.ts` is the sole wake predicate. `DAEMON_OPERATION_ROUTES` must stay exhaustive.
- **A human tag names a corner's implementer.** `corner_facts.worker_agent_id` (NULL = opener) is set by `routeHumanMessage`; agent tags in final replies and `post_to_corner(address,text)` instead invite conversation in that place, never change the implementer or create a report obligation; never to the parent's reviewer or fallbacks; worker-scoped reads use `cornerImplementerSql` (`corner-worker.ts`). `owner_agent_id` stays opener and brief author; any current member agent may archive the corner (`archiveCorner` is membership-gated by `DaemonService.access`, like every other corner write); a person-opened corner (`kind='human'`) has no opener agent, so the first agent to take the implementer role becomes its owner (`setCornerImplementer`, `agent-command.ts`).
- **A phone closes a corner only through `PhoneService.requestCornerClose`** (current member; a human-created corner closes for its creator or a Workspace owner/admin), which applies `closeCornerState` (`corner-close.ts`); never close by chat prose. Every path that archives a corner — a human close, an agent's `close_corner` (`closeCornerState`), and the GitHub merge webhook (`GitHubOperations.mergeCorner`) — cancels its pending/claimed `agent_commands` and `working` turns in the same transaction via `cancelCornerAgentCommands`, so landing a corner never leaves a stale assignment behind. Closing and landing also abandon live saved workflows and remove their timers via `abandonCornerWorkflowRuns` (`workflow-runs.ts`; `corner-lifecycle.test.ts`). Any agent that reaches a repository corner closes its PR without merging through `close_corner_pr(address)` (`GitHubOperations.closeCornerPullRequest`): the branch stays, the corner stays open, and `lifecycle.pr` is cleared so the merge gate reads no PR.
- **An agent reaches a corner when it is a current member of the corner or of its parent Room** (`DaemonService.reach`). Reach authorizes closing, renaming, ordering, revising the brief, reading (status, transcript, brief, checks, PR discussion, members) and `post_to_corner`. Any reachable member agent may merge through the same live merge gate. Check reach on the target `cornerId`, never only on the turn's `roomId`. A Room and its corners always read each other's history (`AUTHORIZED_ROOMS_CTE`).
