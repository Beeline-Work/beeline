# Corner authority and lifecycle invariants

Paths and commands below are relative to the repository root. Read these invariants before editing this area; named code and tests hold implementation detail.

## Authority and lifecycle

- **The merge gate is one rule, PR/head-scoped and GitHub-authoritative:** `mergeAllowed = live checks green AND a yes on the exact head AND no hold`. `GitHubOperations.prChecksStatus` reads the live PR head's GraphQL `statusCheckRollup`; webhooks only trigger re-reads. The yes (`cornerMergeGate`, `apps/server/src/corner-lifecycle.ts`) is a configured reviewer agent's `approve_merge` PASS or a current Workspace owner or admin's yes (`order_corner_merge` or the phone's `approveCornerMerge`, both `recordPersonMergeYes`); both live in `corner_merge_approvals` (one row per corner). The server does not referee whether a reviewer is the corner's opener or author — that is prompt discipline (`corner.implementer`/`cornerReviewerInstruction`, `apps/body/src/prompt-assembly.ts`), not a gate; a builder made reviewer could approve its own code if it ignored the prompt. A new commit cancels the yes; a brief edit does not. A hold is the only veto. Yolo is not a merge condition. `pr_checks_status` returns facts only (`stage`, `checks`, `approved`, `held`, `mergeAllowed`), no prose rule.
- **One merge path: `GitHubOperations.landCorner`.** A reviewer's PASS wakes the implementer, whose `merge_corner` calls it; a person's yes calls it at once. It first refuses (`assertCornerBriefAllowsMerge`, `corner-brief.ts`, throwing `CornerBriefMergeRefusedError`) unless the corner's current brief assigns repository work: no brief revision, or `repositoryWork: false`, blocks the land for `merge_corner`, `order_corner_merge` and the phone's approve alike (an unset `repositoryWork` is allowed; the reviewer's `approve_merge` PASS is still recorded). It then reads the gate live, claims the head (`claimCornerMergeAttempt`, one attempt per head, no run-state requirement) and squash-merges; a refusal returns the corner to `implement`. No instruction may contain `gh pr merge`. The merge webhook archives the corner and reaps its worktree.
- **Corner reviewers come only from the parent Room** (`rooms.reviewer_agent_id`/`reviewer_fallback_ids`). An unreachable reviewer reports to the commander (`reachableReviewer`). `approveCornerMerge` (`daemon-service.ts`, refusals as `CornerVerdictRejectedError` in `corner-merge-approval.ts`) accepts a configured reviewer's current-head PASS. Without a reviewer, green checks go to `review` with outcome `no_reviewer` and wake the implementer to arrange review or report a merge decision to the commander. Green review gaps use `noteReviewBlocked` (`corner-lifecycle.ts`) to privately wake the implementer and report to the commander; coverage: `corner-lifecycle.test.ts` and `corner-reviewer-list.test.ts`.
- **`CORNER_LIFECYCLE_CONTRACT` (`corner-lifecycle.ts`) owns corner transitions.** It is TypeScript, never a saved Workspace workflow. Every corner starts `opened` → `implement`; repository work proceeds through `checks` → `review` → `landed`, with `closed` terminal and legacy `ask_human` resumable. `advanceCorner` validates under the run lock, writes the lifecycle card and wakes the reviewer on green, otherwise the implementer. A brief revision wakes only the implementer and changes only legacy `ask_human` state. CI failures, reruns, stalled checks and unconfirmed merges return to the implementer without a human escalation cap (`noteBlockedCornerChecks`, `refreshCheckRollup`; `corner-lifecycle.test.ts`). Failed worker/reviewer wakes report to the commander through `commander.ts`; opened/merged/closed watches replace PR merge subscriptions.
- **A corner has one server-owned state vocabulary:** `working|waiting|idle|review|archived`, from `deriveCornerState` (`apps/server/src/corner-state.ts` over `packages/api-contract/src/corner-state.ts`). `waiting` needs an unexpired `corner_owed` row for a human member; triggers maintain `corner_owed` in the writer's transaction and readers use `cornerOwedLookupSql`, never a per-read `messages` scan. Clients render `CornerListItem.state` verbatim.
- **A repository corner starts from a brief authorized by the dispatching message, never its short objective.** Brief = Markdown spec (≤ `CORNER_BRIEF_SPEC_MAX_LENGTH`) + file manifest + one approving human message or active private commander order resolved server-side (`resolveCornerBriefApproval`, `corner-brief.ts`). The objective is navigation only; the approval quote wins conflicts.
- **The brief's spec is the scope source.** `beeline-spec` (`apps/body/src/beeline-skill.ts`) writes intent, stories, criteria, non-goals, risks and references; `beeline-review` grades that outline. The dispatching message authorizes work; no separate spec/mock approval or Room post is required. Planning questions and mocks are agent judgment unless a person requests one before building (`CORNER_AUTHOR_CONTRACT`, `prompt-assembly.ts`).
- **A corner is repository work exactly when its parent Room has a repository** (`rooms.repository_resolution='repository'` / `repository_key`); there is no `lane` column. A repository-backed corner, agent- or person-opened, opens on the code path directly (feature branch, PR, merge gate). A corner in a Room without a repository runs in `rooms/<corner>/scratch` with no token or checkout, never opens a pull request, and ends via human `requestCornerClose` or the `close_corner` of any agent that reaches it.
- **Orders go down; reports go one step up.** `apps/server/src/commander.ts` derives reports from the active order chain; the opening command is fallback provenance. `order`/`report` use private `agent_commands` payloads; only human reports enter chat at the original order address. DMs can open, read and command member Rooms. `watch` is lifecycle-only; opening auto-watches. Proof: `npm run prove:command-grammar`; coverage: `commander*.integration.test.ts`.
- **A corner operates as a Room: membership is the authority, the branch is the shared artifact.** Only `agent_commands` authorize a turn (`agent-command.ts`); creation wakes only the selected implementer; `membership-join.ts` copies Room joins without resurrecting removed members. Each helper syncs to `origin/<feature_branch>` before every turn (`corner-branch-sync.ts`); a rebase conflict realigns to the remote and drops local unpushed commits, never force-pushes. `corner-wake.ts` is the sole wake predicate. `DAEMON_OPERATION_ROUTES` must stay exhaustive.
- **A human tag names a corner's implementer.** `corner_facts.worker_agent_id` (NULL = opener) is set by `routeHumanMessage`, and by `routeAgentResult` when an agent's turn, requested by a person who is a corner member, tags another agent (a hand-over the person asked for); never to the parent's reviewer or fallbacks; worker-scoped reads use `cornerImplementerSql` (`corner-worker.ts`). `owner_agent_id` stays opener and brief author; any current member agent may archive the corner (`archiveCorner` is membership-gated by `DaemonService.access`, like every other corner write); a person-opened corner (`kind='human'`) has no opener agent, so the first agent to take the implementer role becomes its owner (`setCornerImplementer`, `agent-command.ts`).
- **A phone closes a corner only through `PhoneService.requestCornerClose`** (current member; a human-created corner closes for its creator or a Workspace owner/admin), which applies `closeCornerState` (`corner-close.ts`); never close by chat prose. Every path that archives a corner — a human close, an agent's `close_corner` (`closeCornerState`), and the GitHub merge webhook (`GitHubOperations.mergeCorner`) — cancels its pending/claimed `agent_commands` and `working` turns in the same transaction via `cancelCornerAgentCommands`, so landing a corner never leaves a stale assignment behind. Closing and landing also abandon live saved workflows and remove their timers via `abandonCornerWorkflowRuns` (`workflow-runs.ts`; `corner-lifecycle.test.ts`). Any agent that reaches a repository corner closes its PR without merging through `close_pull_request` (`GitHubOperations.closeCornerPullRequest`): the branch stays, the corner stays open, and `lifecycle.pr` is cleared so the merge gate reads no PR.
- **An agent reaches a corner when it is a current member of the corner or of its parent Room** (`DaemonService.reach`). Reach authorizes closing, renaming, ordering, revising the brief, reading (status, transcript, brief, checks, PR discussion, members) and `post_to_corner`. Any reachable member agent may merge through the same live merge gate. Check reach on the target `cornerId`, never only on the turn's `roomId`. A Room and its corners always read each other's history (`AUTHORIZED_ROOMS_CTE`).
