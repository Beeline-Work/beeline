## Core invariants (read first)

- **A bad read fails alone, and a bad release contains itself.** `apps/server/src/database.ts` owns bounded app/enrichment pools while migrations and background jobs use explicitly long-running pools; `PhoneService` projects core Room data before independently degradable enrichment. Server boot only asserts the release-owned `beeline_schema_state`; the release migration writes it last. `/health` exposes request-pool counts and oldest app-query age through a dedicated diagnostics pool. `.github/actions/server-leg/action.yml` updates one of exactly two Fly Machines, watches its pinned `/health`, version, and authenticated Room reads for five minutes, then updates its peer or restores the recorded previous image. The final smoke uses `scripts/server-release-smoke.mjs`; `.github/workflows/server-rollback.yml` is the manual recovery path. Coverage: server `database.test.ts`, `phone-service.read-room-latency.test.ts`, `server.test.ts`; `scripts/server-release-smoke.test.mjs`, `scripts/unified-release.test.mjs`.

- **The merge check gate is PR/head-scoped, GitHub-authoritative, not corner-owned, and never deadlocks on self-review.** `GitHubOperations.prChecksStatus` (`apps/server/src/github-operations.ts`) resolves the current PR head in the Room's repository and reads that commit's GraphQL `statusCheckRollup`; webhook check deliveries only trigger a fresh rollup read for lifecycle projection and never become locally aggregated verdict facts. The retired `corner_check_facts` and `github_head_checks` tables are dropped by migration. Its `approvalPending` is the configured reviewer's exact-head outcome: when the opener IS the parent Room's `reviewer_agent_id`, it is false because another self-approval adds no signal. The result names the actor with `reviewer` (`@handle` or null), explicit `reviewerExists`, `reviewerIsAuthor`, `reviewerWake` (`unconfigured` | `unreachable` | `waiting` | `dispatched` plus a `detail`), and a `rule` line stating which single reviewer's `approve_merge` records PASS. `pr_checks_status` composes that outcome at the real merge boundary: permission is false on review failure/pending, worker yolo off, the existing latest human hold, or no configured reviewer; only reviewer PASS + yolo on + no human hold + reviewer present permits the author to merge. Missing reviewer/request state is never consent. No Room owner/admin approve-merge control exists in the mobile app (`apps/mobile` has no `approveCornerMerge` call; see `corner-open-approval.design.test.ts`). `pr_checks_status` accepts an explicit PR number/URL; transcript prose never proves passing checks. Coverage: auth `github-pr-checks.test.ts`; server `pr-checks-status.test.ts` (real helper over local HTTP), `github-operations.test.ts`; body `read-only-mcp.pr-checks.test.ts`. Deploy server before helper.

- **A corner reviewer is configured only on its parent Room and subscribes to green checks; the AUTHOR is who runs `gh pr merge` once the complete gate opens — the server never merges and never sends a closing request of any kind.** `rooms.reviewer_agent_id` is the sole authority; green dispatch reads it directly rather than trusting mutable subscription targets. A configured reviewer who is not a current parent-Room member is not "no reviewer": `routeSystemCommand` must not fall through to the author path, must not set `command_check_state`, and posts a visible note naming them (`agent-command.ts`). `updateRoom` projects its mandatory `check-passed` subscription onto the parent and every corner membership, later corner memberships inherit it, and `setEventSubscriptions` cannot remove it. `reconcileConfiguredCornerReviewers` repairs existing projections and dispatches already-green exact heads with no recorded verdict. One green transition wakes the reviewer, who records an exact-head `corner_merge_approvals` verdict with `approve_merge` and tags the implementer; the reviewer never merges, and neither does the server. **A live reviewer session resolves its exact target inside the active turn, not at session activation:** `MonolithCornerTurnLoop.activeReviewerInstruction` refreshes before the prompt and again before its bounded second pass, and names a SHA only when the server's green lifecycle head equals the checked-out `HEAD`; a moving or webhook-lagged head fails closed while `approveCornerMerge` remains the final exact-current-head guard. **The handoff back does not depend on that tag:** `queueCornerWorkerAfterReview` (`agent-command.ts`) queues the corner's worker from the review's own final reply, on approval and on refusal alike, and the tag still wins the row when it was typed. **The verdict and the handoff commit together or not at all:** a handoff written after the verdict commits can leave a durable verdict nobody was woken for — the exact stall — and no retry repairs it, because the reply is stored and its command output authority is spent. So `daemon-service.ts` excludes a corner's configured reviewer from the shorter no-mention reply path (`access` returns the `cornerReviewer` flag from the membership statement it already runs, so no ordinary Room reply pays for the question), putting every verdict on the transactional path where `routeAgentResult` and the handoff share the reply's transaction. **Nothing records a FAIL**, so a rejection, a stale-head refusal and a silent turn are one state — no approval row for the current head — and the handback keys on the reviewer's TURN ENDING, carrying its closing text so the worker can tell them apart. Two bounds: it fires only while `lifecycle.checks` is `passing`, because a reviewer that ended a turn to WAIT for CI has not finished (firing nothing costs nothing — `updateLifecycle` clears `command_check_state` on any checks change, so the next green re-dispatches); and `corner_facts.review_handback_head`/`review_handback_count` counts handbacks per head, a push resetting them, so at `REVIEW_HANDBACK_LIMIT` the corner names `commissioned_by` instead of waking the worker again. The handback sets `retainDepth` — it is a lifecycle transfer, not a delegation — so a disagreement reaches that limit instead of dying silently on `COMMAND_MAX_DEPTH`. The author calls `pr_checks_status` when that turn wakes it and merges only when the composite `approvalPending` is false. **Approval is exact-head-only:** every new PR head, including a base catch-up, requires a fresh reviewer PASS for the current brief revision; no diff-derived identity can carry approval between heads. If `gh pr merge` refuses because the branch is behind its target (branch protection `strict` mode), the AUTHOR updates it (`gh pr update-branch` or merge-from-main), waits for checks, then merges again — this is in the merge instruction text, not left to the agent to infer. Failed checks still wake the opener, and a Room without a reviewer keeps the opener's prior check-turn flow but cannot pass merge authorization. Author/reviewer instructions live in `apps/body/src/monolith-corner-turn.ts`, while `apps/body/src/beeline-skill.ts` owns the bundled review procedure and the `beeline-triage` bugfix execution contract (see [agent request triage](docs/agent-prework-gate.md#bugfix-execution)). Coverage: body `monolith-corner-turn.test.ts`/`agent-home.test.ts`/`beeline-skill.test.ts`/`read-only-mcp.test.ts`/`read-only-mcp.pr-checks.test.ts`, server `integration.test.ts`/`agent-command.integration.test.ts`/`pr-checks-status.test.ts`/`corner-review-dispatch.test.ts`.

## Branch conventions

- **Corner agents own the GitHub workflow.** Finish means commit, push, `gh pr create`, print the URL, wait for the server checks-passed fact. With no human hold the agent merges with `gh`; the merge webhook archives and reaps the worktree. Relay up is retired; a corner's only Room-facing outputs are its cards.
- `fm/*` branches stack; check `gh pr list --json baseRefName,headRefName` before assuming a file is on `main`; `git branch -a --contains <commit>` finds the source branch.
- A cherry-pick off `feature/*` can drop a context-only declaration — `npm run typecheck` catches it. Generated `relay-stack/web/dl/` bundles are ignored; never stage them in a cherry-pick (the release-channel contract is in `docs/cli-bundle-channel.md`).
- **Resolve merges as one batch gate:** enumerate every textual conflict and semantic overlap first, resolve the complete set in one pass, then run one integration matrix plus a single conflict-resolution review before push.
- **`TYPECHECK` (root `npm run typecheck` = turbo + the isolated mobile app + `tsconfig.scripts.json`) and `SHARED PACKAGE TESTS` gate every PR unfiltered by path** — a type error can be introduced by two independently green PRs merging cleanly into a red `main`, so a required-field change on a shared row type must re-run the root typecheck after merging `origin/main`.
- **Stacked PRs merged base-first do not propagate** — re-target to `main`; verify with `git grep <symbol> origin/main`.
