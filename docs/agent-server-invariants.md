# Server safety and feature invariants

Paths and commands below are relative to the repository root. Read these invariants before editing this area; named code and tests hold implementation detail.

## Database and reads

- Establishing the System author reads an already-canonical identity without locking or updating it; one statement inserts a missing row or repairs legacy metadata. Mergeability refresh takes the lifecycle lock before the GitHub cache row, matching check refresh and conflict dispatch. Real PostgreSQL regressions: `production-deadlocks.postgres.test.ts` (`SERVER-49/4A/45`, `SERVER-1W`).

- Owned replies and effects recheck and retain current Room/Workspace membership in an additive commit constraint that survives preceding installer replay; final control replies acquire actual source/access rows with NOWAIT only for synchronous enqueue (`turn-ownership.ts`, `owned-turn-reply.ts`). Scheduled stops hold their actual manager rows through the database write and perform provider cleanup after commit. Existing writer implementations and serialization stay in place for this preparatory reader release; removal follows after the release drains. PostgreSQL coverage: `turn-ownership-authority.postgres.test.ts`.
- Keep bounded app/enrichment/health pools separate from long migrations (`apps/server/src/database.ts`). Project core Room data before optional enrichment; boot asserts only the migration-final `beeline_schema_state`. Queries, transaction starts, dedicated checkout and boot schema observation each make one attempt. A failed or lost reply never replays SQL; command owners retain uncertain outcomes. Only successful admitted work emits database recovery. Proofs: `database.test.ts` and `tests/seams/server-db.test.ts`. Release isolation: [release pipeline](release-pipeline.md).
- **Rollout compatibility and contention:** retain the retired `corner_facts.owner_agent_id` and `github_star_prompts.reached_milestone` through serving/rollback overlap. New column drops use the guarded post-drain contract phase. Same-turn database work queues before checkout; Sentry lock contention leaves the durable batch pending. Recorded events, isolated built HTTP replay and real PostgreSQL regressions: [November rollout replay](rollout-nov03-replay.md).
- Machine vault reports use the owner/machine installation row in `squire-machine.ts`. Whole-report revision claims, unpair generation changes and batched key writes prevent stale snapshots from merging. `squire-machine.postgres.test.ts` and `production-deadlocks.postgres.test.ts` exercise concurrent reports and unpair. GitHub reconciliation still commits its deduplicated repository note before archival; note failure leaves the corner open (`merge-archival.test.ts`).
- GitHub installation callbacks are consumed atomically before provider HTTP. Installation snapshots are fetched first and stored in batches (`github-installation-store.ts`, `github-installation.postgres.test.ts`).

- **`deleteWorkspace` is owner-only and a real `DELETE`** relying on FK cascades. It checks existence before ownership (idempotent retries), writes `workspace_deletions` + per-member notices, revokes tokens only for agents with no other membership, and preserves independent media records. Account deletion retains workspace deletion audits, re-attributing the deleted person and their agents to the hidden deleted-account identity (`account-deletion.test.ts`, `R-ACCOUNT-AUDIT`). Every FK column into `messages`/`rooms`/`workspaces` must carry a leading-column index — an unindexed one forces Postgres to sequentially scan that whole child table per deleted row during the cascade, which is slow enough on a real table to blow the app pool's `APP_STATEMENT_TIMEOUT_MS` and leave the client's delete request hanging with no answer. Guarded by the `cascade-path foreign keys stay indexed` test in `database.test.ts`; `messages` itself is busy enough that a new index there goes through `createIndexConcurrently` in `migrate()`, not inline schema SQL.

- **Push delivery drains a write-time device outbox.** `push-outbox.ts` installs transactional message/device and workspace-join fanout. A native per-turn UPSERT combines sibling message IDs without a Room lock or timed burst grouping (`push-turn-context.postgres.test.ts`). `PushDeliveryLoop` atomically consumes each intent once; claims fence duplicates, and failed deliveries never create another attempt. Read-clear delivery follows committed read marks. No startup backfill or retention clock runs. Coverage: `push-outbox.test.ts` and `background.test.ts`.

- **Retired helper calendar mirrors keep their rows until a separate post-drain contract migration.** `work_schedules` and `schedule_receipts` have no current or release-pinned helper producer after their retired API handlers are removed. Keep their schema, the separately authorized `getWorkScheduleAuthority` reader, and `account-deletion.ts` erasure cleanup; current scheduling stays in `agent_schedules` and `agent_subscriptions`. The storage registry marks these two tables for later deletion rather than requiring an unused runtime writer.

## Grants and retirement

- **Retired corner-app storage remains only for deployment compatibility.** `database.ts` preserves the three legacy tables and their rows, constraints and indexes; idempotent creation repairs installations where #3221 already dropped them (lost data cannot be recovered by this migration). Previous release `2e6951beb1c06174a9adf4c6af6dbfd27d3f94c6` still joins bindings/installations in `PhoneService.loadCorners`, so dropping them before old instances drain breaks ordinary corner lists. Sentry BEELINE-SERVER-22 recorded only that release during the rollout (last seen 2026-11-02 07:07:48 UTC at investigation); current corner reads have no references. Account deletion anonymises retained identity references to the deleted-account tombstone, so compatibility rows cannot block deletion (`account-deletion.test.ts`). Retention ends with a separate reviewed contract migration only after every serving image and every supported rollback image is verified free of these references; elapsed time alone is insufficient. No tools, routes, cards or UI are restored. Proof: `database.test.ts`, Reproduction `SENTRY-22`, runs the historical corner-list SQL against isolated PostgreSQL-compatible PGlite for dropped-table repair and existing-row upgrades, including repeated migration and rollback writes.

- **Agent Grants have one vocabulary and one authority axis.** `packages/api-contract/src/agent-grants.ts` owns kinds, statuses, the command-rule parser (`parseCommandGrantTarget`; `commandGrantMatches` is an argv prefix; approved command grants follow the agent within their Workspace across Room/requester changes) and the decision line; policy follows `docs/approval-matrix.md`; `surface-capabilities.ts` lets a corner dominate a Room. Yolo defaults on (`backfillYoloModeDefault`) and is forced off in public Workspaces; credential-file argv and unread scripts (>4096 B/120 lines) still stop. Human profiles show the grant ledger (`readWorkspaceMembers`, `MemberGrantRow.tsx`, wording in `grantProvenanceLine`); an active `shared_asset` row alone offers revocation there. The agent settings page shows none.
- Command-grant retries within one agent command replace the earlier pending ask on its card. `superseded_at` preserves the old status without granting or revoking access; stale decisions cannot wake the agent. Grant inspection omits superseded asks and lets corner reviewers inspect only that corner implementer’s grants. Proof: `GRANT-CURRENT-1` in `integration/grants-approvals.test.ts` and `agent-grant-inspect.test.ts`.
- **Removing an agent retires it; its work survives.** `PhoneService.removeAgent` → `retireAgentFromWorkspace` (`agent-retirement.ts`) ends memberships, revokes all its daemon tokens and unused exchanges (`apps/server/src/daemon-credential-lifetime.ts`, shared with rollback and Workspace deletion) and grants, hides the identity, clears configuration, and deletes schedules; corners, turns and messages stay. A helper retires only on 403 `agent_removed` (`isAgentRemovedError`), never on transport errors, 5xx, or plain 401.
- **Issued capabilities follow membership lifetime.** Pairing claims lock the issuer's current Workspace membership; leave/removal deletes their unclaimed codes. A legacy permission requester's decision locks current Room and Workspace memberships; the manager path keeps its policy (`apps/server/src/phone-service.ts`). Credential and pairing races: `apps/server/src/authorization-lifetime.test.ts` (isolated PostgreSQL via `BEELINE_LIFETIME_TEST_POSTGRES_URL`).

## Room departure

- **Leaving a Room.** Any human can leave a top-level Room (`PhoneService.leaveRoom`, under the Room row lock); the last Workspace owner/admin in it deletes it for everyone and must pass `confirmDelete: true`. `leaveDeletesRoom` drives `buzz/room-leave.ts`. Swiping a DM writes a per-viewer `chat_dismissals` row hidden only until newer inbound activity.

## Feature contracts

- Automatic identity handles are assigned once at creation, using a readable base name and a monotonic number. `identity-handles.ts` reserves numbers with one counter upsert, seeded from existing suffixes; numbers are never reused. Pairing, roster changes, renaming the display name, and migrations preserve existing handles. Explicit handle choices use the same atomic counter and refuse an occupied address.

- **Plan usage belongs to an account, not an agent.** Helpers send a quota-axi read with `AgentUsage.account` (a hash of the vendor-verified account id, else of machine plus credential file; never the identity); `saveAgentUsage` keeps one `usage_accounts` row per owner, provider and account and points each agent at it, so Profile, Members row and `read_agent_usage` agree. A fresh read replaces the window set; the stamp is the oldest window; `read` carries why numbers are older. `refreshAgentUsage` answers `offline` at once without a helper connection, else waits ≤20 s for `answerUsageRefresh`. One read per login per interval on a helper (`HarnessQuotaReader`). Proof: `agent-usage-accounts.integration.test.ts`, `harness-quota.usage-truth.test.ts`, `scripts/prove-usage-accounts.mjs`.
- **Public agent `post` text excludes leading inline reasoning blocks.** `agent-post-text.ts` removes initial `<think>`/`<thinking>` blocks; `DaemonService.postCornerMessage` refuses reasoning-only input before storage. Ordinary replies and quoted tags later in a reply stay intact. This does not classify untagged model-authored prose or establish the cause of an inaccessible incident. Coverage: `agent-post-text.test.ts`, ACP/proxy `R-REASONING-POST` cases and the built MCP → phone-read proof in `scripts/prove-public-post.ts`.

- **Incoming subscription webhooks** use the existing subscription wake path with fixed saved actions and quoted outside payloads. Workspace admins manage Room links; human DM members manage links in their own DM; tokens are encrypted and only phone reveal/rotate returns them. Ingress and rotation serialize on the subscription. Sender contract and retention: [subscription webhooks](subscription-webhooks.md); proof: `subscription-webhooks.test.ts` and `apps/mobile/evidence/subscription-webhooks/README.md`.

- Sentry capture, authenticated Telegram forwarder, configuration and post-release proof: [error monitoring](error-monitoring.md). Keep Telegram outbound-only and exclude forwarder failures from recursive capture. Caller validation failures use `ExpectedRefusalError` (or `CommandRefusalError` with an HTTP status); `captureServerError` excludes that shared type, never matching refusal message text. Unexpected exceptions and provider outages remain reportable. Handler proof: `BEELINE-SENTRY-REFUSALS` in `sentry.test.ts`.

- Private operator dashboard cohorts, fixture exclusions and metric provenance: [dashboard API](operator-dashboard-api.md); aggregate queries and regressions live in `operator-dashboard.ts` and `operator-dashboard.test.ts`.

- Wallet settlement and push authority: [wallet tools](wallet-tools.md), `wallet-notices.ts`, `wallet-webhooks.ts`. Indexed incoming receipts stay in `wallet_transactions` without a System DM. Outgoing transactions, failures, refusals, pending notices and webhook receipts without a history row retain their notices.
- Agent feedback atomically merges open matches and appends every occurrence (`feedback.ts`); it has no daily quota or timed suppression.
- Operator System DMs require lunchboxfortwo's human-rooted command, configured System-sender authority, and their own agent. Durable batches, audit and tool counts: [operator System DMs](operator-system-dms.md), `operator-system-dm.ts` and `operator-system-dm.test.ts`.
- Operator System DM transaction-start failures leave deliveries pending until a new committed delivery event. They never start a retry or deadline timer (`background-database-recovery.test.ts`).
- Feedback resolves silently through `notify_feedback_fixed` with a merged PR in `BEELINE_FEEDBACK_REPOSITORY`; `notify: true` sends Fixed notices only for an explicitly ordered notice in a configured System sender’s human-rooted turn; storage and policy: `apps/server/src/feedback.ts`, [triage workflow](workflows/feedback-triage.json).
- The GitHub star card acts only on the person's own tap and never gates anything (`github-star-prompt.ts`, `StarPromptCard.tsx`).
- Agent faces and names are assigned together by the server under the Workspace lock (`assignSeededAgentIdentity`, `PhoneService.claimAgentConnectPairing`); never re-derive a face on the client. Keep face IDs aligned in `packages/api-contract/src/faces.ts` and `apps/mobile/sources/buzz/faces/index.ts`.
- **A non-agent system author is a hidden `kind='human'` identity** with a fixed id (`SYSTEM_IDENTITY_ID`, `REVIEW_IDENTITY_ID`, `SCHEDULE_SCHEDULER_ID`), never a new `identities.kind`. `system-line.ts` sends essential approvals, sign-in, security and money notices to the recipient's read-only `@system` DM; routine Workspace facts stay in their committed state (`assertRoomIsWritable`); `migrations/one-system-thread.ts` retires every other bot DM and its contents. Tray decisions reuse the transcript's grant/permission/choice operations; Squire retains its own ceremony (`needs-you.ts`, `tray.tsx`).

## External apps and MCP

- **Save to vault cards contain metadata only.** `postVaultSaveCard` posts `vault-save`; the owner's device sends values to the dedicated `vault-save-http.ts` boundary. `VaultSaveRelay` sends them only over the requesting helper's existing socket, never through LiveHub, PostgreSQL notifications or durable commands. A current owner and Room membership, an atomic card claim and attempt fencing protect submission; offline and failed attempts discard values and offer retry. `agent-runtime.ts` calls its existing Squire client outside the model and returns only validated vault metadata; the saved wake retains the original command's provenance. Keep exceptions and provider responses out of logs and Sentry on this path. Coverage: `vault-save.test.ts`; native and web evidence: `apps/mobile/evidence/vault-save/README.md`.

- **External Rooms clients act as a consenting human, never a helper.** `rooms-mcp.ts` exposes only bounded Room tools; `rooms-mcp-oauth.ts` owns separate hashed grants, S256 PKCE, resource binding, browser consent, per-token limits and revocation. Membership is rechecked for every operation; sends use `PhoneService.sendRoomMessage` and its existing command routing. Listing, reviewer fixture, retention and revocation: [Rooms connector](rooms-mcp-connector.md). Coverage: `rooms-mcp.test.ts`; built proof: `node --import tsx scripts/prove-rooms-mcp.mjs`.

- Connector offers retain decision-time validity checks. There is no timeout sweep or stored expiry wake; actual connector completion events settle their offers.

- **Unfinished app sign-ins stay out of Connectors.** `workspace_apps.authorised_at` retains successful authorization across reconnects; the schema preserves known legacy successes from verified managed accounts, linked connection history, usage and connected chat cards. `unfinished-app-sign-ins.ts` deletes only abandoned, never-authorized managed sign-ins in maintenance batches, after failing pending chat cards; vault keys are untouched. Run and report the dry-run count before applying a historical cleanup. Proof: `CONNECTORS-1` in `app-connections.integration.test.ts`, `unfinished-app-sign-ins.test.ts`, and `scripts/prove-connectors-cleanup.mjs`; Android evidence: `apps/mobile/evidence/connectors-cleanup/`.
- **Connected app tools execute only at the server boundary.** `apps/server/src/app-connections.ts` resolves the connection; Body's `list_app_tools`/`execute_app_tool` call `DaemonService` with turn authority and never hold provider tokens.
- **OAuth apps use managed sign-in before stored API routes.** A successful OAuth-support check may replace a Squire API app route; developer-client secrets and browser passwords remain visible as keys but do not suppress OAuth discovery. Existing managed OAuth and official MCP routes stay selected. Regression: `TIKTOK-ROUTE-1` in `app-connections.integration.test.ts` and `workbench-companies.test.ts`.
- **Squire API reconnect requests owner setup on the existing route when OAuth is unsupported.** An existing vault key alone cannot answer an explicit repair request with ready; `connect` retains owner consent and returns a repair goal without the old reference. Recheck normally after repairing the credential, then verify the requested provider resource. Coverage: `SENTRY-ACCESS` in `app-connections.integration.test.ts`.
- **Registry discovery and installation use the connection policy** (`mcp-registry.ts`; OAuth in `apps/body/src/registry-mcp.ts`). Connector search queries the Registry for every term and probes only known company domains (`company-mcp-discovery.ts`, public DNS pinned to HTTPS sockets, bounded cache/timeouts). Foreground reads never await these probes: `connector-discovery-cache.ts` commits shared public snapshots before owner-scoped live invalidation; the phone re-reads the current search in place without polling. Official company matches suppress third-party matches for that company. A person's explicit verified MCP selection may replace a Squire API app route while preserving vault keys; automatic/agent routing and Composio routes retain their policy. Registry grouping uses publisher namespaces, never claimed websites. Automatic `connect` selection requires the app’s official publisher namespace; exact agent installs also reject protected app claims from other publishers. The phone and agent paths share `mcp-registry-policy.ts`, including Google product aliases. Regression: `R-YOUTUBE-PUBLISHER` in `app-connections.integration.test.ts`; isolated built HTTP proof: `node --import tsx scripts/prove-youtube-publisher.mjs`. Proof and limits: [MCP discovery](../apps/mobile/evidence/mcp-discovery/README.md), `company-mcp-discovery.test.ts`, `app-connections.integration.test.ts` (`MCP-DISCOVERY-1`).
- **Connection receipts DM only what needs a human** (`ConnectionUsageRecord.eventClass`). Agents use `find_connectors` to settle a service and `connect` for server-owned setup in any surface. Legacy `offer_connector` and `connect_app` aliases stay hidden for one release. `pairConnector` re-arms a conflicting row. A Squire `google_session` wall becomes an in-Room reconnect card.
- `external-mcp-capabilities.ts` stores only the profiles `squire-credential-use`/`squire-app-access`; Squire spend verbs need an owner-signed one-use envelope.

## Object storage

- Pending agent attachment queues clear transactionally with corner archival. No attachment retention sweep, deadline discovery or timer exists. Reads retain existing expiration tombstones; explicit deletion retains its existing behavior (`object-service.ts`, `corner-lifecycle.test.ts`).

- `apps/server/src/object-storage.ts` is the one SigV4 client (Fly Tigris); `object-service.ts` owns rows. Account deletion attempts each owned object once in bounded batches; a storage refusal preserves the account and durable object keys for a separate explicit deletion request (`account-deletion.test.ts`). Upload retention metadata lives in `media-ttl.ts`: person uploads `MEDIA_TTL_HOURS` (24), agent artifacts `ARTIFACT_TTL_HOURS` (7 days). There is no automatic storage cleanup. An object with an existing expiration tombstone answers 410 `media_expired` from the `object_expirations` tombstone, and the UI says "expired", never "failed". `post_artifact` validates per MIME in `artifact-validation.ts` (≤ `ARTIFACT_MAXIMUM_BYTES`).
