## Branch conventions

- `fm/*` feature branches often stack on each other (PR base is another `fm/*` branch, not always `main`) — check `gh pr list --json baseRefName,headRefName` before assuming a task's target file exists on `main`.
- The local-only `fm-integration-verify` branch (many `fm/*` branches merged together for cross-branch verification) has a pushed origin counterpart: `fm/buzzy-integrated`. If a task references a file that doesn't exist on `main`, check `fm-integration-verify`/`origin/fm/buzzy-integrated` before concluding the task's premise is wrong; find the originating single `fm/*` branch with `git branch -a --contains <commit>` to pick the correct PR base rather than opening against `main`.
- Cherry-picking a single commit off a `feature/*` branch that has other, superseded commits ahead of it in the same lineage: the target commit's diff can still reference state (a JSX identifier, a style key) introduced by one of those earlier, unwanted commits, because that state is unchanged context between the cherry-picked commit and its parent and so is never part of the applied patch. `git cherry-pick` resolves the surrounding hunks fine but silently omits the declaration, leaving a dangling reference — `npm run typecheck` catches it (`Cannot find name`), but a plain merge-conflict resolution pass will not. Diff the target commit against its own parent (`git show <parent>:<file>` vs `git show <commit>:<file>`) to see exactly what it adds versus what it merely touches as context, and drop the JSX/state that belongs to the unwanted ancestor commit rather than reintroducing it.
- Reconciling two independent corner branches that each add a new trailing optional parameter to the same shared function (e.g. two different `feature/*` branches both extending `activity.ts`'s `buildAgentMessage`/`postAgentMessage` signature) produces a real conflict on the parameter list, not an auto-mergeable one — git cannot infer the combined order. Resolve by grepping every call site of the function on the pre-merge `origin/main` (`git show origin/main:<file> | grep -n '<fn>('`) to see which positional slot each already-auto-merged caller (git 3-way merges call sites cleanly even when the signature itself conflicts) assumes for its own new argument, then place each conflicting branch's parameter to match what call sites already assume rather than inventing an order and having to re-edit every call site afterward.
- Merging `origin/main` into a stale `fm/*` PR branch: the only conflicts are usually the committed generated release-bundle artifacts under `relay-stack/web/dl/` (`beeline-linux-x64.tar.gz`, its `.sha256`, `manifest.json`) — `git merge` reports "Cannot merge binary files" plus a text conflict inside `manifest.json`'s hash/byte-count fields, even when every real source file (`apps/body`, `apps/mobile`, `packages/buzz-client`) auto-merges cleanly with no conflict markers. Don't hand-resolve the binary/hash content — pick either side to unblock the commit (content is stale regardless of pick), then regenerate for real with `npm ci && npm run bundle:beeline` and commit the freshly built artifacts in a follow-up commit; the sha256/bytes will differ from both merge parents since they now reflect the merged source tree.

## Body (@beeline/body) — agent session manager

- `apps/body/` — agent body service (see `apps/body/README.md`).
- **Room delivery is WS-push, not polling**: `Body.runRoomPushLoop` (`apps/body/src/body.ts`) holds one authenticated WS subscription per Room (`since`-cursor reconnect, HTTP `pollChannelRequests` only as a one-shot backstop after each (re)subscribe, plus a low-rate maintenance timer for child steering/merge closure). `WorkspaceSupervisor`'s watchdog (`apps/body/src/supervisor.ts`, `DEFAULT_ROOM_WATCHDOG_STALE_MS`) force-recycles a Room whose `lastPollAt` goes stale — so the push loop must keep calling `onRoomPollSuccess` for the *life* of a healthy socket, not just once at subscribe time: it fires on every delivered event and on the maintenance tick whenever `client.socket?.connected`. Getting this wrong (as the original WS-push landing on `main` did) makes a perfectly healthy, silent WS Room get killed and reconnected every `watchdogStaleMs`, which is a self-inflicted request-volume storm, not an ingress problem — see `room-ws-push.live.test.ts` and the liveness-signal test in `body.test.ts`.
- **One mention → at most one corner**: `Body.processChannelRequestEvents` (`apps/body/src/body.ts`) is entered concurrently for the same relay event — the WS-push delivery callback and the one-shot HTTP backstop query above both call it, and `pollRoomMaintenance`'s per-tick invocation can overlap a still-running prior tick. The relay-backed `requestAlreadyOpened` idempotency check has a network round-trip race window, so two concurrent calls can both pass it and both call `openSubchannel`, producing duplicate corners from a single mention. `inFlightRequestIds` (a same-process `Set`, checked-and-set synchronously with no `await` in between, released in a `finally`) closes this: the loop body is claimed per event id before any async work, so a second concurrent call for the identical event id no-ops instead of racing. It is deliberately separate from `processedRequestIds` (only set on success, so a failed attempt still retries on a later poll) — see the "creates exactly one corner" test in `body.test.ts`.
- **Query retry policy**: `packages/buzz-client/src/http.ts`'s `requestQueryEvents` retries 5xx/transport errors (3 attempts, 10s/attempt, linear backoff), mirroring `apps/gate/src/relay.ts`'s `createRelayClient().queryEvents` so every `createBuzzClient()` read (mobile + Body's non-`agentRelay` call sites) tolerates a transient ingress 502/429 instead of failing the turn. `WorkspaceSupervisor.reconcile`'s membership/role reads (`isMember`/`listMembers`/`latestRoleProjection` in `packages/buzz-client/src/channel.ts`) go through this same `queryEvents`, so they inherit the retry for free.
- **Query volume attribution (off by default)**: `http.ts`'s `queryEvents()` carries built-in call-site instrumentation — `getQueryInstrumentation()` / `setQueryInstrumentationEnabled()` / `resetQueryInstrumentation()`, or `BUZZ_QUERY_INSTRUMENT=1` in a Node process like Body. `networkRequests` counts actual `/query` POSTs 1:1 with relay access-log lines; `callSites` groups logical `queryEvents()` calls (cache hits included) by `{kinds, tagKeys, callerLabel}` via a best-effort stack-trace label, so it's always >= `networkRequests` — that gap is the batching/caching win, not a bug. Zero-cost when disabled (single boolean check). Immutable-read caching in the same file (`queryCacheTtl`) also covers a single scoped kind:39000 metadata read once non-empty (same 5-minute TTL as a scoped kind:9007 create), and a genuinely-unscoped scan (no `#h`/`#d` — e.g. `listSubchannels`'s child-discovery scan) gets 10s instead of 500ms.
- **`waitUntilMember`/`waitUntilMemberRole`/`waitUntilNotMember`/`waitUntilRoomArchived` (`packages/buzz-client/src/channel.ts`) are WS-primary, not fixed-cadence pollers**: the shared `waitForRelayProjection` helper subscribes to the relevant 39000/39001/39002 kind(s) scoped to the channel (`#d` and `#h`, matching this file's existing dual-tag read fallback) over `ChannelOpsContext.ws` — an optional live-socket accessor `BuzzClient` wires to its own `this.ws` in `client.ts` — and re-runs the same `isMember`/`getChannelRole`/`getChannelMetadata` check whenever a live event arrives, instead of polling every 300ms. WS is opportunistic only (gated on `ws.connected`, never forces a connect): a `RELAY_PROJECTION_BACKSTOP_POLL_MS` (5s) poll of the same check runs concurrently for the whole wait as the correctness backstop, so an absent/never-authenticated/dropped socket just resolves on the next backstop tick instead of stalling — same technique as `apps/body`'s `waitForWritePermissionDecision` below. A raw hand-built `ChannelOpsContext` with no `ws` field (e.g. `Body.agentClientContext()`) transparently falls back to the original fixed-interval loop, which is why that one Body call site and `apps/gate`'s separate HTTP-only client were deliberately left unwired rather than migrated — see `channel.test.ts`'s `waitUntilMember (WS-driven)` suite for both paths.
- **`query(ctx, filters)` (`packages/buzz-client/src/query.ts`) is the WS-primary read funnel every `queryEvents(ctx.http, ...)` call site in `channel.ts`/`community.ts`/`agent.ts`/`direct-message.ts`/`person-profile.ts`/`repo-room.ts`/`client.ts` now goes through**: opportunistic on `ctx.ws?.().connected` (same gate as `waitForRelayProjection` above — never forces a connect, so cold-start reads stay on HTTP), one-shot NIP-01 REQ→EOSE via `wsQueryEvents` (`ws.ts`) on any hit, HTTP `queryEvents` fallback on literally any WS failure (no WS, not connected, throw, timeout, or a close before EOSE). `enqueueWsQueryEvents` in `query.ts` ports `http.ts`'s same-tick microtask batching (`canPartitionFilter`/`selectQueryEvents`, both exported from `http.ts` for reuse) so concurrent same-tick `query()` calls on the same socket collapse into one multi-filter REQ, split back apart per caller exactly like the HTTP batcher. **Sharp edge proven by a live regression test (`ws.test.ts`)**: `wsQueryEvents` must call its `subscribe()` unsubscribe on every exit path (resolve/timeout/close) or the one-shot REQ's subId is left in `RelayWs.subscriptions` and gets wrongly replayed as a live REQ by a later reconnect's `resubscribeLiveRequests()`. `community.ts`'s `findCommunityInvite` is deliberately NOT wired to this funnel — it takes a bare `http`/`readerPubkey` pair (invite redemption can run before a full `ChannelOpsContext`/socket exists), not a `ctx`, so it stays HTTP-only. `apps/gate`'s independent HTTP-only client is likewise untouched (still no WS support there — see `waitForRelayProjection`'s note above).
- **`Body.isRoomAgentOnline()`'s presence cache cannot reuse `roomSockets`**: `apps/body/src/body.ts`'s `presenceCaches` (keyed by channelId; each entry owns its own `createBuzzClient()` + `agentPresenceSubscribe` subscription, seeded once via a single `agentRelay.queryEvents` read since a fresh subscribe's backfill replay isn't guaranteed to have landed yet) exists because its sole caller, `processChannelRequestEvents`'s agent-exchange online/offline gate, is reachable both from `runRoomPushLoop`'s live socket (where `roomSockets.get(channelId)` is populated) *and* from `pollChannelRequests` called directly with no push loop running at all — every live test exercising this path (`agent-exchange.live.test.ts`) does exactly that, so `roomSockets` is not a reliable source there despite looking like a "straight swap" target. Torn down in `dispose()` alongside `roomSockets`.
- **Reconcile never crash-loops the fleet**: `WorkspaceSupervisor.run` (`apps/body/src/supervisor.ts`) wraps each `reconcile()` call in try/catch — a reconcile rejection (e.g. the relay retry budget above is exhausted) backs off via `reconcileRetryMs` and loops again instead of throwing out of `run()`. Because the failure happens before `reconcile()` ever touches `this.running`, already-active Rooms/corners are untouched by a failed tick. Coverage: `apps/body/src/supervisor.test.ts` → `WorkspaceSupervisor transient relay resilience`.
- **`reconcile()` is wake-driven, not a 5s forever poll**: `WorkspaceSupervisor.run` (`apps/body/src/supervisor.ts`) opens one persistent control-plane WS per daemon subscribed to `{kinds:[KIND_PUT_USER, KIND_REMOVE_USER], '#p':[agent.publicKey]}` (9000/9001, the durable NIP-29 mutation log) and calls `reconcile()` only on startup, on a pushed event, or every `reconcileHeartbeatMs` (default `DEFAULT_RECONCILE_HEARTBEAT_MS` = 60s) as a correctness backstop — not every `pollMs` tick. **This is deliberately 9000/9001, not the 39001/39002 role projections**: a removal republishes the projection *without* the agent's `p` tag, so a `#p`-filtered subscription on the replaceable projection would never notice its own removal; the raw put/remove-user event always carries the affected pubkey. The Room watchdog stays on the tight `pollMs` tick (default 5s) since it only reads already-local `RunningRoom` timestamps — no relay cost either way, so decoupling its cadence from `reconcile()`'s costs nothing. If the control-plane WS never connects (or drops), `run()` logs and falls back to the heartbeat alone; it must not call `.disconnect()` on a client whose `.connect()` never resolved (`supervisor.test.ts`'s existing `mocks.createBuzzClient.mockReturnValue({...})` fixtures reuse one shared mock object across every `createBuzzClient()` call in a test, including this new control socket, so an unconditional `finally`-block disconnect there would silently double the disconnect count and break unrelated assertions). Coverage: `apps/body/src/supervisor.test.ts` → `WorkspaceSupervisor control-plane wake signal`.
- **Write-permission decisions resolve off the Room's own WS first, HTTP poll is the backstop**: `Body.waitForWritePermissionDecision` (`apps/body/src/body.ts`) subscribes on `this.roomSockets.get(tlcChannelId)` (the same live socket `runRoomPushLoop` already holds open) for the `WRITE_PERMISSION_RESPONSE_TAG` kind:9 event, instead of polling `agentRelay.queryEvents` every 500ms. The WS path is opportunistic only — a `WRITE_PERMISSION_BACKSTOP_POLL_MS` (5s) HTTP poll runs concurrently for the whole wait regardless of socket state, so a Room driven without a live socket (e.g. `pollChannelRequests` alone, as `room-conversation.live.test.ts` does) still resolves correctly, just off the backstop instead of instantly.
- **Read-only boundary = ACP mode + MCP capability boundary**: Room sessions request a supported read-only ACP mode and mount only Beeline's `buzz-readonly-mcp` (`apps/body/src/read-only-mcp.ts`), whose fixed repository-contained list/read/literal-search/local-history tools expose no shell, raw git args, or mutation. Pure information requests are locked to read-only Room answers and cannot project ALLOW even if the agent asks for a mutating permission. An explicit human open-a-corner command creates the isolated edit corner directly; for non-research work, the first actual mutating ACP request requires a current human member to sign ALLOW. A repo-less normal Room must name an exact `owner/repo` in that signed request and may materialize it only after ALLOW; no target, DENY, or clone failure stays read-only. Edit sessions alone mount `buzz-dev-mcp`. Each human-triggered Room turn includes attributed recent messages from every participant. Non-addressed and agent-authored messages remain context-only except for a signed human-opened peer exchange: `apps/body/src/body.ts` authenticates the opening event and caps the visible exchange at two messages per agent; `apps/body/src/agent-exchange.live.test.ts` is the relay-backed proof. All other agent-to-agent turns remain disabled. Authority: `apps/body/src/body.ts` (`isReadOnlyInformationRequest`, `isChannelWorkIntent`, `replyInRoom`) and `apps/body/src/repository-target.ts`.
- Body drives `buzz-agent` directly over stdio (NOT `buzz-acp`), because `buzz-acp` auto-approves permissions and doesn't expose `session/update` to the relay.
- **`ROOM_AGENT_PROMPT_TIMEOUT_MS` (`apps/body/src/body.ts`) is an idle window, not a hard cap on turn length.** `AcpClient.sessionPrompt` (`apps/body/src/acp.ts`) re-arms the timeout on every `session/update` for that session (message chunk, tool call, anything) via `resetPendingIdleTimeout`; only zero activity for the whole window cancels + force-suspends the session. This covers both the quick read-only Room reply path and the long corner edit-session path since both go through `Body.promptAgent`. A fixed (non-idle) deadline here previously killed every corner task past ~1 minute regardless of progress — see `acp.test.ts`'s "does not time out a turn that keeps streaming activity past the idle window" / "cancels a turn that goes fully idle" tests for the contract.
- **A stalled backend gets an honest early notice and a bounded blind-retry cap, both layered on top of the idle timeout above, not a replacement for it.** `Body.promptAgent` arms a much shorter `ROOM_AGENT_STALL_NOTICE_MS` (20s) timer off `AcpClient.sessionPrompt`'s new `onActivity` hook — the identical per-`session/update` trigger `resetPendingIdleTimeout` already uses — so it only fires on genuine zero-output inactivity and never on a slow-but-active turn; on fire it publishes a one-time `postAgentStallNotice` (`apps/body/src/activity.ts`) as an ordinary visible message, so the stall is visible tens of seconds in, not only after the full `ROOM_AGENT_PROMPT_TIMEOUT_MS`. Separately, the two call sites that retry a failed turn from scratch on a later poll — `processChannelRequestEvents` (Room turns) and `pollMembers` (corner follow-ups) — now read the attempt count `DurableBodyState.failed()` already tracked but nothing previously consulted, and once a genuine ACP idle-timeout (`isAcpPromptStallError`) has recurred past `ROOM_AGENT_STALL_MAX_ATTEMPTS` (3), they stop rethrowing and instead mark the item delivered/processed and publish a clean terminal failure — otherwise a wedged backend was re-driven from a brand-new session on every poll forever. Corner-open (`startAgentTask`) is a one-shot task with no retry loop above it, so it only picks up the stall notice, not the cap. See `body.test.ts`'s "surfaces an honest stall notice…", "never surfaces a stall notice for a turn that keeps producing genuine ACP activity…", and "bounds a stalled backend's blind retry loop…" tests.
- Activity projection: body bridges ordered ACP `session/update` batches → kind:9 `#t=agent-activity` channel events for multi-user visibility without exhausting per-key relay quotas. Read-only Room turns also publish `#t=agent-turn` working/complete lifecycle events for the mobile thinking indicator. Room daemon liveness uses one parameterized-replaceable `#t=agent-presence` record per agent/Room with a bounded freshness lease; presence and turn events share a daemon-generation ID so an old `working` event cannot revive after restart. `isAgentPresenceOnline` (`packages/buzz-client/src/agent-presence.ts`, the sole helper backing the mobile "AGENT OFFLINE" banner, the corner presence dot, and `Body.isRoomAgentOnline()`) checks `|now - observedAt| <= AGENT_PRESENCE_STALE_MS`, not a one-sided `now - observedAt >= 0` — the daemon and the reader are independent clocks, and a one-sided check makes every heartbeat look "future" forever (banner stuck offline for a genuinely live, actively-replying agent) whenever the daemon's clock merely runs a little ahead of the reader's. `apps/body/src/activity.ts` owns these wires and the narrow Codex startup-warning filter. Within a batch, only *terminal* load-bearing tool calls (`kind` in `edit`/`delete`/`move`, or an `execute` whose command isn't a plain inspection like `grep`/`git diff`) or any `failed` status are projected onto the wire at all; pending/in-progress chatter, reads/searches, MCP calls, and `agent_thought_chunk`/`plan` reasoning steps stay background telemetry and are dropped, never merged. A surviving tool call is projected as `compactActivityUpdate`'s full `tool_activity` record (redacted command/input/output/files/plan, per `SENSITIVE_ACTIVITY_KEY`) — built from a shallow merge of that toolCallId's creation event (`kind`/`title`/`rawInput`, hence files/diff) and its terminal event (`status`/`output`), tracked in a per-projection `toolCallRaw` map — with `title`/`status` then overridden to the concise human label, so the one-line summary stays readable while the full detail remains available for the mobile corner drill-down (`ActivityTimeline.tsx` → `buildTurnActivity` in `apps/mobile/sources/buzz/activity-timeline.ts`: tap a turn's one-line `activity_summary` to see its file/tool list, tap an entry for the diff or command+output). A synthetic `activity_summary` update (short "Edited X; ran Y" text) is appended whenever a batch has at least one major action. Assistant prose remains a separate `#t=agent-message` publish, never duplicated into activity. **Presence has no Workspace-wide record** — only the per-(agent, Room) one above — so the Workspace-scoped Agents directory (`apps/mobile/sources/app/(app)/buzz/MembersScreen.tsx`) can't reuse a single-Room presence read like the Corner list or Room roster do. `BuzzRigTransport.agentPresenceBackfillForWorkspace(communityId)` (`apps/mobile/sources/sync/transport/buzz-rig-transport.ts`) derives it instead: `client.communityChannels(communityId)` for every Room the Workspace has, then one multi-`#h` `client.query` for `KIND_AGENT_PRESENCE` across all of them (same proven cross-Room `#h` pattern as `fetchManyRoomsLifecycle`) — an agent online in any Room reads online in the directory; an agent live nowhere (a stopped daemon, e.g. a dormant paired agent) correctly reads offline without being removed from the list.
- Live text streaming (true incremental, not reveal-on-arrival): `AcpClient.sessionPrompt`'s optional 4th arg (`apps/body/src/acp.ts`) fires per `agent_message_chunk` delta — the ACP boundary, so it's harness-agnostic; a harness that never emits chunks just never calls it. `Body.promptAgent`'s optional `stream` param wires this into `createDraftStreamer` (`apps/body/src/activity.ts`), which coalesces deltas on a 250ms window and publishes the growing full text as one parameterized-replaceable `#t=agent-draft` record (kind 30078, `d=agent-draft:<channelId>`, same convention as `#t=agent-presence`) via `postAgentDraft` — bounded relay write rate regardless of chunk frequency or reply length. **Sharp edge**: each flush's `created_at` must be strictly monotonic (bumped past the last one, not just `Date.now()/1000`) — streaming flushes easily land multiple times within one wall-clock second, and a same-second tie lets a relay's NIP-33 replaceable-event tie-break pick the wrong (non-newest) content; `startAgentPresence` already solved this for its heartbeat, `createDraftStreamer` reuses the same technique. Mobile subscribes via `BuzzRigTransport.agentDraftSubscribe`/`agentDraftBackfill` (parallel to `agentPresenceSubscribe`, not the kind:9 `sessionEventsSubscribe` stream), but — unlike presence — feeds each draft event through the same `projectChatEvent`/`upsertChatMessages` pipeline as ordinary messages (`[channelId].tsx`'s `handleLiveMessage`), Room/DM only (`!parentId` at install time). Live proof: `apps/body/src/streaming-draft.live.test.ts`.
- **Room/DM streaming reply is one in-transcript bubble, not a separate banner** (a prior `StreamingAgentText` bottom-panel component — now deleted — caused a "banner vanishes, new bubble appears" jump when the turn finished): `buzz-event-projection.ts`'s `projectChatEvent` projects a live `#t=agent-draft` straight into the transcript as a provisional bubble at `agent-draft-${requestId}` (`isAgentDraft: true`). Reconciliation onto the SAME bubble id when the turn's final `#t=agent-message` lands relies on a wire coincidence, not a shared explicit field: `publishAgentResult`'s Room/DM call site in `replyInRoom` (`apps/body/src/body.ts`) sets `replyTo: request.eventId`, the same value threaded as the `agent-turn`/`agent-draft` `request` tag — so the final message's NIP-10 reply-to (`replyToId`) equals the draft's `requestId`, and the projection reuses `agent-draft-${replyToId}` as the final message's id too. This does NOT hold for corners: `startAgentTask`'s `publishAgentResult` call never sets `replyTo`, which is exactly why corners are excluded from this mechanism (`[channelId].tsx` only installs the draft subscription when `!parentId`) and keep relying on the narrative-segment mechanism above instead — feeding corner drafts through this same path would leave an unreconciled, permanently-provisional bubble alongside the narrative segments. **Sharp edge**: because the display id diverges from the real relay event id for a reconciled bubble, reply-threading (`messageSubmitReply` does a relay lookup by event id) would silently break if it read `.id` — `ChatDisplayMessage.relayId` carries the real id for this case, and both `replyTargetForMessage`'s outbound `messageId` and `visibleMessageById`'s inbound lookup must read `relayId ?? id`. A second sharp edge: the draft and final message arrive over independent relay subscriptions with no ordering guarantee, so `upsertChatMessages` refuses to let a late-delivered draft flush regress an already-finalized bubble (`existing && !existing.isAgentDraft && message.isAgentDraft` short-circuits the upsert). Regression proof: `chat-event-projection.test.ts`'s "streams a Room reply into one bubble" test.
- **Corner narrative persistence (durable, not just live)**: the draft above is deliberately volatile and a corner's own end-of-turn reply is deliberately compressed (`conciseCornerTurnSummary`, ≤480 chars/3 items via `publishAgentResult(..., {concise:true})`) — neither ever commits the agent's actual mid-turn narrative anywhere durable, so a long corner turn used to leave no readable trail once it finished. `Body.promptAgent`'s `stream.narrate` option (set only by corner call sites — `startAgentTask`'s primary turn and `pollMembers`'s no-active-run follow-up/`promptNewTurn` — never Room/DM turns) additionally wires `createNarrativeCommitter` (`apps/body/src/activity.ts`) onto the same `agent_message_chunk` stream as the draft. It durably commits each completed paragraph as its own ordinary `#t=agent-message` kind:9 event via `nextNarrativeSegment`'s paragraph-boundary cut (falling back to a sentence/line boundary past `NARRATIVE_SEGMENT_MAX_CHARS` for one long run-on paragraph), so the transcript fills in as the turn runs and the text stays after it ends; the final concise `publishAgentResult` call remains as a short trailing summary, not a replacement. **Sharp edge, same family as the draft/presence one above but a different failure mode**: these are ordinary (non-replaceable) kind:9 events, so a same-second `created_at` tie doesn't pick wrong content — it lets mobile's `upsertChatMessages` id-hash tie-break scramble the segments' *display order* instead. `createNarrativeCommitter` threads a monotonic `createdAt` through the new optional trailing param on `buildAgentMessage`/`postAgentMessage` for exactly this reason — any other caller publishing more than one related kind:9 event in quick succession needs the same treatment. `publishAgentResult` also no longer throws `'agent returned an empty reply'` when concise reduction alone empties an otherwise-real reply (e.g. one that is entirely a fenced code block) — it falls back to the caller's `fallback` text instead of failing the whole turn. The monotonic sequence originally stopped at the last narrative segment: `publishAgentResult`'s own trailing summary is a *separate* publish call and on a fast turn could still land at the same integer `created_at` as the final segment, sorting the completion line before the intro. `NarrativeCommitter.lastCreatedAt()` (read only after `finish()` resolves, since `finish()` may flush one more segment) exposes that floor; `Body.promptAgent` surfaces it as `result.narrativeFloor`, and both `narrate:true` call sites (`startAgentTask`, `pollMembers`'s `promptNewTurn`) pass it to `publishAgentResult` as `options.minCreatedAt`, which bumps its own `createdAt` strictly past it — same pattern, one hop further down the chain.
- **Harness-boilerplate filtering is per-backend and composed, not a single regex**: `stripAgentReplyPreamble` (`apps/body/src/activity.ts`) is a composition of one stripper per known CLI harness (`stripCodexHarnessPreamble`, `stripPiHarnessPreamble`), applied to both narrative segments (`createNarrativeCommitter`'s `commit()`) and the corner's `publishAgentResult` turn summary — so a new harness's noise shape gets its own stripper added to the composition, not a rewrite of the existing ones. pi-acp (the ACP adapter for `pi` driving deepseek/other OpenRouter models) emits its whole startup block — version-update banner, `## Context`/`## Skills`/`## Prompts`/`## Extensions` path dumps (skill files under `~/.agents/skills/…`, the corner's own `.git/beeline/…` worktree path) — as one leading `agent_message_chunk`, exactly like Codex's skill-budget warning. **Sharp edge specific to pi's shape**: that block's own internal blank lines are themselves paragraph breaks, so `nextNarrativeSegment`'s last-break cut can land *inside* the block — a later segment can start mid-block (e.g. bare `---\n<version notice>`, or `## Extensions\n- /path\n- /path`) rather than at the true message start. `stripPiHarnessPreamble` therefore recognizes several leading entry shapes (the `pi vX.Y.Z` header, a bare known section header, the version-notice line alone, or a divider immediately followed by the version-notice line) and only treats a bullet line as boilerplate while inside a recognized section *and* the bullet body is a bare path token (`/…`, `~/…`, `npm:…`) — never a prose bullet — so a genuine narration bullet list is never eaten. Regression coverage: `apps/body/src/activity.test.ts`'s `createNarrativeCommitter` suite. **Streaming is not the bug**: pi-acp forwards every underlying `text_delta` event as its own `agent_message_chunk` notification immediately (not batched — see its `emit()`/`handlePiEvent`), and `AcpClient.sessionPrompt`'s `onChunk` (`apps/body/src/acp.ts`) plus `createNarrativeCommitter` are harness-agnostic and already commit progressively as deltas arrive; a corner that looked like "no live narration, just a noise summary" was this filtering gap, not a broken delta pipe.

## Grok Mono Hull UI theme

- **Single source of truth**: `/DESIGN.md` (repo root) is the concise, committed unified-language doc — palette, the one shape rule, identity-mark rule, the Room/Corner-are-one-system rule, motion primitives, and the two sanctioned color exceptions. Read it before any Buzz visual work; it supersedes prose description here.
- **Design tokens and mark authority**: `apps/mobile/sources/buzz/groknight.ts` owns grayscale semantic roles, the one accent (`accent`/`agentAccent`, `#d7af5f`), the one shape radius (`radius: 3` — most call sites use the literal `3`, matching the codebase's existing convention, rather than referencing the token), and the two sanctioned diff colors (`diffAdded`/`diffRemoved`, `#3FB950`/`#F85149`, also mirrored in `theme.ts`'s legacy `darkTheme.colors.diff` for the background-tint values `ChangeReviewPanel.tsx` still reads from there). `apps/mobile/sources/buzz/brand.json` owns the light mark color; `apps/mobile/sources/buzz/beeline-mark.json` locks the approved continuous-line outline used by in-app and SVG assets. Regenerate platform art and both theme lockups with `apps/mobile/scripts/generate-monochrome-assets.sh`.
- **Design authority**: Grok Mono Hull. No chromatic state or brand color survives in Buzz except the two DESIGN.md exceptions. State is redundant through text, glyph, contrast, geometry, faint deterministic texture, reduced-motion-aware mechanical signals, and haptics. A box (border+fill+radius) only ever wraps something the user must find and act on, or a small number of genuinely distinct non-repeating regions (merge-approval panel, a safety notice) — never a repeating content unit (chat message, list row, avatar); those get whitespace and, for list rows only, a single hairline divider (`MonoHull.tsx`'s exported `hairlineDivider` style — spread it into a row's own style rather than re-declaring `borderBottomWidth`/`borderBottomColor` inline). Shared primitives live in `apps/mobile/sources/components/buzz/MonoHull.tsx`.
- **Rooms and Corners render one transcript row**: `chat/[channelId].tsx`'s `TranscriptRow` (local component, just above `export default function BuzzChat()`) is the single row both a top-level Room and a Corner render — no per-message bubble/box, a small (18px) faceted avatar, a `›`/`·` glyph, and an uppercase mono label that names *who* (not a category word) via the same `isOwn ? 'YOU' : display ? display.name : personName` precedence used everywhere else identity is resolved. The only structural difference is `terminalTurnUser` (a human's own short message: right-aligned, inset, still boxless) — never a separate component per surface. If a future change needs Room- or Corner-only structure, that's a real design fork and should get a fresh audit pass, not a silent re-divergence of this component.
- **Identity marks are one faceted-polygon family**: `AgentAvatar`/`PersonAvatar`/`WorkspaceAvatar` (`apps/mobile/sources/components/buzz/`) all render deterministic, seed-derived, all-`Polygon` SVG marks with no `Circle`/`Ellipse` and a small near-square frame radius (`size * 0.08`, `Math.max(2, size * 0.08)` for the two smaller marks) — `PersonAvatar` was re-skinned from a circle+ellipse "flower" to a 12-sided frame / hexagon core / tapered-kite-shard mark to match; it stays visually distinct from `AgentAvatar` by silhouette (radial rosette vs. bilateral drone) and by omitting gold (gold accent strokes are Agent-only). The geometry-derivation files (`agent-avatar.ts`/`person-avatar.ts`/`workspace-avatar.ts`) keep their historical filenames/comments describing bee/flower/honeycomb geometry deliberately (renaming is churn with no visual payoff) even though the rendered output is now uniformly mechanical/faceted. **The kind:0 `picture` field is deliberately ignored on all three**: `groknight.photoIdentityMarksEnabled` (`groknight.ts`) gates the relay-photo render path in `AgentAvatar`/`PersonAvatar`/`WorkspaceAvatar`, hardcoded `false` — a kind:0 `picture` must never override the faceted mark on these identity surfaces (an on-device agent profile photo doing exactly that was the bug). Flip the one flag, not per-component logic, if photos are ever reinstated; each component's test file asserts a profile *with* a picture still renders `Polygon`s, not an `Image`.
- **Restyled screens**: `buzz/channels.tsx`, `buzz/chat/[channelId].tsx`, `buzz/onboarding.tsx` — session/channel list, live session transcript with merge controls and composer, and key onboarding.
- **Mono-font governance**: `apps/mobile/sources/components/buzz/Typography.test.ts` enforces that `Typography.mono(...)` is only used by an allowlisted set of style names across the Buzz screens (commands, handles, roles, other deliberate machine identifiers). A new mono-styled `Text`/`TextInput` style needs its name added to that Set, and a style name removed from a screen should be pruned from the Set too.
- **Font system is exactly IBM Plex Sans + IBM Plex Mono + Bricolage Grotesque**: the vendored Happy template's `SpaceMono` font (`_layout.tsx`'s `useFonts`/`Fonts.loadAsync`, `Typography.ts`'s `FontFamilies.legacy`) was unused anywhere in the Buzz surface and has been removed along with its asset — don't reintroduce a `SpaceMono`/`legacy.spaceMono` reference for Buzz work; `legacy.systemMono` (the platform monospace fallback) is unrelated and stays.
- **`HullWaveSignal` (`MonoHull.tsx`) is the live-state motion primitive**, wired into both the corner composer footer (`chat/[channelId].tsx`'s `cornerFooterRow`, replacing the plain `sessionState === 'working'` text with `<HullWaveSignal compact label="LIVE" />`) and `MembersScreen.tsx`'s pairing "WAITING" state. It renders its own label as a `Text` child inside a `View`, so it must sit as a row sibling next to other `Text` nodes, never nested inside a `Text` run.
- **Android sharp edge — nested Text-in-flex-row goes blank**: a `flex:1` `<Text>` that only wraps other `<Text>` (no plain string child) as a sibling inside a `flexDirection:'row'` `<View>` renders zero-height/invisible text on-device (marker/glyph siblings still show, since they're plain fixed-width `Text`) — this hit `MonoMarkdown.tsx`'s list-item rendering. `react-test-renderer` does not reproduce it (its JSON tree still contains the text regardless of native layout), so a regression test must assert structure, not content-presence — see the `topLevelTextGroups` helper in `apps/mobile/sources/components/buzz/MonoMarkdown.test.ts`. Fix: put the marker and body inline segments as children of the *same* `<Text>` (nested Text-in-Text lays out fine; Text-flex1-in-row-View does not) instead of splitting them across sibling Text nodes in a row View.
- **Diff added/removed coloring is a deliberate, in-code-documented exception to Grok Mono Hull's zero-chroma rule ("captain override"), not a violation to grayscale-ify.** `ChangeReviewPanel.tsx`'s `diffAddedLine`/`diffRemovedLine` and `ActivityTimeline.tsx`'s `diffAdded`/`diffRemoved` (its own inline per-file diff drill-down) both source the same conventional green/red from `darkTheme.colors.diff` (`theme.ts`, Happy's legacy palette) — one shared source, not two independently hand-picked palettes, after a fix that found `ActivityTimeline.tsx` had drifted onto a second, slightly different pair of hex values. Hunk headers and context lines stay on the neutral grayscale palette in both (`groknight.bgHover`/`bgTerminal`, `groknight.textMuted`/`textSecondary`) — only added/removed lines get color; `groknight.ts`'s `danger`/`success` tokens still deliberately share one gray, since that rule has no carve-out for chrome/state elsewhere in the app. **Corner change-review diff (`ChangeReviewPanel.tsx`) does not use the legacy Happy diff renderers** (`components/diff/PierreDiffView.tsx`, `DiffView.tsx`) despite sourcing the same color values — those components render a different diff UI shape entirely, not because of the color exception. The per-file diff sits inside the parent Room's *inverted* transcript `FlatList` (as `ListHeaderComponent`). **Android nested-scroll direction matters**: a vertical `FlatList` nested inside a horizontal `ScrollView` never receives vertical drags on Android regardless of `nestedScrollEnabled` — that shape (shipped in #173) left the diff unscrollable vertically. The working shape is vertical-outer, horizontal-inner: a bounded (~300px) vertical `ScrollView` (`testID="change-review-diff-scroll"`, `nestedScrollEnabled`) wrapping a horizontal `ScrollView` (`nestedScrollEnabled`) wrapping a plain column of `Text` rows — same-axis nesting (vertical diff inside the vertical transcript) hands the gesture off correctly via `nestedScrollEnabled`, cross-axis does not. Rows are plain `Text`, not a virtualized `FlatList` (the previous vertical `FlatList` is exactly the piece that broke), capped at `DIFF_MAX_RENDERED_LINES` (1500) with a truncation footer to bound memory; long lines use `numberOfLines={1}` plus an explicit width estimated from the longest line (`DIFF_CHAR_WIDTH_PX`) rather than wrapping, so the horizontal `ScrollView` has real content to scroll.

- **Chat transcript list** (same `[channelId].tsx`): the `FlatList` is `inverted` (data newest-first) with `maintainVisibleContentPosition`, seeded synchronously from `local-cache.ts` on mount so history is on screen on first paint. There is no manual `scrollToEnd`/`onContentSizeChange` scroll-following — inversion keeps the tail pinned for free; reintroducing that hack was the root cause of a cluster of on-device-only bugs (empty-then-fill, blank space past the last message, jitter, send freeze) that only reproduced on a cold open of a room with real history. History opens on a short recent window (`INITIAL_MESSAGE_WINDOW`) and pages older messages in via `onEndReached` (`loadOlderMessages` in `local-cache-sync.ts`, kept out of the shared cache's recent-tail bound). `ListHeaderComponent` (not `ListFooterComponent`) holds content meant to sit near the composer, since inversion swaps their visual position. `buzz/activity-timeline.ts` collapses ACP tool/search/reasoning telemetry into sparse Claude-Code-style rows, folding a repeated action title into its first row even across other actions in the same turn.
  `maintainVisibleContentPosition` uses `{ minIndexForVisible: 1, autoscrollToTopThreshold: 50 }`, mirroring `apps/mobile/sources/components/ChatList.tsx`: anchor index 0 (the newest row) is volatile — replaced on every send (optimistic id → real event id) and every agent stream token — so anchoring there fights revealing a just-sent message (worst on multi-line sends, where the composer also collapses in the same commit); anchoring index 1 plus the threshold gets native stick-to-bottom instead. Do not add a JS-side `scrollToOffset` alongside it — the two fight and drag the viewport while reading older messages mid-stream. Live session events are batched per animation frame through `cacheLiveSessionEvents` (`local-cache-sync.ts`) rather than one `cacheLiveSessionEvent` call per raw event — the latter's per-call cache rebuild+sort is O(n log n) and a burst of per-token corner activity events calling it individually can saturate the JS thread and read as a send/UI freeze.

Presence (online/offline) and turn activity ("thinking…") are separate, secondary signals and must never replace the lifecycle word. Corner-card agent identity is resolved via `resolveCornerCardAgentPubkey` (`apps/mobile/sources/buzz/agent-display.ts`), preferring the declared `agent` tag but falling back to the event's own signer pubkey when that tag misses the registered-agent roster. This same declared-tag staleness applies to `ChatDisplayMessage.agentTurn.agentPubkey` (also a declared `agent` tag, projected in `buzz-event-projection.ts`), so the corner view's OWN header identity (`[channelId].tsx`'s `cornerAgentPubkey`) must not trust it unconditionally either — `resolveCornerViewAgentPubkey` (`apps/mobile/sources/buzz/corner-session.ts`) applies the identical roster-preferring precedence over the transcript's `agentTurn` messages, so a stale declared pubkey on one message can't force a pubkey-hash placeholder name (e.g. "Alden") when a later message in the same corner is actually signed by the current registered agent. Any new agent-identity read of a corner's transcript should go through one of these two helpers rather than reading `agentPubkey`/`pubkey` fields directly. The room-list sidebar re-derives its corners via `listSubchannelLifecycle` on every `channels.tsx` *focus* (fresh relay read, correct), but `ChannelDisplayItem.corners` is otherwise a once-fetched snapshot held in `useBuzzLocalCache`'s `channelLists` entries — a corner that gets archived while the screen stays mounted and focused (no new focus event fires) kept showing its pre-archive status. The corner view's OWN header badge (`[channelId].tsx`'s `cornerLifecycleStatus`, `testID="corner-view-status"`) has the identical exposure: it is a one-time snapshot fetched at mount, with no live-update path of its own, unlike `isArchived` on the same screen (kept current by four independent signals — live archive event, initial `messageSync.archiveChannel`, initial `isChannelArchived` check, and `isArchived` never regresses once true). A screen that stays mounted across an archive (very possible — RN/Expo Router does not tear down a backgrounded/covered screen) can show a stale non-terminal status indefinitely on either surface. Two fixes close this: `resolveCornerLifecycleStatus` (`corners.ts`) forces the corner-view badge to `'archived'` once `isArchived` is confirmed, using the `cornerStatusPrecedence` ordering (`archived` outranks `merged`) so a confirmed archive can never render as less-terminal than a stale snapshot; and `applyCornerStatusSignals` (`local-cache-sync.ts`, called from both `cacheLiveSessionEvents` and `performMessageRevalidation`) mirrors every `.corner`-tagged signal it already sees for a Room's own transcript into that Room's sidebar `corners` entry via the new `patchCornerStatus` store action / `updateListCornerStatus` (`local-cache.ts`) — precedence-guarded, and it only ever updates an *already-listed* corner, never fabricates one from a bare signal. The room-chat inline card (`.corner` messages merged straight into the reactively-cache-driven message list via `upsertChatMessages`'s own precedence guard) was already correct on both the live-event and revalidation paths — verified, not assumed, with a passing-either-way test in `local-cache.test.ts` before any sidebar fix was written.

## Android push notifications

- App registration lives in `apps/mobile/sources/push/buzz-push-registration.ts`; runtime defaults/overrides are in `app.config.js` and `sources/buzz/runtime-config.ts`. The public gateway default is `https://push.buzzrouter.com`.
- Notification presentation authority is `apps/push-gateway/src/mapping.ts`; cached recipient-authorized Room/sender resolution is in `metadata.ts`. Message previews are intentionally lock-screen-visible, while Android `tag`/FCM collapse keys replace rapid updates per Room.
- At-most-once delivery authority is `apps/push-gateway/src/delivery-state.ts`: event/recipient attempts are durably reserved before FCM, delivered results and per-recipient cursors survive restarts, and bounded history cannot reopen old backlog. `mapping.ts` + `metadata.ts` fail closed to persistent Workspace-linked Rooms and suppress fixture/test Room, repository, Workspace, and marker signals. `npm run verify:live -w @beeline/push-gateway` proves fixture=0, real=1, restart/replay=0 additional payloads with an isolated identity and no FCM client.
- Gateway authority and operations: `apps/push-gateway/README.md`; durable production deployment is `apps/push-gateway/deploy/README.md`. Production reads use a host-loopback-only, query-only trusted relay sidecar that preserves the relay's per-recipient channel ACL, while event wakeups stay on the public auth-enforced relay. Credentials and device tokens must never be logged or committed.
- Gateway checks: `npm run build -w @beeline/push-gateway && npm test -w @beeline/push-gateway`.

## Community model

- SDK authority: `packages/buzz-client/src/community.ts`; gate convention + live proof: `apps/gate/src/community.live.test.ts`.
- Workspace pictures use the existing admin-gated kind:9002 metadata command and relay-signed kind:39000 projection; kind:9007 stays immutable and supplies the owner plus fallback picture. The relay's current projection preserves the namespaced picture URL through `purpose`; `community.ts` owns this compatibility convention.
- A community reuses NIP-29 group state: kind:9007 stream create with a self-referencing `community=<h UUID>` tag, kind:9000 roles, and 39001/39002 admin/member projections. Contained channels carry `community=<community UUID>`; absent remains a valid standalone channel.
- Workspace membership is asserted as direct membership in every live top-level Room for people: invite redemption skips corners, DMs, and archived Rooms while repairing existing Room membership, new community-linked Rooms mirror current human members, and self-listing Workspaces repairs historical/partial projections before mobile Room discovery. Registered agents are linked once at Workspace scope, never participate in that repair, and require an explicit per-Room attachment. Live proof: `packages/buzz-client/src/community-invite-visibility.live.test.ts`.
- Invites are signed kind:30078 lookup records (`t=buzz-community-invite`, `d=SHA-256(token)`, NIP-40 `expiration`). Token-only reads must use `findCommunityInvite`, which also scans the marker tag for legacy group-scoped kind:9 records because Buzz requires an unknown `h` to query those directly. Redemption validates the marker and self-adds through kind:9000; plaintext tokens are never published.
- Invite web authority is `relay-stack/nginx.conf`: the `relay-front` service owns the published relay port, serves `/join/bzi_*` plus both `/.well-known` app-association documents from `relay-stack/web/`, and proxies every other HTTP/WebSocket request to Buzz.

## NIP-05 handles (display + verify + Buzz-issued `name@buzzrouter.com`)

- `packages/buzz-client/src/nip05.ts` owns parsing (`parseNip05Identifier`/`normalizeNip05Identifier`) and client-side verification (`verifyNip05`, fetches `https://<domain>/.well-known/nostr.json?name=<local>` and checks it maps back to the expected pubkey) of a `name@domain` identifier. It never throws — every failure mode (bad format, unreachable domain, malformed response, name/pubkey mismatch) resolves to a distinct honest status (`verified`/`mismatch`/`unreachable`/`invalid`), consumed by `apps/mobile/sources/buzz/nip05-verification.ts`'s cache/hook so a label only ever renders the nip05 string once *that viewer's own client* has independently confirmed it — the profile's `nip05` field itself is never trusted at face value.
- `PersonProfile.nip05`/`PersonProfileInput.nip05` (`packages/buzz-client/src/types.ts`, wired in `person-profile.ts`) round-trips through the standard NIP-01 kind:0 `nip05` content key, same optional-field pattern as `avatar`/`handle`.
- `apps/mobile/sources/buzz/member-display.ts`'s `personIdentityLabel` is the one shared display waterfall (verified nip05 → `@handle` → name → truncated npub); it is wired into `MembersScreen.tsx` (central per-render verification map keyed by pubkey) and `settings/identity.tsx` (own-profile editor + verification badge, `useVerifiedNip05Status`). The chat transcript (`chat/[channelId].tsx`) only got the DM peer room-title spot wired (the one self-contained async call site); its many other `shortMemberNpub` call sites (message author, participant list, mention dropdown) were deliberately left on the pre-nip05 fallback chain — wiring those in means either extracting per-row list components to host `useVerifiedNip05Status` or growing this already 2800+ line file's central `personProfileByPubkey`/effect graph, and was scoped out of the initial landing as a fast-follow rather than risked blind.
- **Issuance** (a first-come-first-served, Buzz-minted `name@buzzrouter.com` handle) is owned by `apps/auth` (`@beeline/auth`), the same deployed TS service that already owns the DB and sits behind `buzzrouter.com` via `relay-stack/nginx.conf`'s `/auth/` proxy — not `apps/gate`, which has no persistence layer. `apps/auth/src/protocol.ts`'s `isValidNip05Name` (lowercase alnum + `-`/`_`, 1-30 chars, reserved-name blocklist) gates a flat `beeline_nip05_names` table (`apps/auth/src/store.ts`'s `claimNip05Name`/`resolveNip05Name`; name is the primary key, so FCFS is enforced by the unique constraint itself — no explicit transaction needed). `POST /nip05/claim` (`apps/auth/src/server.ts`) is NIP-98-authenticated (reuses the same `verifyNip98Header` + `claimNip98Event` replay guard as `/auth/oidc/links/:pubkey`) and reachable through the existing `relay.buzzrouter.com` tenant — it needs no new `BUZZY_AUTH_TENANTS_JSON` entry. `GET /.well-known/nostr.json?name=<name>` deliberately bypasses the tenant/Host map entirely (it's a single flat namespace for the whole product, not per-community) and sets `access-control-allow-origin: *` for cross-origin NIP-05 fetches. **Both routes are new top-level paths, not nested under the existing `/auth/` prefix, so they are not yet reachable in production** — `relay-stack/nginx.conf` needs two new proxy locations to `auth:8789` (`/nip05/` and the exact-match `/.well-known/nostr.json`, mirroring the existing `/auth/` block's headers), and the bare apex hostname `buzzrouter.com` (not just `relay.buzzrouter.com`) must reach the same `relay-front` container for the well-known route to resolve at all, since that's the literal domain NIP-05-verifying clients fetch. `packages/buzz-client/src/nip05.ts`'s `claimNip05Handle` is the SDK call site (same `endpoint`/`nip98AuthHeader`/typed-error shape as `oidc-bind.ts`'s `lookupRecovery`), wired into `apps/mobile/.../settings/identity.tsx`'s "BEELINE HANDLE" section, which writes the claimed `<name>@buzzrouter.com` onto the profile via the existing `setGlobalPersonProfile` immediately (same immediate-write pattern as `changeAvatar`, not the deferred "Save identity" button) so the already-shipped verify/display path lights up as soon as the well-known route is wired.

## Direct messages

- SDK authority: `packages/buzz-client/src/direct-message.ts`. A DM is a deterministic, private NIP-29 Room marked `t=buzz-dm`, bound immutably to one Workspace and two sorted participant pubkeys; SDK discovery requires the current projection to contain exactly those two members.
- Workspace membership propagation and Room/agent invite APIs skip or reject DMs, and mobile hides the Room member picker in DM chat. Agent DMs are discovered by `apps/body/src/supervisor.ts` but remain strictly conversational/read-only: they never borrow another Room's repository, request write permission, or open an edit corner.
